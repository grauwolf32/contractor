# Предложение: переносимые eval’ы playground-v2 через существующий сервер

Статус на 2026-09-07: **V41-001–V41-008 завершены; portable v2 реализован в
playground-v2 и прошёл [offline readiness gate](reviews/portable-eval-format-readiness.md)**.
Ниже сохранено исходное предложение и описание исходной связности. Точные поля,
версии, владельцы данных и правила сравнения определяет
[спецификация 26](spec/26-portable-evaluation-format.md). Следующий этап V40 —
fixtures, bindings и frozen plan для отдельного эксперимента с инструкциями.
Качество модели ещё не измерено; readiness report перечисляет ограничения
live adapters, service pins и budgets.

Цель — использовать и развивать eval’ы `playground-v2`, запускать Contractor
через его существующий серверный механизм и сохранять возможность проверить
другую реализацию теми же кейсами и критериями.

## Исходная база предложения

В `playground-v2` имеются проекты, корпуса и закреплённые subsets, скрытый ground
truth, схемы suites/results, предметные scorers, управление тестовыми targets,
`ContractorV2Client`, Workflow runner и Audit runner. Они используют публичный
HTTP API и не импортируют внутренние пакеты Contractor. Эту основу переиспользуем.

В Contractor уже есть evaluation Projects, обычные Runs, метки `eval.*`, точные
артефактные ревизии, идемпотентное создание, очередь, retries, cancellation,
метрики и UI для просмотра. Новый движок выполнения не требуется.

Исходная связность в playground: `suite.schema.json` допускает только два
Contractor-адаптера; `runner.py` напрямую использует `ContractorV2Client`; в
`result.schema.json` есть поля `contractor_run_id`, `contractor_audit_id` и
`contractor_run_ids`. Это границы для адаптации, а не повод переписывать harness.

## Предлагаемые границы

| Часть | Ответственность | Зависимость от Contractor |
| --- | --- | --- |
| Dataset / case | Исходники или target, задача, скрытые ожидания, provenance, требования к возможностям | Нет имён Workflow, tools, namespaces и внутренних типов |
| Suite / experiment | Выбор кейсов, scorers, вариантов, повторов, бюджетов и критериев сравнения | Только ссылка на отдельную конфигурацию адаптера |
| Execution adapter | Подготовка входов, submit/observe/cancel/collect, преобразование результата в общий вид | Здесь находятся Workflow/AuditProfile refs, API и привязки артефактов |
| Scorer | Оценка предметного результата и подтверждающих доказательств | Не знает об ADK, внутренних классах, конкретных tools или порядке исследования |
| Result publisher | Сохранение/экспорт manifest, результатов и сравнения | Contractor Project artifacts — один поддерживаемый способ публикации |

В первой реализации достаточно одного адаптера Contractor и тестового адаптера,
возвращающего заранее записанные результаты. Полноценная plugin-система, второй
боевой backend и перенос всех старых suites не нужны для первого пилота.

## Минимальные доработки

1. **Отделить кейс от способа исполнения.** Сохранить проекты, корпуса и ground
   truth playground. Вынести Workflow/Profile selectors, параметры их API и
   mapping выходов в execution binding. Один case должен запускаться с двумя
   bindings без копирования source или ожиданий. Возможности проверять явно:
   исходники, HTTP target, trace, OpenAPI, LikeC4, Audit и т. п. Неподдерживаемый
   кейс отмечать отдельно, сохраняя его в отчёте о покрытии.
2. **Нормализовать наблюдаемый результат.** Общая часть: идентичность case/sample/
   variant, outcome выполнения, логические выходы, evidence refs, usage с признаками
   полноты и provenance. `provider` и непрозрачные execution refs содержат ссылки
   на Run/Audit, но scorers не разбирают внутреннюю структуру этих идентификаторов.
   Score и технический outcome остаются отдельными. Неизвестные метрики — `unknown`,
   не ноль. Несовместимое изменение схемы получает новую версию; v1 читается через
   совместимый преобразователь, существующие suites продолжают работать.
3. **Добавить experiment identity и восстановление в имеющийся runner.** Единый
   experiment ID, явные A/B и sample, заранее сохранённая матрица, стабильные ключи
   отправки, восстановление после частичного запуска. Сейчас Workflow runner
   создаёт отдельный `eval.id`, фиксирует `eval.leg=project` и генерирует случайный
   idempotency key при вызове — этого недостаточно для возобновляемого A/B.
4. **Сопоставлять результаты и публиковать отчёт.** Пара определяется case/sample,
   ожидаемые участники — manifest’ом. Учитывать все страницы, пропуски, дубли,
   неудачные попытки и неполные метрики. Переиспользовать имеющиеся scorers;
   добавлять только недостающие проверки качества доказательств и контрпримеры.
   Нормализованный результат сохраняется в playground; publisher дополнительно
   сохраняет manifest/scores/comparison обычными Project-артефактами Contractor,
   с общей идентичностью и digest. Ground truth остаётся только у evaluator и
   не загружается на сервер или в контекст агента.

Для Contractor каждая обычная попытка остаётся отдельным Run с `eval.*` метками.
Прежний и новый вариант выбираются точными версиями конфигураций, например
OpenAPI `@5` и `@6`; labels не управляют prompt. Выходы берутся по точным Run refs,
а не из общей Project-привязки `outputs/<slot>`. Audit adapter использует штатные
Audit controller/importer и сохраняет соответствие Audit/item/child Run; его
особенности не переходят в общий runner или базовые кейсы.

## Что проверяем независимо от реализации

Основная оценка — полнота и правильность API/архитектуры, подтверждённость findings,
отсутствие ложных находок, корректность trace и оценок Audit. Имена tools,
конкретная цепочка вызовов и число внутренних агентов не являются критерием
предметного качества. Проверки протокола Contractor остаются отдельными contract
tests в его репозитории; число вызовов и повторов — диагностические метрики.

Реальная предметная зависимость сохраняется: OpenAPI/LikeC4 проверяются их
валидаторами, а benchmark с внешним oracle использует закреплённый oracle. Например,
WebExploitBench нельзя заменить поиском слов в отчёте: его verifier и judge должны
наблюдать тот же target. Адаптер изолирует инфраструктуру, но не меняет смысл eval.

## Первый этап и критерии готовности

Начать с имеющихся widget-service / FastAPI suites для OpenAPI, LikeC4 и trace,
затем подключить Audit smoke. Зафиксировать источники, expectations, scorers,
модели, Skills, tools/docstrings и бюджеты; в A/B менять только инструкции и
соответствующие версии конфигураций. Матрица из 18 предложенных сценариев — список
пробелов для сопоставления с готовыми кейсами playground, а не 18 новых fixtures.

Готовность первого этапа:

- один case и один scorer работают с Contractor adapter и записанным результатом
  через тестовый adapter без изменений в кейсе/scorer;
- существующие v1 suites/results продолжают читаться;
- возобновление частичного A/B не создаёт лишние Runs;
- сравнение учитывает отсутствующие, повторные и failed попытки;
- все оценки связаны с точными source/config/result revisions и доступны из
  серверного evaluation Project, скрытый ground truth не передаётся агенту;
- отчёт различает качество, техническую успешность и стоимость.

В первый этап не входят универсальный UI-конструктор экспериментов, новый
Scheduler, отдельное хранилище Runs и новая реализация уже имеющихся scorers.
Основная работа находится в `playground-v2`; в Contractor — совместимость API,
версии конфигураций и только подтверждённые недостающие серверные возможности.
