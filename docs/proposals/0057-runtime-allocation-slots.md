# Несколько аллокаций в одном Runtime

Предложение от 25 ноября 2026 года. Подготовлены задачи для последовательной
реализации. Проверка общего mitmproxy ещё предстоит.

Оператор запускает один Runtime с четырьмя одновременно работающими аллокациями,
чтобы совместно использовать интерпретатор, библиотеки и процессные ресурсы.
Количество слотов задаётся параметром запуска конкретного Runtime. Разные
Runtime могут иметь разную ёмкость. Расход памяти и пропускная способность
подлежат измерению на одинаковой нагрузке.

## Основания и авторство

Решения пользователя от 2026-11-25 задают следующий порядок и границы.

- Сначала проверить изоляцию сессий общего mitmproxy.
- Затем реализовать несколько аллокаций в одном процессе с параметром запуска.
- Runtime владеет Podman и bridge и выдаёт аллокациям отдельные ресурсы.
- Очистка обязательна для каждого исхода аллокации и остановки процесса.
- Кэш артефактов общий для аллокаций Runtime.
- По возможности сократить код. Рост реализации должен быть обоснован.

Предложения агента для реализации — имя `--allocation-slots`, диапазон `1..4`
и default `4`, один heartbeat и lease на Runtime, ограниченный набор
allocation-local состояний и ленивое создание ресурсов. Диапазон и default
являются предложенными значениями, которые можно уточнить перед реализацией.
Смена значения через перезапуск создаёт новый `instance_id` при сохранении
сертификатной идентичности Runtime. Повторная регистрация живого экземпляра
подтверждает прежнюю ёмкость. Динамическое уменьшение ёмкости требует отдельного
решения о завершении уже занятых слотов.

Это проект будущего поведения. Изменения нормативных требований вносятся вместе
с соответствующим кодом и проверками в задачах ниже.

## Владение и минимальная структура

Control Plane владеет размещением, grant, lease и подтверждением release.
Runtime владеет доступной ёмкостью и реальными ресурсами процесса.
HTTPTransport сохраняет интерпретацию engagement, policy, credentials, cookies,
redirect/retry, счётчики и результаты конкретной аллокации. Podman backend
сохраняет исполнение и доказательство остановки контейнера. ArtifactStore
сохраняет авторизацию, exact revisions и retention.

| Ресурс Runtime | Ресурс аллокации | Граница очистки |
| --- | --- | --- |
| Регистрация, heartbeat, listener, capability snapshot, watchdog | Worker, State, RuntimeSettings, tasks, workspace | Завершение аллокации освобождает её объекты после joined cleanup. |
| Один лениво создаваемый HTTP engine | HTTP-сессия, соединения, trust, identity jars, вызовы сканеров | Закрытие сессии отзывает её authority и удаляет её приватное состояние. Общий engine закрывается при остановке Runtime. |
| Один Podman lifecycle/owner | Контейнер, guardian, workspace mount, команды | Аллокация прекращает команды, подтверждает остановку и удаление контейнера, затем удаляет mount files. |
| Один существующий archive cache | Авторизованные readers/fills и отдельные распакованные каталоги | Release joins собственные операции. Допустимые завершённые cache entries живут до eviction, TTL или остановки процесса. |

Расширять существующие владельцы и точки composition. Удалить заменённые
single-allocation поля, ветви, наблюдения API и тестовые обходы. Ввести только
те структуры, которые требуются текущим production callers. Отдельный общий
resource broker, plugin framework, новый receipt store или persistent pool
не требуются. Существующие идентификаторы аллокаций остаются authority для
запросов и ресурсов. Слот представляет ограниченную ёмкость процесса.

Подготовка, финализация и освобождение разных аллокаций могут продвигаться
независимо. Подготовка и неподтверждённая очистка занимают ёмкость. Долгая I/O
не удерживает общую блокировку таблицы аллокаций. В одном Worker по-прежнему
выполняется одна A2A Task за раз.

## Первый эксперимент с mitmproxy

Эксперимент использует закреплённую библиотеку, один engine в одном Python
процессе, реальные локальные HTTP/TLS endpoints и существующие HTTP/bridge
пути. Он проверяет две конфликтующие сессии, затем четыре одновременно.
Одинаковые origin, имена identity и cookies имеют разные секретные значения.
Доверенные CA и входные proxy capabilities различаются.

Гарантии, которые требуется продемонстрировать на принимающих endpoints и
наблюдении фактических соединений, перечислены ниже.

- Tool получает выданную сессию с неизменяемым владельцем. Scanner capability
  проверяется и связывается с этой сессией. Текст allocation ID в запросе
  самостоятельно полномочий не даёт.
- Ingress connection, CONNECT и HTTP/2 streams закреплены за владельцем.
  Чужой, отозванный и старый токен не выдаёт запрос другой сессии.
- Исходящие connection pools разделены по allocation session, credential
  identity, exact origin и эффективному TLS-профилю. Cookies, auth headers,
  request IDs, captures и счётчики сохраняют владельца.
- DNS, redirects, retries, TLS callbacks и queued sends проходят authority
  проверку нужной сессии. Блокировка или смена глобального `ctx` вокруг await
  не доказывает изоляцию. Проверяется работа callbacks в потоках.
- Закрытие одной сессии при незавершённом handshake, HTTP/2 stream и scanner
  invocation joins её работу. Остальные сессии продолжают запросы. Запоздалые
  callbacks после повторного использования слота не получают новую authority.
- Повторные циклы создания и закрытия сессий освобождают references, tasks,
  sockets, TLS-материалы и временные файлы. Проверка учитывает private caches
  закреплённой библиотеки и не ограничивается успешными HTTP-ответами.

Результат эксперимента содержит команду воспроизведения, версии, матрицу
проверок, фактические результаты, необходимый объём адаптации библиотеки и
решение о применимости. Успешный результат разрешает переход к реализации.
При провале автор завершает исследование с отрицательным результатом, добавляет
`context.decision_needed` в зависимые задачи и сохраняет их `pending`.
Варианты для обсуждения — allocation-specific HTTP subprocess с измерением
памяти или пересмотр интеграции общего движка. Выбор альтернативы остаётся
открытым до появления такого результата.

## Ёмкость и управляющий протокол

Runtime строго разбирает параметр запуска и объявляет ёмкость при регистрации.
Различающиеся значения между Runtime допустимы. Один `instance_id` соответствует
одной стартовой декларации. Новый экземпляр с меньшей ёмкостью проходит обычную
замену старого и сверку его аллокаций. Занятый процесс перед плановым перезапуском
можно освободить от работы через действующий lifecycle.

Одна последовательность heartbeat и один подтверждённый lease обслуживают
процесс. Наблюдаемое состояние каждой аллокации передаётся явно, сверка возвращает
адресные действия. Протокол ограничивает коллекции и байты, отклоняет дубли,
невозможную ёмкость и неверную принадлежность. Повторный heartbeat сохраняет
прежний ответ. Server и Runtime независимо предотвращают переполнение.

Подбор Workers использует свободную ёмкость совместимых процессов. Несколько
Workers одного Stage могут разместиться в одном Runtime. Резервирование
Stage остаётся all-or-nothing. Существующие правила приоритета model Stages,
capacity backoff, Scheduler lanes, grants и записи размещения сохраняют свой
смысл при разной ёмкости. Потеря lease закрывает все аллокации данного экземпляра.
Один неизвестный или несовпадающий allocation state сверяется адресно.

Operations показывает ёмкость, занятость, состояния и все аллокации процесса.
Показатель `runtime_process` отражает процесс за интервал наблюдения.
Пересекающиеся измерения нельзя суммировать как независимый расход аллокаций.

## Общий кэш артефактов

Развивать существующий `ImmutableArchiveCache` согласно
[RTA-R119–R124](../spec/execution/runtime-agent.md#private-immutable-archive-cache).
Для этого среза общий кэш означает уже поддерживаемые immutable ZIP source и
Skill packages. Остальные Artifact reads сохраняют свои действующие контракты.
Расширение перечня кэшируемого содержимого требует отдельного caller и решения.

Каждый hit и coalesced reader сначала получает metadata с grant своей
аллокации. Ключ сохраняет trust domain и content identity, без scoped aliases
и grants. Shared bytes распаковываются в отдельные allocation-owned каталоги.
Отзыв доступа, удаление Project/Run и отказ metadata исключают cache hit.

Общие лимиты сохраняются на весь Runtime — 1 GiB логических байтов, 1024 entries,
4 MiB metadata, 4 simultaneous fills, 64 waiters, 24-hour non-sliding TTL,
bounded maintenance по LIM-RTA-10–15. Они не умножаются на число слотов.
При отмене лидера его fill joins работу до освобождения grant. Waiter может
продолжить обычную авторизованную загрузку со своим grant. Release одной
аллокации не закрывает cache и не удаляет данные, которыми пользуется другая.
Shutdown joins всех пользователей и удаляет принадлежащие cache файлы.

## Очистка и исходы отказов

1. Запретить новые операции конкретной аллокации и отозвать proxy capabilities.
2. Остановить и join её Worker, scanners, команды, streams, callbacks,
   readers и fills под существующими deadline владельцев.
3. Подтвердить остановку и удаление контейнера до удаления mounted workspace.
4. Удалить private HTTP state, credentials, TLS files, workspace и Skill state,
   а также удерживающие их ссылки ADK и процессных реестров.
5. Завершить существующий release handshake. До подтверждения слот недоступен.

| Исход | Требуемый результат |
| --- | --- |
| Success | Удалено состояние только завершённой аллокации, соседи продолжают работу. |
| Permanent validation/policy failure | Классифицированный отказ с существующим кодом, без повторения неизменного запроса. |
| Retryable resource failure | Действующие ограниченные retry/deadline, точные cleanup handles сохранены. |
| Lost response | Повтор операции с прежним allocation/operation ID сверяется существующим receipt/release механизмом. |
| Cancellation/timeout | Joined cleanup, сохранённые handles при неопределённости, занятая ёмкость до подтверждения. |
| Unconfirmed producer stop | Существующее аварийное завершение Runtime затрагивает все его аллокации. Server учитывает каждую потерю. |
| Runtime shutdown/crash | Общие сервисы закрываются после пользователей, следующий owned startup очищает допустимые остатки до admission. |

Владелец принятого общего failure domain — Runtime lifecycle. Проверка
process-loss в завершающей задаче обнаруживает нарушения. Вернуться к вопросу
процессной изоляции следует при требовании переживать зависание соседней
аллокации. Приватность сессий проверяется на доверенном Runtime-коде и обычных
sandbox границах проекта, отдельная изоляция адресного пространства Workers
этим предложением не вводится.

Первый production срез изменения ёмкости в V487-004 проходит через реальные
Server, Runtime и PostgreSQL. Четыре операции удерживаются управляемыми

продолжающихся трёх. Затем проверяются смешанные ёмкости 1, 2 и 4, Stage с
несколькими Workers, HTTP и Podman, повторные ответы и потеря процесса.

Нормативные изменения распределены по владельцам. V487-002 обновляет HTP и
HTTP lifecycle. V487-003 обновляет EXE и Podman lifecycle. V487-004 обновляет
CTL-R112/R142/R143, RTA-R1/R116, SCH-R139, LIM-CTL-4, обзор/glossary,
architecture, wire fixtures, OpenAPI и оба generated clients, UI и startup docs.
Существующий archive-cache контракт усиливается необходимыми concurrent cases.

Проверены соседние планы. [Предложение 0053](0053-mitmproxy-runtime-and-sandbox.md)
фиксирует историческое allocation-owned встраивание и отдельный sandbox routing.
Настоящий план заменяет только владение общим HTTP engine. V410-037 сохраняет
allocation-owned VPN и получает HTTP-сессию своего владельца, V411-013 использует
обычные sandbox/HTTP boundaries. V469-002 расширяет Podman для retained Audit
environment со своим lifecycle. Этот retained ресурс не должен попадать под
удаление соседней обычной аллокации, если тот план будет реализован первым.
При начале V487-002/V487-003 проверяется актуальный код этих интеграций.
Их отдельные продуктовые возможности и существующие зависимости сохраняются.

Каждая implementation-задача фиксирует удалённые поля, функции и ветви,
новые абстракции и их production callers. Изменение строк production-кода
показывается отдельно от tests, generated и docs. Численного лимита строк нет,
но каждый оставшийся рост должен объясняться конкретной гарантией. Предпочтение
отдаётся удалению старого пути и одному владельцу cleanup с ограниченным
состоянием. Проверяются все затронутые пакеты и потребители изменённых gates.

Выходная проверка сравнивает четыре однослотовых процесса и один четырёхслотовый
на одной сборке, одинаковых входах и фазах прогрева. Сохраняются RSS/PSS,
private memory и память дочерних процессов, latency и heartbeat responsiveness.
Число выигранных MiB заранее не обещается. Optional heavy-I/O проверки
запускаются только по явному флагу. PostgreSQL и Podman случаи требуют реальных
компонентов, отсутствие prerequisites отражается как незавершённая проверка.
