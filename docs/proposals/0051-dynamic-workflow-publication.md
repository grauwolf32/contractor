# Динамическая публикация Workflow

Дата: 31 октября 2026 года. Исходная ревизия:
`feec3d0ff51621aac01a4156c3a43288bdc6f31f`.

Статус: направление, выбранное пользователем 2026-10-31. Динамическое
создание и публикация новых Workflow рассматриваются как отдельная будущая
возможность. Для текущего рефакторинга конфигураций достаточно этого
направления; реализация публикации не становится его предпосылкой.
Задачи на реализацию этой заметкой не создаются. Действующие контракты
остаются в [спецификации](../spec/configuration/catalog.md).

## Направление

Изменения моделей, политик и бюджетов для эксперимента следует описывать
вариантами Workflow. Run выбирает готовый Workflow, получает параметры и
материалы, фиксирует разрешённый snapshot и выполняет его. Eval сравнивает
выбранные варианты Workflow.

Целевой путь:

```text
Создать или скопировать Workflow
  → изменить определение
  → проверить на Server
  → опубликовать новую неизменяемую версию без рестарта
  → выбрать её для Run или Eval
```

Это позволяет пересматривать необходимость `Run.executionConfig` и
соответствующих Eval overrides. Разрешение конфигурации и точный snapshot
Run сохраняются независимо от наличия этих переопределений. Конкретный
состав удаляемых полей и уровней определяется задачами текущего рефакторинга.

До появления динамической публикации варианты Workflow можно готовить
через существующий файловый каталог и загрузку при старте Server. Текущий
рефакторинг не должен разрастаться в систему публикации ради удаления
каскада настроек.

## Будущая возможность

Пользователь создаёт Workflow из существующего определения или импортирует
YAML, меняет политики либо структуру, получает серверную диагностику и
публикует новый вариант. Он сразу появляется в каталоге для запуска и
сравнения. Существующие Runs продолжают использовать свои snapshots.

Публикация добавляет новое имя или версию; изменение уже опубликованной
версии не входит в направление. YAML anchors и aliases внутри одного
Workflow должны проходить тот же путь проверки, что и развёрнутые блоки.

Предложение агента для первого среза: публиковать только Workflow со ссылками
на существующие AgentTemplates, инструкции, ModelPolicy и Gateway. Этого
достаточно для сценария «скопировать Workflow и изменить политики».
Публикация новых зависимостей и импорт полного набора рассматриваются
отдельно.

## Основа и открытые решения

Существующий [config.Manager](../../internal/config/manager.go) уже владеет
управляемой публикацией ModelPolicy и Gateway: проверкой, долговечной записью,
идемпотентностью и атомарным обновлением каталога. Предлагается развивать
этот механизм для Workflow. Сейчас Workflow доступны только для чтения,
а изменения файлов загружаются при старте Server; это текущие ограничения
[CAT-R45](../spec/configuration/catalog.md) и
[CAT-R72](../spec/configuration/catalog.md).

Перед реализацией отдельно определяются API и права публикации, состав
зависимостей и гарантии их фиксации, поведение при сбоях, границы размера и
количества версий, lifecycle опубликованных определений и путь редактирования
в UI. Место deployment defaults и инфраструктурных настроек Gateway и
credentials также требует отдельного решения. Эта заметка не задаёт новый
формат конфигурации, endpoints или хранилище черновиков.
