# Validation и retest для Finding

Статус: согласовано направление, задачи реализации pending. 28 ноября 2026.
Этот документ описывает будущую возможность; нормативные спецификации и код
пока не меняются. Планирование не означает начало реализации или разрешение
на запуск проверок против живого Project target.

## Пользовательский результат и авторство

Из карточки существующего Project Finding исследователь запускает проверку
конкретного утверждения, получает доказательства в истории той же проблемы
и повторяет выбранную проверку после исправления приложения.

Решения пользователя, 2026-11-28:

- Добавить retest и validation к Finding.
- Retest выполняет тот же тип агента с аналогичным набором инструментов;
  инструкции и входные данные меняются под повторную проверку.
- Зафиксировать обсуждённое предложение и разложить на задачи.
- **Первый сценарий: finding из sources → validation на target → retest
  после исправления.**
- Последующее уточнение: делать изменения максимально компактно, максимально
  переиспользовать существующие механизмы либо обобщать их; новый код добавлять
  только при доказанной необходимости.

Принятое направление обсуждения: отдельные результаты проверок и доказательства
дополняют один Finding; оценка аналитика остаётся отдельной. Validation выбирает
способ получения доказательств; проверка в коде и воспроизведение на target
имеют разные гарантии. Обычные Workflow/Run, Artifact, receipts и история
переиспользуются.

Конкретная декомпозиция, границы первого выпуска, имена будущих полей и
технические ограничения ниже — предложение агента в рамках этого направления.
Изменение поведения, владельца или существенное расширение общей подсистемы
требует пересмотра плана по AGENTS.md 4.1. Модель проекта не меняется.

## Два действия и два способа проверки

| Действие | Цель | Основание |
| --- | --- | --- |
| Validation | Получить дополнительные доказательства конкретного утверждения | Выбранный source receipt существующего Finding и его точные материалы |
| Retest | Повторить известный способ проверки на выбранных текущих материалах/target | Явно выбранная предыдущая проверка или воспроизводимый источник обнаружения |

| Способ | Проверяемое свойство | Граница вывода |
| --- | --- | --- |
| HTTP target | Поведение приложения при выбранном запросе, роли и условиях | Конкретная цель, время, deployment и условия доступа |
| Sources | Причина и достижимость дефекта в выбранном коде | Точная ревизия исходников и исследованные пути |

В первом выпуске исполняется только способ HTTP target. Validation получает
source Finding, а retest повторяет **выбранную HTTP-validation**, уже выполнившую
проверку и сохранившую принятый результат. Исходный source-reviewer не становится
HTTP-агентом. Неуспешный технический запуск можно повторить обычным действием
Run; он не подменяет основание retest, для которого требуется сохранённая
проверка с условиями и результатом.

Retest создаёт новую сессию, сохраняя профиль исполнителя, инструменты, skills
и ограничения метода основания. Сохранённые credentials, cookies и диалог
не копируются. Текущий разрешённый target/credential pin и модель проекта
выбираются обычным путём. Версионированные инструкции retest задают повторение
одного сценария и сравнение условий; исторические конфигурации не мутируются.
Если совместимый профиль недоступен, операция объясняет причину до запуска,
без молчаливого выбора другого агента или расширения инструментов.

Способ sources и retest исходного source-обнаружения — следующий срез V497-005.
Универсальный retest любых сторонних scanners и автоматический выбор метода
по тексту Finding в эти два среза не входят.

## Первый сквозной сценарий

1. Обычный source Workflow создаёт Finding с source receipt и exact evidence.
2. В карточке выбираются receipt, утверждение для проверки и действие
   «Проверить на работающем приложении». Показываются текущий Project target,
   выбранный профиль, разрешённая учётная запись/роль и пределы запуска.
3. Server фиксирует Finding ID/revision, receipt, точные материалы, утверждение,
   исполнителя и безопасную конфигурацию target. Создаётся обычный Project Run.
4. HTTP Worker проверяет утверждение, явно сохраняет контрольный и проверочный
   обмены, условия, ограничения и вывод. Runtime собирает структурированный
   результат; Server принимает его в историю исходного Finding.
5. Приложение исправляется и развёртывается владельцем вне этого Workflow.
   Из конкретного результата validation запускается retest. Пользователь видит
   прежнюю и выбранную текущую цель/версию, отличия условий и основание сравнения.
6. Новый Run повторяет метод проверки. В истории остаются оба результата,
   их evidence, исполнители и условия; исходный Finding и оценка аналитика
   не переписываются.

```mermaid
flowchart LR
    S["Source Run"] --> F["Project Finding + source receipt"]
    F --> V["HTTP validation: обычный Run"]
    V --> E["Сохранённый результат + HTTP evidence"]
    E --> R["HTTP retest после исправления: новый Run"]
    R --> E2["Новый результат + сравнение условий"]
    E --> H["История того же Finding"]
    E2 --> H
    H --> A["Отдельное решение аналитика"]
```

Демонстрация использует настоящий Server, PostgreSQL, Runtime и управляемое
HTTP-приложение с уязвимым и исправленным состояниями. Scripted Gateway делает
сценарий детерминированным, но не подменяет HTTP, сохранение evidence или
публичные API. Такая демонстрация не доказывает качество живой модели.

## Семантика результата

Существующие `supported`, `refuted`, `inconclusive` сохраняют значение
[ACT-R4–R6](../spec/audits/common-contract.md#ACT-R4). Проверяется ограниченное
утверждение, например «роль reader может прочитать чужой документ через
GET /documents/{id}», с явно записанными условиями. Положительный и отрицательный
вывод требуют доказательств; inconclusive требует ограничения.

- Технические `succeeded`, `failed`, `cancelled` относятся к Run.
- `supported` подтверждает утверждение в проверенных условиях.
- `refuted` опровергает конкретное ограниченное утверждение в этих условиях.
  Один отрицательный probe не опровергает существование дефекта вообще.
- `inconclusive` означает, что данных для вывода не хватило: login не удался,
  отсутствует нужная роль, target недоступен, путь не установлен или бюджет
  закончился до достаточной проверки.

UI показывает «воспроизведено», «не воспроизвелось в проверенных условиях»
или «не удалось сделать вывод» только по принятому результату. Сбой Run без
такого результата остаётся сбоем исполнения. Ранее принятый результат/evidence
при последующем сбое сохраняется с исходом соответствующей попытки.

«Не воспроизвелось» не меняет Finding на fixed/false positive. Новый статус
исправления и автоматическое закрытие не вводятся. Concurrent analyst edit
после старта не отменяет исторический результат по старому snapshot и не
разрешает записать поверх новой оценки. Итоговый «общий verdict» из последнего
Run или большинства источников не вычисляется.

Сопоставление исходников и deployment может быть подтверждённым, заявленным
владельцем либо неизвестным; сохранить фактическое основание и ограничение,
не вводя для этого систему учёта deployments. URL и время наблюдения не
заменяют идентичность сборки. Неизвестная версия не запрещает HTTP-проверку,
но ограничивает связь её вывода с найденным кодом.

## Текущее основание и недостающая возможность

Уже существуют:

- Project Finding, immutable sources и независимая история результатов
  ([FND-R209–R219](../spec/findings/findings.md#FND-R209)).
- Exact finding collections и их передача обычным Run
  ([FND-R226–R229](../spec/findings/findings.md#FND-R226)).
- HTTP evidence, включая несколько выбранных обменов в одном Finding;
  сохранение HTTP не означает повтор запросов ([FND-R241](../spec/findings/findings.md#FND-R241)).
- Runtime-owned result collection, `evidence`/`submit_result`, tested conditions
  и limits ([AWC-R127–R129](../spec/audits/worker-completion.md#AWC-R127)).
- Pinning Project target и credentials при Run creation
  ([PRJ-R80](../spec/artifacts/projects.md#PRJ-R80)).

Это ещё не готовый запуск validation из Finding. Сейчас
`internal/runservice/audit_completion.go` получает completion из Audit binding;
`internal/runstore/audit_completion.go` допускает pin только у `audit-managed`
Run; Runtime collector использует Audit judgment persistence. Исторический
direct-verification path в `internal/auditstore/internal/pgstore/finding_intake.go`
также связан с Audit collection. Нельзя объявить обычный Run работающим,
просто подключив ему `audit-results@2` или передав произвольный JSON от модели.

Проверка main `d4b8c5112fef383a47ce3aae9abc1094e346c2e5` уточняет объём:
ограничение `audit-managed` есть также в PostgreSQL CHECK и Scheduler;
`auditservice.RecordJudgments` требует AuditExecution/Task membership,
AuditScope и Audit budgets, а Runtime receipt содержит Task generations.
Поэтому это изменение границы владения completion, не только настройка
AgentTemplate. Общие validation/assembly/evidence/Artifact операции надо
переиспользовать; целиком переносить Audit task registry, budgets и lifecycle
в обычный Run не требуется. Если сохранение принятых гарантий требует большого
переноса, отдельно предъявить предпосылку и варианты до расширения реализации.

V497-001 — отдельная узкая предпосылка всего сценария и одновременно первая
вертикальная поставка: одна source→HTTP validation через public API и реальные
компоненты. Она распространяет существующий механизм completion/judgment
на конкретного обычного Run caller, сохраняет доказательства в том же Project
и связывает результат с выбранным source receipt. Привязка к Audit становится
контекстом его собственных вызовов, а не обязательной сущностью для Finding check.

Уточнение при начале реализации 28 ноября: первоначальное объединение общего
completion ownership и публичного launch в V497-001 недооценило предпосылку.
Прежде нужны изменения согласованных Audit-only authority, receipts и retention
на Server, Runtime и в схеме. По правилу AGENTS.md 4.1 выделена V497-006:
она обобщает уже используемый приём evidence/results с сохранением Audit caller.
V497-001 зависит от неё и затем даёт первый публичный source→HTTP сценарий.
Черновик изменения launch/pin не оставлен в implementation tree: компиляция
не доказывает сохранение этих гарантий. Ни одна возможность не объявлена готовой.

## Границы ответственности и альтернативы

| Владелец | Ответственность |
| --- | --- |
| Finding domain/service | Snapshot выбранного Finding/source, допустимое основание retest, доверенная связь нового результата с существующим Finding, чтение его истории |
| RunService / Scheduler | Единственный путь создания и исполнения Run, idempotency, completion pin, deadlines, retry/cancel и восстановление финализации |
| Runtime / HTTP adapter | Реальные запросы, выбранные captures, tool observations, сбор ограниченного результата; HTTP-парсинг остаётся в адаптере |
| Artifact owner / существующий judgment persistence | Exact bytes, CAS/receipt replay, принятые evidence/judgments, публикация и retention |
| UI | Явный выбор основания/цели, запуск через public API, история и различение исполнения, результата проверки и оценки аналитика |

Server выводит Finding/Run/Project/source provenance из авторизованного контекста.
Модель даёт ограниченный вывод и выбирает evidence; она не назначает родительский
Finding, canonical assessment или происхождение результата. Проверка не должна
повторно вызывать `finding` для сохранения того же утверждения. Если Worker
отдельно публикует иную проблему, обычный intake сохраняет её независимо.

Рекомендовано: расширить общий completion/judgment путь ровно для одного
finding-bound Run и переиспользовать историю/Artifact retention. Audit-вызовы
продолжают пользоваться тем же ядром. Заменённые Audit-only предположения
удаляются из общего пути; второй assembler, очередь, controller, receipt store
или mutable FindingCheck lifecycle не добавляются. Если общий путь потребует
перестройки Audit или нового координирующего механизма, остановиться, выделить
предпосылку и пересмотреть границу, а не поглощать её задачей.

Более простая альтернатива: создавать Audit с одной Task на каждую кнопку.
Она меньше меняет текущий completion, но добавляет пользователю и cleanup
искусственные Audit/Task сущности и связывает обычную проверку с их lifecycle.
Альтернатива с Markdown-отчётом обычного Run дешевле, но не даёт принятого
структурированного результата и надёжного сравнения. Эти варианты не выбраны.
Вернуться к первому, если доказанная цена общего расширения несоразмерна срезу.

## Вход, публикация и границы работы

Один запуск первого среза проверяет один Finding, один явно выбранный source
receipt или результат-основание и одно утверждение. Request содержит purpose,
основание, ожидаемую revision, параметры выбранного профиля и явный выбор
текущих материалов. Exact finding/input refs, effective Workflow/AgentTemplate,
target и безопасные сведения о роли фиксируются Server; secrets остаются
в существующем credential path. В первой реализации принимать только HTTP
method; source method добавляется вместе с production caller V497-005.

Result — обычный неизменяемый Artifact с trusted provenance, semantic conclusion,
tested conditions, limitations и exact evidence. Связь ретеста с предыдущим
результатом точная. История использует существующие Project finding history
artifacts и индексируемую связь Run с основанием; строки новых таблиц не
обосновываются одним удобством UI. Конкретное размещение pin/связи проверяется
по владельцам существующих таблиц в V497-001.

История первого среза остаётся привязанной к выбранному source receipt;
существующий reader уже возвращает её Artifact metadata с пагинацией. Общая
лента по всем источникам Finding не является новой обязательной возможностью.
Сравнение получает два exact результата обычными Artifact reads и показывает
их условия/evidence; отдельный comparison endpoint или сохранённая projection
для этой пары не нужны. Existing Finding source origin хранит Workflow ref и
digest, что само по себе не является полной копией исполняемой конфигурации.
Для обещанного retest после purge сохранить действительно необходимые exact
профиль/материалы обычными bindings; не восстанавливать их из имени/digest.

Границы предлагаемого среза: один item и один passthrough Worker на Run;
не более 1 MiB launch metadata; result/evidence — действующие LIM-AWC-2–6
(включая общий 8 MiB бюджет); коллекция входов — действующие FND bounds без
загрузки всей истории. History page — максимум 64 metadata rows, до 1 MiB;
полные материалы читаются отдельно через Artifact limits. Нужные числовые
ограничения регистрируются в limits и общих fixtures при реализации.
Тестовая история содержит 10 000 записей: работа одного запроса не растёт
с полным числом проверок или источников. Lifetime quota отдельно не вводится.

## Отказы, повторы и lifecycle

| Ситуация | Исход |
| --- | --- |
| Чужой/отсутствующий Finding, receipt, result или материал | Отказ до запуска и target traffic; публичный ownership-not-found |
| Stale revision, несовместимое основание/профиль, превышение лимита | Permanent conflict/invalid response; ни нового Run, ни принятой связи результата |
| Повтор launch с тем же ключом и содержимым | Тот же Run через существующую Run/request receipt; другой payload конфликтует |
| Storage serialization conflict | Существующий bounded retry и `503 storage_transaction_conflict`; HTTP не повторяется для исправления store write |
| Ответ сохранения результата потерян | Сверка того же receipt/точных bytes и окончание финализации без повторного model/target вызова |
| Target/auth/network не позволяют проверить | Явное ограничение либо техническая ошибка; никакого вывода «исправлено» |
| Ответ target потерян после возможного эффекта | Не считать запрос невыполненным и не повторять скрыто; сохранить неопределённость |
| Cancel/deadline | Обычный Run fencing и joined cleanup; принятые материалы сохраняются, late writes не оживляют запуск |

У первого HTTP-профиля нет автоматического повторения активной Stage после
failed/interrupted: новый target запуск явный. Store/finalization reconciliation
сохраняется. HTTP budget и request timeout, Worker/Run deadline и publication
timeout принадлежат существующим владельцам и не объединяются.

Source Run/validation Run можно удалить после обычной терминальности, release
и удержания принятых материалов в Project. Retest по retained результату
остаётся доступным после удаления Run, если нужная exact конфигурация и
материалы доступны; иначе явный unsupported/missing outcome. Project deletion
останавливает admission, использует обычную отмену/cleanup и ограниченно
освобождает историю и bindings. Никакого самостоятельного удаления FindingCheck
или дополнительного tombstone lifecycle не требуется.

## Компактность изменений и сверка с main

На main `d4b8c5112fef383a47ce3aae9abc1094e346c2e5` ни одна из пяти задач не
выполнена целиком. Существующие составные части считать готовыми основаниями,
а не повторной реализацией:

| Уже есть | Изменение, которое действительно нужно |
| --- | --- |
| Run create/replay, Scheduler, completion interface и deterministic publisher | Доверенное finding-bound admission и узкое обобщение completion/evidence ownership для ordinary Run |
| Project source/history Artifact reader и exact collections | Принять и связать результат с выбранным существующим receipt |
| Несколько HTTP exchanges (V496), code preview (V491), evidence widgets (V495-001) | Передать результаты новых проверок существующим readers/renderers |
| `ui/src/modules/checks` (V495-002), Run navigation, source history UI | Добавить действия, baseline selection и необходимые result labels; lifecycle commands остаются в routes |
| `test-findings-e2e`, completion matrix, mocked browser и real UI stack | Добавить сценарии и required-case assertions в существующие gates |

Для каждого нового endpoint, table, exported abstraction или механизма
указать конкретного caller и почему существующий владелец не может выполнить
операцию после малого расширения. Новая возможность не требует заранее
универсального validator registry, profile inheritance, framework для всех
scanners, отдельного frontend cache или журнала проверок.

V497-002 добавляет к тому же запуску явное основание и retest instructions;
V497-005 добавляет один поддерживаемый source-профиль к тому же пути.
Для V497-005 сначала использовать существующий `source_findings_reviewer`
и его source-analysis tools, без нового tracing engine. Audit-варианты

## Проверки и условия пересмотра

Каждая реализация обновляет свои owning specs, OpenAPI/generated clients,
общие Go/Python fixtures, limits/failures/lifecycle и architecture при изменении
границы. Проверяются реальные PostgreSQL replay/races, все затронутые packages,
оба Audit и ordinary callers общего completion, процессный путь HTTP/evidence,
source Run purge и UI в 390 px/light/dark/black. Tests используют testdata.

История планирования не является доказательством прохождения этих проверок.
Live-model качество потребует отдельного повторяемого Eval с configured model.
Вернуться к решению при необходимости нескольких findings в одном запуске,
нового типа исполнителя, отдельного deployment registry, автоматического
изменения оценки Finding или перестройки общей Audit persistence.
