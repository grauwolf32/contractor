# Перенос инструкций агентов и план eval’ов

Подготовлен кандидат для A/B: **20 улучшенных инструкций, 15 новых версий
AgentTemplate и 10 Workflow**. Они находятся в
[`tests/eval/agent_instructions/candidate/configs`](../../tests/eval/agent_instructions/candidate/configs).
Штатный `configs/` сохранён. Проверено соответствие контрактам; улучшение качества
ответов модели пока не измерено.

Уточнение направления: [предложение интеграции с playground-v2](../agent-evals-proposal.md).
Формат закреплён в [спецификации 26](../spec/26-portable-evaluation-format.md):
V41 завершена и прошла [offline readiness gate](portable-eval-format-readiness.md)
на 2026-09-07. Следующий этап V40 — fixtures, bindings и frozen plan;
модельные eval и выбор инструкций для rollout ещё не выполнены.
Используем уже имеющиеся там datasets/scorers и HTTP-адаптер/runner, отделяя
Contractor bindings от переносимых кейсов. Основная реализация eval-интеграции
находится в playground; здесь остаются кандидаты инструкций и проверки API/
конфигураций. Ground truth не переносится в серверные Project-артефакты.

## Что оказалось слабым

В исходном срезе кандидата от 2026-09-06 было 27 файлов инструкций и 17 шаблонов агентов. Подробность
неодинакова: архивные OpenAPI/LikeC4 workers уже содержат полезную процедуру,
workspace-варианты заметно короче. В trace/audit хорошо определены tools и
результат, но слабее закреплены проверка реального пути, применимость защиты и
завершение исследования без повторов. HTTP/Caido не хватает явного сравнения
гипотезы с исходным запросом.

Короткие copy/passthrough-инструкции соответствуют простоте их задачи. В trace и
LikeC4 существенная часть предметных правил уже находится в Agent Skills,
раскрываемых по запросу. Поэтому длина базовой инструкции сама по себе не
показывает, насколько содержательны полные инструкции агента.

## Что перенесено и адаптировано

Источники — файлы `contractor/agents/<agent>/prompts/` в соседнем
`contractor-old`; выбранные основные версии сверены с `prompt.yml`.

| Источник | Перенос в кандидат |
| --- | --- |
| `trace_agent/converge.md` | Сначала назначенный entrypoint, затем значения/контроли/чувствительная операция; учёт исследованных путей; прекращение повторов без новых данных; сохранение корректных аннотаций. |
| `trace_verifier_agent/v1.md`, `codereview_agent/v3.md` | Проверка реализации middleware/защиты и обходных веток; различение validation, authentication и ownership; отсутствие доказательств не равно опровержению. |
| `http_agent/v1.md` | Последовательность зависимых запросов, baseline/probe, сравнение значимого сигнала, использование истории без дублирования, явные непроверенные гипотезы. |
| `oas_builder_agent/v4.md` | Реестр method/path и пробелов, порядок зависимых компонентов, работа после успешной мутации без немедленного повторного чтения, исправление причины отклонённого вызова. |
| `oas_linter_agent/v1.md` | Ограниченный цикл validate/repair/validate, минимальные подтверждённые исправления, честное сообщение об ошибке CLI. |
| `likec4_builder_agent/v3.md` | Фактические потоки между работающими компонентами, протоколы/данные/границы доверия по доказательствам, фазовое построение и сверка покрытия. |
| `planning_agent/v5.md` | Один проверяемый результат подзадачи, критерии готовности, отсутствие повторного делегирования уже выполненной работы. |

Caido адаптирован к текущему Skill и текущим tools: вывод сканера проверяется по
конкретному exchange; timeout локального ожидания не означает остановку удалённой
задачи. Discovery использует граф при вопросах о символах/вызовах, а не обязательно
строит его для чтения зависимостей из manifests.

В workspace-варианты OpenAPI/LikeC4 перенесены существенные правила архивных
workers: приоритет resume/seed/new, сохранение исходного seed, доказательства,
согласованность тегов, нейтральный сервер `.`, ограниченная валидация и отчёт о
пробелах. Общие planners больше не предписывают распаковку архива worker’у, у
которого исходники уже подготовлены в workspace.

Формулировки организованы вокруг результата, порядка работы, критерия
доказанности и условия завершения. Подробные сигнатуры остаются в tools,
справочники DSL/классов уязвимостей — в Skills. Простые copy, Podman demo и
делегирующие trace/security planners сохранены; project discovery уже задаёт
достаточно конкретный результат. Исправлена опечатка в dependency planner.

Не перенесены старые memory/inbox tools, `SubtaskExecutionResult`, ручная запись
спецификаций, устаревшие аргументы аннотаций и прежние структуры security reports.
Не перенесены требования искать «максимум findings» и считать отсутствие
локального декоратора доказательством отсутствия защиты: это повышает риск ложных
находок. Большие примеры DSL не продублированы из Skill в базовый prompt.

## Размер и совместимость

Суммарный объём эквивалентного набора инструкций: **35 385 → 42 922 символа
(+21,3%)**. Это объём авторских текстов, не токены одного запроса: worker получает
только выбранные инструкции, а общий контекст также содержит task, tools, Skills
и результаты вызовов. Четыре изменённых OpenAPI/LikeC4 planner-текста в сумме
сокращены на 932 символа; workers получили более конкретную методику.

Самые большие тексты кандидата:

| Инструкция | До, символов | После |
| --- | ---: | ---: |
| OpenAPI builder, архив | 2 802 | 3 219 |
| Workspace taint analyst | 1 953 | 3 119 |
| LikeC4 builder, архив | 2 628 | 3 089 |
| Workspace source graph analyst | 1 896 | 2 516 |

По [контракту AgentTemplate](../spec/01-agent-template.md) изменение инструкции
создаёт новую версию. Кроме того, тесты каталога намеренно ограничивают штатный
набор актуальными workflow, а trace `@1` закреплён точными digest. Поэтому
кандидаты подготовлены отдельным eval-overlay: существующие версии, привязки
AuditProfile и работающие Run не изменяются. Это позволяет сравнить тексты до
решения о включении новых версий в основной каталог.

[`variants.json`](../../tests/eval/agent_instructions/variants.json) содержит
все пути, версии и SHA-256; [`baseline.json`](../../tests/eval/agent_instructions/baseline.json)
сохраняет исходные тексты. У кандидатов остаются прежние tools, policy, budgets,
Skills, workspace scope, retries, inputs/outputs. В частности, новые Audit
AgentTemplate `@2` продолжают использовать **`audit-results@1`** — номер версии
шаблона не означает переход на планируемый collector/finalizer из V39.

## Eval-план

Подробная матрица из 18 сценариев, правила scoring, изоляции, бюджетов и принятия
решения находятся в [README эксперимента](../../tests/eval/agent_instructions/README.md).
Запланированы три последовательные задачи:

1. [V40-001](../../tasks/v40-001-agent-instruction-eval-fixtures.yml): фиксированные
   исходники и ожидаемые факты/дефекты, безопасные контрпримеры, semantic scorers.
2. [V40-002](../../tasks/v40-002-agent-instruction-paired-runner.yml): тонкий клиент
   существующего серверного механизма — evaluation Project, обычные Runs,
   `eval.*` метки, идемпотентный запуск и Project-артефакты; восстановление матрицы,
   scoring и сравнение качества, ошибок, повторов, токенов и времени.
3. [V40-003](../../tasks/v40-003-agent-instruction-eval-decision.yml): пилот
   **6 сценариев × 2 варианта × 2 повтора = 24 попытки**, затем подтверждение на
   отложенных примерах и решение по каждому семейству агентов.

Docstrings tools в A/B фиксируются одинаковыми: иначе эффект инструкций будет
неотделим от предыдущего изменения tools. Сначала сравниваются workers на
одинаковых входах, затем полные workflows с discovery/planner. Успех Run,
формальная валидность артефакта, принятие Audit результата и фактическое качество
оцениваются отдельно. Новые ложные находки, пропущенные ожидаемые факты и
неподтверждённые clean/secure выводы требуют разбора, даже если токенов стало меньше.

Live-прогоны в этой доработке не выполнялись. Существующий live harness пока
выбирает workspace workflows `@5` и не реализует эту матрицу. Задачи V40 оставлены
`pending`; новый пользовательский Evals-интерфейс V38 не является предпосылкой
для CLI-сравнения, а новый контракт Audit V39 оценивается отдельно после реализации.

Основой live-eval служит уже реализованный серверный механизм из спецификаций
[16](../spec/16-run-metadata-labels.md) и [17](../spec/17-projects-and-queue.md).
Отдельный executor, очередь, хранилище Runs и сервер на каждый пример не нужны.
Недостающие части — manifest ожидаемых попыток с восстановлением, предметные
scorers и корректное сопоставление A/B. Их результаты сохраняются обычными
Project-артефактами и ссылаются на точные выходы каждого Run. Уже доступные метрики
attempt учитываются вместе с `reportsComplete`/`truncated`; отсутствующие данные
не заменяются нулём. Расширенный comparison UI и серверные агрегаты можно сделать
позже, не блокируя ограниченный пилот. Audit-кейсы проходят через штатный Audit
controller/importer, с фиксацией Audit/item/Run связей в manifest.

## Проверка

`go test ./tests/eval/agent_instructions` загружает обе конфигурации настоящим
config loader, проверяет pinned hashes и сравнивает полные контракты агентов и
workflow с допустимыми различиями только в инструкциях и версиях. Это защищает
чистоту эксперимента, но не заменяет quality eval.

Также выполнены штатные проверки `internal/config`, `tests/eval/project_workflows`
и `tests/eval/audit_programs` с явным исключением live-теста. Тексты-кандидаты
проверены на доступность упомянутых tools и сохранение исходных контекстов/выходов.
