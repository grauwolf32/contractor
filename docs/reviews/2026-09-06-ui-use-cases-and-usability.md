**Contractor UI: use cases, user stories и оценка удобства — 6 сентября 2026**

Интерфейс лучше всего поддерживает пользователя, который уже знает Workflow,
Artifact, Stage, RuntimeConfig и правила версионирования. Он хорошо раскрывает
состояние выполнения и происхождение данных. Первый запуск, подбор входов,
возвращение к незавершённой настройке и повтор анализа требуют заметно больше
усилий. Основная возможность улучшения — сделать частые действия доступными
раньше и яснее объяснять, что пользователь получит и что нужно сделать дальше.

**Основание оценки**

Целевые user stories и план реализации вынесены в
[отдельный документ](../ui-user-stories.md): V37-001…V37-012 и V38-001.
Этот отчёт сохраняет наблюдения на момент исследования. После снятия снимка
V35-004 получил статус completed; новые задачи используют существующий Git UI.

Исследован отдельный снимок текущего `ui/`, включая незакоммиченные изменения
Home, формы Run и сводки Run. В Chromium пройдены 22 маршрута с данными
демо-сервера через ограниченный чтением адаптер запросов. Проверены desktop
1440×1000 и шесть страниц на мобильной ширине 390×844. Для состояний Audit,
которых не было в демо, использованы существующие browser fixtures из
`ui/e2e/audits.spec.ts`: создание черновика, запуск, coverage, программы,
findings, provenance, reviews и report. Ошибка Run проверена отдельной
контролируемой подстановкой ответа API.

Мутации Audit выполнялись только на тестовых ответах API. Данные демо не
менялись. Вход в сессию и надёжность живого WebSocket в этой проверке не
оценивались; сообщения reconnect тестового адаптера не считаются недостатком
продукта. Это экспертная оценка сценариев, а не измерение успешности задач
реальными пользователями. «Удобно / средне / сложно» ниже — качественная
оценка обнаруженных препятствий, без выдуманного общего балла.

**Основные сценарии и user stories**

| ID | Use case | User story | Сейчас | Основное препятствие |
|---|---|---|---|---|
| UC-01 | Создать рабочий проект и подготовить исходники | Как аналитик, хочу собрать исходники, цель и результаты в проекте, чтобы повторять работу с тем же объектом. | Средне | Создание простое, есть загрузка файлов и разделы проекта; основной следующий шаг уступает место метаданным и Delete Project. |
| UC-02 | Выбрать подходящий Workflow | Как пользователь, хочу выбрать анализ по ожидаемому результату, чтобы не разбираться сначала в названиях реализаций и Stage. | Сложно | Каталог показывает техническое имя, версию, entry stage и количество слотов; объяснение назначения и сравнение вариантов слабые. |
| UC-03 | Подготовить и запустить Run | Как аналитик, хочу указать подходящие входы и использовать разумные настройки по умолчанию, чтобы запустить работу без знания инфраструктуры. | Средне | Дополнительные настройки свёрнуты и есть индикатор заполнения; форма далеко внизу, отсутствующий файл требует ухода на другую страницу, черновик теряется. |
| UC-04 | Следить за выполнением и управлять очередью | Как пользователь, хочу видеть текущую работу и причину ожидания, чтобы понимать, нужно ли вмешаться. | Средне | Home и Queue дают быстрый обзор; технические состояния не всегда превращены в объяснение конкретного следующего действия. |
| UC-05 | Получить результат и использовать его дальше | Как аналитик, хочу открыть основной результат и продолжить работу с ним, чтобы не искать нужный файл среди служебных выходов. | Средне | Результаты уже наверху Run; для просмотра остаются несколько последовательных раскрытий, все выходы представлены почти одинаково. |
| UC-06 | Разобраться с ошибкой и повторить запуск | Как пользователь, хочу понять причину сбоя и создать исправленный повтор, чтобы не собирать параметры и входы заново. | Средне для диагностики, сложно для повтора | Сводка показывает первую причину, Stage и retryability; рядом нет понятного пути к исправлению и новому предзаполненному Run. |
| UC-07 | Провести Audit и обработать findings | Как исследователь, хочу пройти проверки, оценить находки и принять отчёт, чтобы видеть доказательства и незакрытые вопросы. | Сложно | Есть coverage, provenance и разделение оценки от технического успеха; информация разнесена по семи вкладкам, а Reviews выглядит журналом, а не очередью действий. |
| UC-08 | Посмотреть агента, промпт и выбранные возможности | Как автор Workflow, хочу прочитать точный базовый промпт, Skills и tools агента, чтобы понимать его поведение. | Удобно | Preview/Source/Copy решают основную задачу; поиск ограничен страницей, версию нужно вводить вручную, нет обратного списка использующих Workflow. |
| UC-09 | Управлять файлами и их версиями | Как аналитик, хочу загрузить, найти и проверить версию файла, чтобы воспроизвести результат и не перезаписать чужое изменение. | Средне | История, точные ссылки, CAS и previews полезны; namespace, revision, MIME и протокольные детали доминируют над назначением файла. |
| UC-10 | Сравнить варианты через Evals | Как автор агента, хочу сравнить варианты на одинаковых случаях, чтобы понять, что изменилось в результатах и расходах. | Сложно; поддержан главным образом учёт запусков | Evals группирует обычные Runs по labels, но не даёт законченного сценария постановки эксперимента и сравнения вариантов. |
| UC-11 | Настроить исполнение и разобраться с инфраструктурой | Как оператор, хочу видеть готовность Runtime и влияние настроек, чтобы устранять причину недоступности и управлять выполнением. | Средне для наблюдения, сложно для настройки | Отдельные разделы есть; версии, bindings, credentials и формы публикации собраны на длинных страницах, механика хранения занимает заметное место. |

**Что уже стоит сохранить**

- Catalog объединяет Workflows, Agents и Skills; Runtime Agents остаются в Operations.
- Базовый промпт можно прочитать и скопировать; интерфейс объясняет, что контекст задачи и Skills добавляются отдельно.
- Новые Home и Run triage сокращают поиск активной работы, причины ошибки, метрик и результатов.
- У Run setup дополнительные Runtime/metadata/model настройки свёрнуты по умолчанию; виден прогресс заполнения.
- Project объединяет входы, результаты, рекомендации и историю; типовые файловые плитки упрощают загрузку.
- Coverage и findings не выдают успешное выполнение процесса за положительный результат проверки.
- Project deletion требует ввода имени, фокусируется на Cancel и сообщает, какие данные будут удалены.
- На шести проверенных мобильных страницах ширина документа не превышала 390 px; меню складывается, таблицы адаптируются.

**Подтверждённые препятствия и предложения**

**UX-01 · P1 · Главный путь запуска находится слишком низко.**

На `likec4-from-workspace-streamline@2` начало формы Run находилось на y≈1922 px
при высоте окна 1000 px; полная страница — около 2967 px. До формы идут слоты,
Stage, Worker, модели, credentials и переходы. На проверенном Project первая
кнопка запуска рекомендуемого Workflow находилась на y≈2210 px, а Delete Project
был виден вверху. На мобильном экране удаление занимает отдельную широкую кнопку,
до запусков приходится проходить длинную страницу.

Предложение: вверху Workflow показать назначение, результат, необходимые входы
и `Configure Run`; форму поместить сразу после краткого описания, подробный
контракт раскрывать отдельно. В Project вынести `Add sources` и `Run analysis`
в основной блок действий, а удаление — в меню дополнительных действий. Не
прятать существующую историю и точные параметры: они нужны при разборе сложных
случаев. Критерий: с первого экрана понятен следующий шаг; начать настройку можно
без прокрутки через контракт.

Основание: [Workflow detail](../../ui/src/routes/workflows/detail.tsx#L294),
[Project detail](../../ui/src/routes/projects/detail.tsx#L106).

**UX-02 · P1 · Переход за входным файлом уничтожает черновик.**

Воспроизведение: включить `objective`, ввести текст, открыть Artifacts, дождаться
библиотеки, вернуться Back. Значение исчезает. Сама форма предлагает ссылку
`Upload one`, когда нет подходящего входа. В Project Run dialog Escape закрывает
форму без проверки изменений; повторное открытие также даёт пустой objective.

Предложение: загружать/выбирать файл в контексте формы, сохранять черновик при
переходах внутри приложения и явно обрабатывать закрытие изменённой формы.
Хранилище черновика должно учитывать Workflow/version и Project; переход в другой
проект не должен переносить чужие входы. Сохранение можно начать с памяти
приложения, без автоматической записи содержимого задач в browser storage.
Критерий: после загрузки отсутствующего файла и возврата введённые параметры,
labels и выбранные входы сохранены; закрытие с потерей изменений явно объяснено.

Основание: [Run draft state](../../ui/src/routes/workflows/run-form.tsx#L458),
[Upload one](../../ui/src/routes/workflows/run-form.tsx#L1041),
[Project dialog](../../ui/src/routes/projects/workflow-recommendations.tsx#L132).

**UX-03 · P1 · «Ready» смешивает заполненность и содержательную пригодность входов.**

На демо для `openapi-from-analysis@2` один `outputs/likec4_validation_report`
автоматически выбран сразу как `dependency_report` и `project_report`.
Основание выбора — единственный файл подходящего `text/markdown`; форма показывает
Ready. Совместимость по MIME реализована согласно текущему контракту, однако
пользователь может принять её за проверку смысла документа. Это не доказательство
неверного результата Run: такой запуск в исследовании не выполнялся.

Предложение: различать «обязательные поля заполнены» и «выбранные документы
проверены пользователем». Показывать назначение слота, понятное имя выбранного
файла, источник и быстрый preview. Для произвольного документа единственного MIME
совпадения недостаточно для уверенной автоматической подстановки. На первом этапе
просить подтверждение такого выбора; затем добавить явную роль/происхождение
артефакта в контракт рекомендаций. Не запрещать любой повтор одного файла в разных
слотах: он может быть намеренным. Критерий: слабое совпадение не выглядит
доказательством готовности анализа, пользователь понимает каждую подстановку.

Основание: [Recommendations](../../ui/src/routes/projects/recommendations.ts#L50),
[Readiness](../../ui/src/routes/workflows/run-form.tsx#L795).

**UX-04 · P1 · Отмена и удаление Audit выполняются одним кликом.**

На browser fixture нажатие Cancel сразу отправляет POST cancel; затем Delete
сразу отправляет DELETE. Ни браузерного подтверждения, ни alertdialog нет.
Это особенно заметно на экране отчёта, где удаление находится среди главных
действий. У Project и completed Run уже есть подтверждения.

Предложение: единый шаблон подтверждения с названием Audit, последствиями,
безопасной кнопкой по умолчанию и понятным состоянием выполняющейся операции.
Для Pause, которая приостанавливает новые запуски, отдельное подтверждение не
обязательно. Критерий: открытие подтверждения не отправляет мутацию, Cancel/Escape
закрывают его без запроса; разрушительная операция начинается только после
явного подтверждения.

Основание: [AuditControls](../../ui/src/routes/projects/audits/detail.tsx#L237).

**UX-05 · P1 · Модальное окно Run не управляет фокусом клавиатуры.**

После открытия Project Workflow dialog активной остаётся кнопка Configure Run
за ним. Следующий Tab переводит фокус на другую фоновую кнопку, хотя окно
помечено `aria-modal=true`. Затем пользователь может работать с элементами,
которых визуально не видит как доступные.

Предложение: общий Dialog для форм и подтверждений: перевод фокуса внутрь,
ограничение Tab/Shift+Tab, недоступность фона для взаимодействия, возврат фокуса
к вызвавшему элементу и согласованное закрытие. Критерий: весь сценарий открытия,
заполнения и закрытия проходит с клавиатуры без ухода на фон. Внешний вид остальных
модальных окон не доказывает отсутствие того же дефекта; их нужно проверить при
внедрении общего компонента.

Основание: [ProjectWorkflowLauncher](../../ui/src/routes/projects/workflow-recommendations.tsx#L146).

**UX-06 · P2 · Каталог помогает найти реализацию, но слабо помогает выбрать результат.**

Workflow list показывает Exact Workflow, Entry Stage и число параметров/входов/
выходов. Поиска нет. В Agents есть описания и поиск, но только по текущей странице;
на detail версия вводится свободным текстом. Пользователь должен помнить имена
и знать, чем отличаются похожие версии и варианты Workflow.

Предложение: человекочитаемое название и короткое назначение; ожидаемый результат
и необходимые материалы на карточке; группировка версий с явным выбором точной
версии при запуске; поиск по каталогу. Для Agents — выбор существующих версий и
«Используется в этих Workflow». Описания должны приходить из опубликованных
определений, а не угадываться по имени или зашиваться в UI как закрытый список
предметных задач. Критерий: назначение и различия вариантов видны до открытия
полного контракта.

Основание: [Workflow list](../../ui/src/routes/workflows/list.tsx#L64),
[Agent search](../../ui/src/routes/catalog/agents.tsx#L45),
[Agent version form](../../ui/src/routes/catalog/agent-detail.tsx#L65).

**UX-07 · P2 · Нужен законченный сценарий «исправить и повторить».**

На тестовом failed Run сводка сразу показала Stage, `planner_gateway_unavailable`,
объяснение и retryable — это полезно. Дальше доступен переход к attempt, но нет
создания повторного Run с прежними входами. Слово retryable само по себе не говорит,
произойдёт ли повтор автоматически или что должен сделать человек.

Предложение: `Run again` / `Configure another Run` с предзаполненными входами,
параметрами и выбранным контекстом проекта. Создавать новый Run и давать проверить
черновик; недоступные старые refs показывать явно. Для известных причин добавить
следующий шаг и ссылку на соответствующую настройку; явно отличать уже назначенный
Scheduler retry от возможности нового запуска. Критерий: после исправления причины
не нужно вручную восстанавливать прежний запрос или менять историю старого Run.

Основание: [Run triage](../../ui/src/routes/runs/detail.tsx#L106),
[Terminal run controls](../../ui/src/routes/runs/detail.tsx#L222).

**UX-08 · P2 · Просмотр результата требует лишних раскрытий.**

Верхняя ссылка Preview outputs ведёт к галерее; раскрытие Preview on demand
загружает metadata, после чего появляется ещё одна кнопка Load preview.
Пользователь уже выразил намерение посмотреть документ, но всё ещё не видит его.
В деталях файла дополнительно читается «Go Server; Node does not proxy the payload»
и If-Match — это редко помогает выбрать действие.

Предложение: одна явная команда просмотра конкретного результата выполняет
проверку metadata и допустимую ограниченную загрузку. Для недоступного preview
сразу давать понятную причину и Download. Выделять основной выход, отчёт и
дополнительные файлы; полную revision/CAS/lineage оставлять в подробностях.
Критерий: поддерживаемый небольшой документ виден после одного явного действия
над ним, без автоматической загрузки всех больших выходов.

Основание: [Run output preview](../../ui/src/routes/runs/artifacts.tsx#L90),
[Artifact preview](../../ui/src/routes/artifacts/preview.tsx#L208),
[Download copy](../../ui/src/routes/artifacts/detail.tsx#L63).

**UX-09 · P2 · Audit нужен рабочий список решений и понятная сводка.**

Coverage полезно отделяет requested/completed/gaps. Findings показывает модельное
предложение, решение аналитика и provenance. Однако Reviews перечисляет pending
subject ID и «No decision recorded»; для самого решения приходится искать
соответствующий finding. В шапке Audit главным названием служит технический ID.

Предложение: над вкладками показать выполнено/всего, пробелы, непроверенные findings
и ожидающие решения; ссылки ведут на отфильтрованный список. В Reviews добавить
переход «Рассмотреть» к конкретному finding/report с сохранением контекста.
В списках нужны фильтры по severity, disposition и состоянию review. В качестве
заголовка сначала использовать профиль, проект и дату; точный ID оставить рядом
с Copy. Критерий: из состояния waiting_review человек за одно действие попадает
к предмету ожидаемого решения. Массовое подтверждение findings без чтения
доказательств не предлагается.

Основание: [Reviews](../../ui/src/routes/projects/audits/detail.tsx#L1270),
[Audit title](../../ui/src/routes/projects/audits/detail.tsx#L1615).

**UX-10 · P2 · Operations стоит организовать вокруг наблюдения и изменения.**

Runtime configuration одновременно показывает версии, bindings, credentials,
создание credential и публикацию RuntimeConfig. На desktop страница заняла около
3646 px, на mobile — 5569 px. Overview уделяет отдельную карточку generation и
revision, а вступление объясняет REST/WebSocket. Оператору чаще нужен ответ,
почему конкретный Run ждёт и что изменится после настройки.

Предложение: сохранить обзор фактической доступности; формы открывать по явному
Create/Edit. Для изменений показывать сохранённое и новое значение, на какие
новые allocations оно повлияет, и ошибки применения. Связать ожидание Run с
нужным Runtime/настройкой, не называть любое свободное место гарантией совместимой
ёмкости. Механизм snapshot и точные refs вынести в диагностику. Критерий:
наблюдение не требует обхода нескольких незаполненных форм; изменения и их
область действия видны до сохранения.

**UX-11 · P3 · Evals пока не покрывает сравнение экспериментов.**

Существующая реализация — evaluation Project и группы Run по `eval.id`, с
колонками leg/case/sample/workflow/state. Это полезная инфраструктура учёта,
но user story «сравнить два варианта» требует ручной сборки labels и просмотра
отдельных Runs.

Предложение: мастер эксперимента с вариантами, случаями и числом повторов;
сопоставление запусков по case/sample; сравнение outputs, времени и токенов.
Оценку качества показывать только при наличии явного evaluator/критерия;
`succeeded` нельзя автоматически называть качественным или правильным ответом.
Критерий: пользователь видит сравнимые пары и пропуски, а не делает вывод по
случайно загруженной странице истории.

Основание: [EvaluationRuns](../../ui/src/routes/projects/runs-region.tsx#L20).

Projects / Runs / Catalog / Artifacts / Evals / Operations дают подходящие места.

**Как проверить эффект**

После первых двух инкрементов дать новому и опытному пользователю одинаковые
задания: выбрать Workflow по цели; запустить с отсутствующим в библиотеке файлом;
уйти и вернуться к черновику; открыть основной результат; повторить после ошибки;
найти pending review и безопасно отменить удаление. Зафиксировать завершение без
подсказок, время, возвраты между страницами, неверный выбор входов и потерю ввода.
Отдельно пройти те же формы с клавиатуры и на 390 px. Числовые цели стоит ставить
после такого исходного замера; текущие координаты и высоты страниц показывают
конкретную компоновку, но не заменяют измерение пользовательских усилий.
