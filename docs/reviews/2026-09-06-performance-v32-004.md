# V32-004: allocation-scoped Runtime resources

The Runtime advertises `supportedPerformanceMetricsVersions: [1]`. Collection
is activated only by AllocationSpecV2's optional
`performanceMetrics: {version: 1, intervalSeconds: 15}`; legacy requests and
omission construct no collector and perform no process reads or timer work.
Server-side request selection and durable history remain V32-005 work.

## Measurement boundaries and meaning

The initial boundary follows validation and acceptance under the allocation slot
lock, before adapter, sandbox, tool and Worker preparation. The final boundary
follows confirmed Worker/tool/adapter teardown (and abort workspace cleanup),
immediately before building the final Runtime resource block. Release cleanup
and subsequent idle time are excluded. Failed preparation uses existing rollback
and discards observations; it does not add a new final-report delivery path.

CPU is the difference between Linux `getrusage(RUSAGE_SELF)` user/system counters.
RSS is the resident page count from a bounded `/proc/self/statm` read, multiplied
by page size. Scheduled observations read only RSS every 15 monotonic seconds.
The observed peak belongs to this allocation interval, not `ru_maxrss`.

These are **whole Runtime process** observations: other service work contributes
to CPU, retained caches contribute to RSS, and children/containers are excluded.
Even complete coverage cannot guarantee the actual RSS peak between readings.

## Bounds, missing data and failure isolation

One asyncio task owns periodic observations. Synchronous kernel reads do not
overlap, and there is no executor, GC, object/stack scan or retained time series.
Only boundary CPU counters, successful RSS count/peak, timestamps, maximum gap
and a safe reason are accumulated. Delayed ticks are skipped, never replayed.
The injected clock, sleeper and reader support deterministic tests.

Complete coverage requires readable boundaries and scheduled observations, with
no observed gap over 30 seconds. A failed RSS observation, skipped tick or reset
marks the resource result partial/unavailable; independently valid CPU deltas
survive RSS failure. Unknown values are omitted, not replaced by zeros. Only
fixed reason codes are returned; underlying exception messages are not exposed.

The final resources are cached with the existing terminal response. Repeat
finalize/abort and authoritative operations following watchdog drain reuse the
same bytes. Confirmed release drops the context; the next allocation gets fresh
baselines. Close cancels the timer synchronously without waiting on extra I/O,
so measurement cleanup introduces no new async finalization deadline. The task
has no asynchronous cleanup and can perform no read after close.

Unconfirmed stop/cancellation retains existing fencing/process-exit behavior and
discards collection, including with an injected non-exiting test callback. Hard
process loss cannot manufacture a recovered endpoint or resource report.
Resource failures do not change Worker/runtime report completeness or slot reuse.
The existing 1 MiB final-report validation remains in place.

## Verification scope

Required resource/contract and allocation/capability/metrics suites cover fake
time, short/long allocations, missing/failed readings, reset, unsupported hosts,
Linux reader semantics, bounded accumulator, disabled collection, preparation
failure/cancellation, teardown, watchdog drain, retries and sequential reuse.
Focused state/control/adapter tests supplement these checks. No live LLM,
production deployment or whole-repository release gate is part of this task.
