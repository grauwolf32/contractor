# Проверка PostgreSQL на демо-стенде — 2026-09-05

Проверены семь пунктов статического ревью. Подтверждены воспроизводимые проблемы
с пулом, блокировками, очисткой blobs и сохранением SQLSTATE, а также рост числа
запросов Run detail и неэффективные планы на большой истории артефактов.
Отсутствие стандартных ограничений SQL/lock wait подтверждено настройками.
Это не означает, что все семь проблем уже проявляются как сбои на обычной
нагрузке демо: условия и ограничения каждого эксперимента указаны ниже.

Изменения реализации не вносились. Подготовлены задачи **V29-001–007**, статус
`pending`, milestone `postgres-reliability-and-query-efficiency`.

### PG-01 — соединение из пула внутри уже открытой транзакции

Цепочка: `postgresPublicUnitOfWork.Do` → `PinRuntimeLabels` →
`PinRunSnapshot` → `validateRunLLMCredential` → `EncryptedProvider` →
`credentials.Repository`, созданный на общем pool, а не на текущем `pgx.Tx`.

Проба использовала production `OpenPool`, `PinRuntimeLabels` и
`EncryptedProvider`. У пула `MaxConns=2`; одно соединение занято `LISTEN`, второе
— транзакцией `REPEATABLE READ`. Выбран RuntimeConfig с LLM credential.
Проверка его metadata пытается получить третье соединение.

Результат: **801 мс до установленного пробой deadline, один cancelled acquire,
`context.DeadlineExceeded`**. При обращении к credential repository через уже
имеющийся `pgx.Tx` тот же lookup завершился за **1 мс**, cancelled acquire — **0**.

Credential в изолированной пробе намеренно отсутствует: ожидание возникает
ещё до SQL-проверки его наличия. У валидной записи та же зависимость от свободного
соединения. Не утверждается, что работающий demo pool настроен на два соединения
или что демо уже зависало. При больших пулах риск возникает при насыщении.

Доработка: передавать транзакцию в metadata lookup, сохранить composite-provider
проверки и deletion fence. Транзакционно обязательные операции должны явно
требовать транзакцию; увеличение размера пула не является исправлением причины.

### PG-02 — эксклюзивная блокировка обязательного `default`

Две отдельные транзакции вызывают настоящий `PinRunSnapshot` без explicit labels.
Первая оставлена открытой после pinning. Вторая ждёт до deadline **700 мс**;
`pg_stat_activity` показывает **`wait_event_type=Lock`, `wait_event=transactionid`**.
Причина — `FOR UPDATE` в `runtimeconfig.Repository.LockBindings`; `default`
всегда входит в набор выбираемых labels.

Контроль: два `SELECT ... FOR SHARE` на той же строке проходят без ожидания
второго читателя (**менее 1 мс**). Изменение binding при этом блокируется и
получает **`55P03`** после заданного только для пробы `lock_timeout=200ms`.

Доработка: совместимая shared-блокировка читателей, сохранение порядка захвата
labels и запрета изменения выбранного binding до commit. Контроль проверяет
семантику блокировок; полноценная замена должна пройти production concurrency
тесты. См. [PostgreSQL: Explicit Locking](https://www.postgresql.org/docs/17/explicit-locking.html).

### PG-03 — общий blob остаётся после двух purge

Использованы настоящие `ArtifactStore.Write` и
`runstore.DeleteReleasedTerminalRun`, без отключения FK или triggers.

1. Созданы два terminal/released Run с разными версиями одинаковых bytes.
2. Открыты транзакции A и B.
3. A полностью выполняет удаление первого Run, но ещё не делает commit.
4. B полностью выполняет удаление второго Run, также без commit.
5. Обе транзакции фиксируются.

Итог: **оба удаления успешны; revisions = 0, versions = 0, orphan blobs = 1**.
`NOT EXISTS` каждой транзакции видит ещё не удалённую для неё версию соседней
транзакции. После commit повторного прохода по этому blob нет.

Доработка: согласовать сборку общих versions/blobs между purgers и параллельными
writers/forks. Сохранить существующее требование синхронной физической очистки
PostgreSQL и доступность всех данных с сохранившимися ссылками.

### PG-04 — индексы и планы запросов

На основной демо-БД через `pg_indexes` подтверждено:

- Нет индекса `artifact_binding_revisions(version_id)`.
- Нет индекса `artifact_versions(blob_sha256)`.
- Нет индекса по времени внутри истории одного logical binding.
- `artifact_bindings_list_idx` полностью повторяет колонки и порядок PK.
- `artifact_lineage` имеет только target-side PK; польза отдельного source-side
  индекса в этом проходе не измерялась и отдельной задачей не объявлена.

FK автоматически не создаёт индекс на ссылающейся стороне:
[PostgreSQL: Constraints](https://www.postgresql.org/docs/17/ddl-constraints.html).

Для проверки планов в тестовой БД созданы **50 000 blobs, versions и revisions**,
все revisions — история одного binding. Выполнен `ANALYZE`, затем
`EXPLAIN (ANALYZE, BUFFERS, FORMAT JSON)`. Digest передавался параметром,
чтобы вычисление правой части выражения не искажало результат.

| Запрос | Исходный план / мс | После изменения / мс | Буферы исходно → после |
| --- | --- | --- | --- |
| Поиск digest через `encode(sha256,'hex')` → прямое сравнение `bytea` | Seq Scan / 9.262 | Index Only Scan по существующему PK / 0.051 | 657 → 4 |
| Обратная ссылка revision → version | Seq Scan / 3.795 | Index Only Scan / 0.034 | 618 → 4 |
| Обратная ссылка version → blob | Seq Scan / 2.307 | Index Scan / 0.028 | 618 → 4 |
| Страница истории, 51 строка, с исходными joins | Полные проходы + Sort / 74.739 | Index Scan по истории + Nested Loops / 0.349 | 1894 → 414 |

Экспериментальные индексы:

```sql
CREATE INDEX ON artifact_binding_revisions (version_id);
CREATE INDEX ON artifact_versions (blob_sha256);
CREATE INDEX ON artifact_binding_revisions
    (scope_kind, scope_id, namespace, name, created_at DESC, revision DESC);
```

После добавления индексов выражение с `encode` всё равно давало Seq Scan;
необходима именно замена predicate на бинарное сравнение.

Это единичные измерения синтетической выборки, не нагрузочный тест и не обещание
ускорения демо в указанное число раз. Обратные проверки измерялись как SELECT
с теми же условиями поиска, а не как полный purge 50 000 артефактов. Значимый
результат — изменение access path и объёма работы. Миграция должна быть новой,
совместимой с существующим транзакционным migrator.

### PG-05 — N+1 в Run detail

На основной демо-БД измерен настоящий `handler.getRun` из экспортированного
исходного кода. Использованы реальные repositories и `pgx.QueryTracer`.
Авторизация владельца установлена в контексте тестового HTTP-запроса; сетевой
login и работающий HTTP listener в этой пробе не участвовали. SQL и его параметры
не логировались; сохранялись только количество запросов и категории таблиц.

| Stage attempts | SQL-запросов | Metrics / sessions / allocations | Ответ | Время, мс |
| --- | --- | --- | --- | --- |
| 4 | 25 | 4 / 4 / 4 | 200 | 19 |
| 4 | 25 | 4 / 4 / 4 | 200 | 8 |
| 4 | 23 | 4 / 4 / 4 | 200 | 7 |
| 5 | 28 | 5 / 5 / 5 | 200 | 10 |

Различие базового числа запросов связано с составом данных Run. Подтверждены
три дополнительных запроса на каждую Stage попытку; текущая задержка демо мала.
Доработка: batch-read связанных коллекций, без изменения публичной модели.

### PG-06 — потеря SQLSTATE

В `REPEATABLE READ` зафиксирован snapshot чтением binding. Другая транзакция
выполнила валидный semantic rebind и commit. Затем первая транзакция попыталась
заблокировать изменённую строку.

- Непосредственный SQL вернул **`40001`**.
- Та же ситуация через `Repository.LockBindings` вернула
  **`read RuntimeConfig binding`**, SQLSTATE через общий helper — **пустой**.

Потеря причины подтверждена на PostgreSQL. Отсутствие полного retry
при независимом конфликте snapshot проверено чтением кода:
HTTP create Run после распознаваемого `40001` ищет победителя с тем же
idempotency key, но не повторяет транзакцию при независимом изменении binding.
Полная гонка двух сетевых POST в этой проверке не запускалась.

Доработка: сохранить безопасно классифицируемую внутреннюю причину и добавить
ограниченный retry всей транзакции для явно допустимых операций. Не повторять
вслепую внешние эффекты или ambiguous commit. V28-004 отвечает за представление
диагностики в логах; V29-006 — за сохранение причины и transaction recovery.
См. [PostgreSQL: Transaction Isolation](https://www.postgresql.org/docs/17/transaction-iso.html).

### PG-07 — бюджеты SQL и ожидания

На демо и на соединениях, созданных настоящим `OpenPool`, получены:

```text
statement_timeout                    0
lock_timeout                         0
idle_in_transaction_session_timeout  0
```

`max_connections=100` относится к PostgreSQL, а не к лимиту `pgxpool`.
`ConnectTimeout` ограничивает установление соединения, но не ожидание pool slot
и не выполнение SQL. Проба `pg_sleep(0.3)` завершилась за **301 мс**;
блокирующие пробы PG-01/02 остановил только deadline, добавленный проверкой.
В production HTTP server установлен `ReadHeaderTimeout`, но не общий бюджет
операции БД. Наблюдавшегося длительного простоя пользователей не заявляется.

Доработка: конечные бюджеты обычных операций, отдельные правила для migrations,
cleanup и LISTEN; освобождение ресурсов при timeout и минимальные метрики
насыщения/ожидания пула. V29-007 также завершает общую проверку V29.

## Воспроизводимость и завершение

Временные пробы находятся в игнорируемом рабочем каталоге
`.local/sql-review/source`: `cmd/sql-review`, `cmd/sql-review-controls`,
`cmd/sql-review-plans` и `internal/httpapi/public/sql_review_test.go`.
Они не входят в изменение приложения. Полные JSON-планы сохранены в
`.local/sql-review/{before,after}-*.json`; секретов и SQL-параметров пользователей
в отчёте нет.

Для повторения нужны отдельная пустая БД на демо-экземпляре, миграции исходного
baseline, описанные выше interleavings и синтетическая выборка. Нельзя направлять
write-пробы на основную БД. Локальные планы являются вспомогательными файлами;
результаты и достаточные условия сценариев зафиксированы в этом документе.

Проверка завершена: временная БД удалена после закрытия всех её соединений;
приватный временный файл подключения удалён. На основной демо-БД остались
4 Runs, 17 StageExecutions, 78 blobs, 85 versions и 110 revisions; исходные
SQL/lock timeout не изменены, экспериментальных индексов нет. Проверка этих
счётчиков не является побайтовым сравнением данных; write-пробы выполнялись
исключительно в удалённой тестовой БД.
