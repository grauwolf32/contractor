# V29 PostgreSQL verification

Environment: disposable PostgreSQL 17 (`postgres:17-alpine`), isolated schemas,
race-enabled Go integration tests. Demo data was not used or modified.

## Artifact query plans (V29-004)

`TestPostgresArtifactSelectiveQueryPlans` generates 50,000 distinct blobs,
versions and revisions of one binding. It captures the actual repository
`ListVersions` query, including metadata joins. For the baseline it drops only
the three new indexes inside a transaction, then rolls that DDL back before
measuring the migrated schema. Sequential scans are not disabled.

Representative `EXPLAIN (ANALYZE, BUFFERS)` execution samples:

| Query | Before | After | Execution buffers before → after |
| --- | --- | --- | --- |
| Revision reference (`version_id`) | Seq Scan, 3.018 ms | `artifact_binding_revisions_version_idx`, 0.027 ms | 516 → 3 |
| Blob reference (`blob_sha256`) | Seq Scan, 2.617 ms | `artifact_versions_blob_idx`, 0.023 ms | 569 → 4 |
| Digest equality | encoded column Seq Scan, 5.732 ms | binary `artifact_blobs_pkey`, 0.030 ms | 516 → 4 |
| History page, limit 51 | full joins + top-N sort, 71.475 ms | ordered history index + selective nested loops, 0.277 ms | 1602 → 363 |

The history index reads 51 revision rows (5 buffers), not all 50,000.
A sequential scan of the **single-row binding table** remains appropriate;
the regression check rejects scans of retained revisions, versions and blobs,
and rejects a history sort. Timing is evidence, not an asserted SLA.
The test also verifies exact first/next page boundaries and removal of the
redundant binding index. Original migration 000002 defines that index with
exactly the primary key's columns and order. New migration 000046 uses ordinary
transactional DDL; no applied migration is rewritten.

The migration integration test's expected table inventory was also brought
up to date with already-existing `audit_proposal_items` and
`audit_report_candidates`; it continues checking the full schema and replay.

## Recovery and collection (V29-002, V29-003, V29-006)

- Shared binding pins coexist; mutations take exclusive locks from the start.
  Tests cover opposite input ordering, blocked update/delete and cancellation.
- Purge locks resource scope, sorted candidate versions, then sorted binary
  blob hashes. Post-lock reference checks use new READ COMMITTED statements.
  Repeatable-read purge is rejected rather than silently using stale checks.
  FK locks protect retaining revisions, blob upserts coordinate identical
  writes, and source-scope locks coordinate input forks/output publications.
- Purge has a five-second context bound. Pool-owned Run deletion and final
  Project and claimed Audit purge replay only complete database transactions on definite aborts.
  Transaction-backed callers remain responsible for their entire transaction.
- SQLSTATE and context causes survive safe error wrappers. Opt-in transaction
  recovery allows at most three attempts for `40001`/`40P01`, with cancellable
  backoff and fresh result state. Business CAS failures and ambiguous transport
  or commit failures are not replayed.
- Real PostgreSQL tests exercise overlapping terminal Run deletion with a
  shared blob, rollback, an uncommitted identical write, retaining publication,
  deadlock recovery, and a binding rebind during repeatable-read Run creation.

Required package suites were run with `CONTRACTOR_TEST_DATABASE_URL` set; these
were database-backed passes, not environment-skipped integration tests.

## Run detail batching (V29-005)

`TestPostgresRunDetailFixedBatchQueries` traces the actual GET Run method using
production PostgreSQL RunStore, ArtifactStore, telemetry repository and Planner
session service. It compares the response byte-for-byte against the same
production dependencies behind their single-item interfaces.

| Stage attempts | Single-item composition | Batch composition |
| --- | --- | --- |
| 1 | 13 queries | 13 queries |
| 5 | 27 queries | 13 queries |
| 30 | 115 queries | 13 queries |

Each related collection uses exactly one `ANY(text[])` query: allocations,
metrics, sessions. Empty collections need no query. The fixture mixes terminal
and active attempts, missing plans/metrics/allocations, one malformed optional
metrics summary and an exact frozen output. Healthy optional diagnostics remain
visible when a sibling record cannot decode. There is no fallback query fan-out
after a production batch error. Non-PostgreSQL implementations can still use
the compatibility interfaces.

Owner denial stops after the two Run/metadata-label queries, before any related
collection load. Complete Planner session/execution/invocation identity and
schema checks remain mandatory; missing sessions still return an error rather
than being confused with a valid session that has no plan. Physical allocation
identities are not exposed. Input/output binding reads are unchanged, so the
fixed count here is relative to Stage attempts, not arbitrary artifact counts.
