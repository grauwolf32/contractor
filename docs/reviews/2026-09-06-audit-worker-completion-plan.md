# Ревью плана гарантий завершения Audit Worker — 2026-09-06

Проверены рабочая версия [спеки 25](../spec/25-audit-worker-finalization.md),
связанные изменения спек 00/01/02/04/14/15/19 и задачи V39-001–007.
Контракты сопоставлены с текущим кодом Runtime, конфигураций, RunStore,
Artifact API и Go Audit importer. Это ревью проекта решения; новая стратегия
ещё не реализована.

Архитектура подходит для первой версии: явное включение из доверенного
AuditProfile, один passthrough Worker на пакет заданий, отдельный коллектор,
ограниченные напоминания и программная публикация результата. Особенно полезны
разделение принятого вызова и предложенного вызова, независимость от финального
текста модели, запрет обхода через summarizer и сохранение независимой проверки
импортёром. Универсальная система обязательных инструментов здесь не нужна.

В спеку и задачи внесены следующие уточнения.

## 1. Продолжение ADK требует отдельного управления жизненным циклом

[before_run_callback](../../runtime/src/contractor_runtime/instrumentation.py)
потребляет одноразовый prepared token и инициализирует invocation/reducer.
ADK Runner вызывает этот callback при запуске; второй run_async сам по себе
не обеспечивает продолжение того же логического invocation. Повторная
инициализация также рискует сбросить учёт вызовов и наблюдения артефактов.

В V39-001 добавлена ранняя проверка на настоящем закреплённом ADK Runner,
production instrumentation и scripted model до фиксации интерфейсов. V39-005
затем интегрирует этот механизм: один begin, непрерывные counters/tool ordinals,
один terminal State и cleanup. Отдельный сценарий проверяет нормальное
завершение на последнем разрешённом вызове: программный finalizer не требует
дополнительной ёмкости бюджета.

## 2. Create-only публикация ограничивает повторные попытки одного Run

[ArtifactRef](../spec/03-artifact-plane.md) привязан к RunScope, а не к попытке
Stage. [write_artifact](../../runtime/src/contractor_runtime/artifacts.py) с
expected_revision=None использует If-None-Match: *. Если первая попытка
записала ZIP и затем потеряла completion, следующая попытка того же Run может
сформировать другие bytes и получить постоянный конфликт. Proposal invocation
IDs тоже могут менять содержимое.

В V39-004/005/006/007 явно разделены повтор одной публикации, новая invocation
того же Run и новый child Run Audit. Старый артефакт не заполняет новый
коллектор; одинаковые bytes можно признать только после новой полной валидной
коллекции, другие — конфликт. Примеры завершают child Run при failed/interrupted
и оставляют решение о новой попытке существующей политике Audit. Прозрачное
восстановление после записи через Stage retry не обещается.

Уточнены пределы публикации: максимум два PUT и два ограниченных read-back в
рамках deadline; auth/write-fence errors не превращаются в транспортные
повторы или ошибки LLM.

## 3. Локальная валидация должна использовать весь доступный task-контракт

[semanticCoverage / standardEvidenceContractAccepts](../../internal/auditimport/importer.go)
проверяют не только наличие checklist evidence: pinned standard ограничивает
assessment, kinds и количество evidence; операция с not-tested не может
содержать completed coverage. Эти правила уже доступны из task и должны
давать модели обратную связь до завершения invocation.

V39-003/007 теперь требуют общие Go/Python fixtures для этих случаев.
Сохраняется различие между невалидным результатом и допустимым результатом
с gaps/inconclusive coverage. Дополнительно определены смешанные scalar/batch
вызовы: create/replay атомарно, изменённый существующий элемент — конфликт,
коррекция — через scalar expected_revision. Оба инструмента читают exact
snapshot; изменение текущих input aliases не меняет задание.

## 4. Лимиты коллектора зависят от фактического кодирования ZIP

Исходный план разрешал независимую реализацию V39-003 и V39-004, хотя первый
должен проверять размер ещё не опубликованного пакета. Независимые оценки
создают риск принять полный набор, который реальный encoder отвергнет.

V39-004 выделяет чистый encoder/size validator без транспортных операций.
V39-003 зависит от V39-004 и использует его при приёме данных. Один расчёт
учитывает canonical JSON, ограничения members, ZIP overhead и замену элемента.
Проверка граничных значений добавлена в acceptance criteria.

## 5. Доверенное включение должно сохраняться при escalation и restart

Ограничения выбранного Worker теперь явно распространяются на все достижимые
варианты escalation, включая замену AgentTemplate и result mapping. Иначе
валидность исходного binding не доказывает валидность эффективной конфигурации.
V39-001 также явно владеет Server descriptor для @2: регистрация authoring
контракта отделена от объявления доступной Runtime capability.

V39-002 включает хранение authority вместе с Audit child Run, миграцию,
атомарность rollback и проверку восстановления после рестарта/смены каталога.
Обычные Runs и старые snapshots остаются без нового поля и без активации.

## 6. Release gate не должен проходить с пропущенными проверками БД

Существующие PostgreSQL-тесты auditservice/runstore/scheduler вызывают Skip
без CONTRACTOR_TEST_DATABASE_URL. Поэтому go test ./... и make verify сами
по себе не доказывают сохранение authority и recovery.

V39-007 требует отдельный make test-audit-completion-e2e, который проверяет
наличие изолированной БД и фактическое выполнение обязательных тестов без
skip. Реальные bytes нового Runtime ZIP должны попасть в Go importer;
пара независимых mock-тестов этого не заменяет. Общие regression checks
остаются дополнительными требованиями.

## Границы гарантии и проверки этого ревью

Гарантия: Worker не завершится успешно без принятого результата для каждого
задания и подтверждённой публикации. Это не exactly-once вызов инструмента,
не обещание успешного поведения модели и не доказательство истинности её
evidence/выводов. Принятый blocked/inconclusive может быть корректным итогом;
качество анализа оценивается отдельно. Частичные данные теряются при падении,
а importer сохраняет последнее слово по приёму пакета.

Проверены YAML семи задач и индекса, зависимости (189 задач в замыкании без
циклов), порядок шести этапов, соответствие acceptance criteria тестовым
спискам, локальные ссылки и формат документации; git diff --check прошёл.
Продуктовые интеграционные тесты новой стратегии пока выполнить нельзя:
её реализации ещё нет. Изменения ревью ограничены спекой, задачами и этим
документом; существующий код не исправлялся в рамках этого ревью.
