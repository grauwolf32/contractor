# V32-002 — bounded Server performance collection

## Implemented

- The process-level performance switch conditionally installs instrumentation
  around both public and private HTTP handlers and owns one background sampler.
  The disabled branch does not construct the collector or invoke its factory.
- Initial sampling runs asynchronously with the Server's background lifecycle.
  Subsequent samples use a single cancellable timer aligned to 15-second UTC
  boundaries. Late wakeups produce one actual observation and explicit skipped
  intervals, never a replay loop. Durations and CPU rates use monotonic elapsed
  time; wire timestamps are UTC.
- HTTP counters have exactly two surfaces, ten methods and six status classes.
  Interval drains preserve in-flight counts. Health, readiness, performance
  reads and profiling paths are excluded. No path/identity/header/error labels
  or request history are retained.
- Existing `httpsnoop` support preserves Flusher, Hijacker, ReaderFrom and the
  other supported ResponseWriter interfaces. A bounded observer of hijacked
  WebSocket response headers finishes accounting at the handshake, including
  failure, rather than at the socket's eventual close.
- Linux process CPU comes from `getrusage(RUSAGE_SELF)` and current RSS from a
  bounded `/proc/self/statm` read. Selected `runtime/metrics` values supply live
  heap, goroutines, completed GC cycles and a detached, bounded pause histogram.
  No forced GC, process-lifetime RSS peak, profile, or child/host sampling occurs.
- The working pool is read through `pgxpool.Stat()`, including cumulative
  acquisition count/duration, empty-pool wait count/duration and cancellations.
  Collection never acquires a database connection or executes SQL.
- Each process/pool group is independently validated. A malformed or unavailable
  group cannot discard the other group's measurements or valid HTTP counters.
- The ring holds at most 240 completed frames, at most 32 KiB each and 8 MiB
  total, plus the active fixed HTTP accumulator. Expired frames are excluded
  from history reads even when sampling is stopped. Read results are detached
  copies and never trigger collection or DB access.
- Production `/readyz` now uses the working pool's Ping with a one-second
  context deadline, shortened by an earlier request deadline. `/healthz` remains
  independent. Database details are not returned. This applies whether metrics
  are enabled or disabled; the health-only bootstrap harness remains unchanged.

## Minute aggregation boundary

The pure bounded minute primitive merges counts/histograms, uses CPU counter
deltas and actual measured duration, and keeps gauge last/min/max plus observed
sample counts. It rejects mixed generations and duplicate observations. Cached
gauge timestamps are not counted twice. Unknown CPU/HTTP remains absent.

Observation windows crossing a minute boundary cannot truthfully be split into
event counts or CPU deltas. They remain in fine history; the minute primitive
omits that ambiguous contribution, increments `omittedWindows` and reports
partial coverage. It does not silently prorate counters. V32-003 owns durable
writer scheduling and any more precise boundary capture it needs. No minute
writer, diagnostic DB pool or persistent history is started by this task.

The new public GC histogram and empty-acquisition wait fields have matching
OpenAPI/TypeScript contracts. Performance routes still remain planned until
V32-005; charts, allocation resource collection and pprof are separate tasks.

## Verification

Required race tests cover performance, app, public handlers and WebSocket events.
Focused fixtures exercise fake-clock delays/cancellation, concurrent requests
and drains, streaming, live WebSocket handshakes, failed writes, original
ResponseWriter interfaces, Linux readings, no-query pool reads, bounded history,
CPU resets, partial/unknown samples and minute aggregation. Readiness is tested
both with a cooperative fake and a real pgx pool facing a stalled TCP peer.

The benchmark target measures collection, minute aggregation and a minimal
instrumented HTTP handler, with five repetitions. These are synthetic costs,
not a claim about end-to-end production overhead; V32-008 owns that release gate.
