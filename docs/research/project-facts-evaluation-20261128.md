## Исполнение, стоимость и traces

Все **36 Audit завершились успешно** в терминах lifecycle; **35 из 36 вложенных
Worker Runs succeeded**. Один Run завершился `allocation_preparation_failed`
до готового execution report. Корневая причина этого раннего сбоя не доказана.
Успешное завершение Audit не означает успешного извлечения или подтверждения
качества. Native quality reviews отсутствуют у всех участников.

Для 35 участников полностью наблюдаемы **1 473 498 токенов**, **187 обращений
к модели**, **281 tool call**, **43 tool failures** и **USD 0.0975608545 reported**.
У раннего сбоя полные usage/price недоступны; это известная часть расхода,
а не полный итог с якобы бесплатным неуспешным Run. Audit cost учитывается
один раз; стоимость дочерних Runs не прибавляется к нему повторно.

Медиана на участника с полными token counters — 37 537 токенов, p90 — 58 877.
Медиана native wall time всех 36 участников — 59,6 с, p90 — 129,4 с,
максимум — 297,1 с. Латентность измерена на общем Gateway одновременно с
независимой compaction-серией, поэтому это наблюдаемая длительность стенда,
а не изолированный performance benchmark. Cached-input counters недоступны.

Два потерявших факт Worker вместе потратили **25 model calls и 229 929 токенов**.
Native диагностика и исходные tool responses подтверждают восемь отказов
источника и один отказ квоты в каждом. Это не предположение по финальному
тексту модели. Штатный `scripts/audit_trace_report.py` дополнительно проверен
через Phoenix на одном из этих Audit: 14 наблюдаемых Worker tool spans,
9 ошибок. Trace counts не подменяют полные native usage counters.

`debug` выбран у всех 36 участников. У всех 35 успешных Worker есть полный
Runtime report, успешный OTLP flush, ноль failed operations и ноль dropped spans;

model workspaces. Штатный Phoenix восстановлен с сохранением существующей
истории, сохранённые spans догружены без повторных model calls.

## Предложения по улучшению

Это предложения по следующему изменению и эксперименту, а не новые требования
или уже доказанный выигрыш.

| Приоритет | Изменение | Что проверить следующим сравнением |
| --- | --- | --- |
| 1 | Уточнить выбор источника `fact`: ошибка должна явно предлагать `memory_name` или точный `sources`; добавить короткий корректный пример | Recall, восстановление после первого отказа, calls/tokens до сохранённого факта |
| 1 | Сделать два режима `read_artifact` — выбор материала и продолжение по cursor — явными в tool schema или готовом continuation-вызове | Число ошибок пагинации и полная стоимость при том же качестве |
| 2 | Сократить повторение одного и того же некорректного вызова, сохранив квоты и строгую проверку evidence | Число одинаковых отказов и доля восстановившихся публикаций |
| 2 | Отделить знание о целевой системе от метазаписей о scratch/history; точнее различать «не проверялось» и negative probe | Spam и неподдержанные квалификации на новых кейсах |
| 2 | Показывать принятые/отклонённые публикации и проблемы дочерних Runs рядом с итогом Eval/Audit | Видимость потери знания при техническом завершении |

Простой следующий кандидат — новые immutable instructions/template с примерами
и более точными ошибками без изменения модели и persistence. Более крупная
альтернатива — ограничить модель выбором memory IDs и краткой оценкой, оставив
сборку и привязку исходных материалов детерминированному Runtime. Это отдельный
дизайн с большим объёмом изменений; текущая серия не сравнивает эти варианты.
Для проверки нужен новый frozen A/B и новые held-out кейсы.
