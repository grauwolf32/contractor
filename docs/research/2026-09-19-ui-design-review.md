# Дизайн-аудит Contractor — 19 сентября 2026

**Вывод.** У интерфейса есть цельный визуальный стиль и полезные рабочие компоненты: навигация по проекту, контракт Workflow, дерево файлов, просмотр документов, формы с сохранением черновика. Основная проблема — порядок и вес информации. Идентификаторы, сведения о хранении и исполнении, повторные заголовки и большие панели отодвигают результат, решение аналитика и следующее действие. На наполненном стенде это особенно заметно: несколько списков достигают 15–16 тысяч пикселей высоты. Обнаружены и воспроизводимые дефекты отображения и просмотра данных.

Рекомендую сохранить визуальную основу, переработать компоновку ключевых сценариев и унифицировать компоненты. Полная смена темы или глобальной навигации сейчас имеет меньшую пользу.

**Материалы и охват**

Это экземпляры семантических элементов, включая повторные строки и контейнеры; число не означает 16 620 уникальных компонентов. JSON каждого экрана доступен в галерее.
- Ниже дана оценка назначения и расположения функциональных блоков. Повторяющиеся карточки, строки таблиц и одинаковые формы объединены; индивидуальные экземпляры остаются в CSV/JSON.

Данные страниц получены из действующего API. Для браузерного обхода подставлен ответ о сессии, а запросы чтения отправлялись с существующим доступом к стенду. Поэтому проверены реальные данные и отрисовка UI, но не вход по паролю, обновление сессии и авторизованные WebSocket-соединения. Сообщение `Operations Events: Reconnecting` в этой среде не считается дефектом продукта. Отправка форм, запуск работ, изменение настроек и удаление объектов не выполнялись. В итоговом обходе нет ошибок выполнения сценариев и необработанных ошибок JavaScript; отдельные ошибки, обработанные самим UI, перечислены ниже.

На стенде были четыре обычных проекта, 16 Eval workspaces и 147 завершённых Runs. Активных Runs и allocations, ожидающих решений Review и опубликованных ExecutionConfigs не было. Для этих разделов проверены доступные пустые состояния. У LLM Credentials проверены пустой список и форма создания; успешная страница существующего credential недоступна из-за отсутствия записей. Недоступные заполненные состояния изучены по маршрутам и компонентам, но их визуальная корректность не подтверждена. Кнопка начала Review создаёт запись сразу, поэтому дальнейшая форма оценена по исходному коду. Обзор не является пользовательским исследованием или полной проверкой WCAG.

**Подробные наблюдения и предлагаемые изменения**

**D01. Восстановить просмотр успешного Run.** [Снимок](../../.local/ui-design-audit-20260919/screenshots/run-4-succeeded-1440.png). У `run_17fca0457f4ade4cbec9aed20bb4a7f6` API возвращает HTTP 200, но страница показывает только `Runtime configuration response shape is invalid`. В ответе есть `attempts[0].runtimeConfiguration.allocations[*].origins.caido`; клиентский перечень допустимых полей в [runtime-configuration.ts](../../ui/src/api/runtime-configuration.ts) его не содержит. Проверка тем же валидатором развернутой версии воспроизводит ошибку; на копии объекта без `caido` проходит — [результат проверки](../../.local/ui-design-audit-20260919/probes.json). Согласовать контракт клиента и сервера. Ошибка необязательной диагностической секции должна оставлять доступными независимо проверенные основные сведения и результаты Run. Проверка готовности: этот Run открывается, результаты доступны, происхождение Caido отображается корректно.

**D02. Убрать горизонтальное переполнение New Audit.** [Мобильный снимок](../../.local/ui-design-audit-20260919/screenshots/project-new-audit-390.png). При viewport 390 px ширина документа становится **916 px**; блоки выбранного профиля и длинные значения выходят за правый край. Проверить минимальную ширину элементов сетки, переносы длинных значений и ширину select; содержимое формы должно укладываться в доступную колонку. Проверка готовности: форма и основной action доступны при 390 и 320 CSS px без горизонтального перемещения всей страницы. Второй размер — предлагаемый регрессионный критерий; текущий обзор сделан на 390 px. См. [W3C: Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html).

**D03. Исправить hover в дереве ZIP.** [Снимок наведения](../../.local/ui-design-audit-20260919/screenshots/archive-hover-probe.png). У выбранного `App.java` цвет текста `rgb(233, 237, 243)`, фон при наведении `rgb(227, 255, 154)`: контраст **1,07:1**. Без наведения он **11,20:1**. Локальный стиль выбранного файла конфликтует с общим hover кнопок; нужны согласованные состояния default, selected, hover, focus. Проверка готовности: текст обычного размера во всех этих состояниях имеет контраст не ниже 4,5:1, фокус различим. [W3C: Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).

**D04. Отдельно обрабатывать метаданные SKILL.md.** [Снимок](../../.local/ui-design-audit-20260919/screenshots/skill-browse-1440.png). Служебный YAML между `---` попадает в Markdown и интерпретируется как большой заголовок. В результате `name: auth description: ... compatibility: ...` занимает центральную часть просмотра. Выделять ограниченный по размеру frontmatter в компактные поля «Название / Назначение / Совместимость», а основное содержимое рендерить отдельно. Source должен сохранять оригинальный файл. Проверка готовности: открытый `skills/auth` начинается с понятного описания и документа; служебный YAML не превращается в заголовок. Существующие ограничения безопасного просмотра сохраняются.

Проверка готовности: единые интервалы, расположение подписей, ширины, focus/error/disabled состояния во всех перечисленных формах, включая мобильные.

Проверка готовности: по первому экрану понятно, что проверено, что осталось и какое действие доступно.

**Карта views: элементы, назначение и расположение**

В этой карте перечислены функциональные элементы страницы, а не только её название. Оценка «удачно» относится к назначению и текущему расположению блока; замечания ссылаются на список выше. У повторяющихся компонентов, например статусов, таблиц и форм загрузки, общие требования действуют во всех указанных контекстах.

| View / состояния | Элементы и назначение | Оценка расположения и улучшение |
| --- | --- | --- |
| Общая оболочка | Логотип/название; семь ссылок разделов; active state; owner; Settings; Sign out; версия; Skip to content; мобильный Menu | Основная навигация удачна. Согласовать вложенный контекст, Settings и версию; D18, D21, D26, D32. |

**Предлагаемый порядок изменения дизайна**

1. **Восстановить просмотр и исправить явные дефекты:** D01–D05. Проверить успешный Eval Run, New Audit на mobile, hover файла и SKILL.md; распространить общие поля на диалоги.
2. **Привести основные сценарии к результату:** D06–D13. Компактная история, первый экран Run с результатом, просмотрщик с большой областью содержимого, ясный итог Audit и очередь решений, корректная готовность Home.
3. **Согласовать повторяющиеся шаблоны:** единые шапка страницы, toolbar, status summary, compact list, detail/disclosure, field/action row и dialog/drawer. Затем применить D14–D30 к каталогам, Evals и Operations.
4. **Проверить на реальных задачах:** открыть результат завершённого Run; прочитать Skill и файл в ZIP; найти непроверенную Finding и evidence; понять незавершённое покрытие Audit; выбрать Workflow и точные входы; определить действующую default-конфигурацию. Для каждого сценария измерить время поиска и ошибки выбора, а не только число кликов.

Критерий общего улучшения: первый экран отвечает на вопросы «где я», «что произошло / что доступно» и «какое действие нужно сейчас». Техническая точность остаётся доступной в деталях, без необходимости читать её перед каждым действием.
