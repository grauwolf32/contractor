# Contractor design audit — September 19, 2026

**Assessment.** The interface has a coherent visual style and useful working components: Project navigation, Workflow contracts, file trees, document previews and forms with draft preservation. The main problem is information order and emphasis. Identifiers, storage and execution details, repeated headings and large panels push results, analyst decisions and next actions down the page. This is especially visible in the populated environment: several lists reach 15–16 thousand pixels in height. Reproducible display and data-viewing defects were also found.

I recommend preserving the visual foundation, reworking key journey layouts and unifying components. A complete theme or global-navigation replacement would provide less benefit now.

**Materials and coverage**

- Environment: `http://127.0.0.1:4173`, UI **0.2.0**, release `main-dc4d6f3a-20260919T180628Z`.
- Checked **92 states**: main sections, nested pages, populated and empty lists, previews, expanded panels and forms. Each has screenshots at **1440 × 960** and **390 × 960**: **184 first-viewport screenshots** in total, plus full-page captures.
- [Gallery with filters and links to all screenshots](../../.local/ui-design-audit-20260919/index.html), [machine-readable summary](../../.local/ui-design-audit-20260919/summary.json), [complete state and route inventory](../../.local/ui-design-audit-20260919/routes.json).
- [Element inventory — CSV](../../.local/ui-design-audit-20260919/elements.csv): **16,620 records** with labels, types, coordinates, sizes, states, colors and links. These are semantic element instances, including repeated rows and containers; the count does not mean 16,620 unique components. Each screen's JSON is available in the gallery.
- The assessment below covers the purpose and placement of functional blocks. Repeated cards, table rows and identical forms are grouped; individual instances remain in CSV/JSON.

Page data came from the running API. The browser walkthrough used an injected session response, and read requests used existing access to the environment. Thus, real data and UI rendering were checked, but password login, session refresh and authenticated WebSocket connections were not. `Operations Events: Reconnecting` is not treated as a product defect in this setup. Forms were not submitted, jobs not launched, settings not changed and objects not deleted. The final walkthrough had no scenario execution failures or unhandled JavaScript errors; individual errors handled by the UI itself are listed below.

The environment contained four ordinary Projects, 16 Eval workspaces and 147 completed Runs. There were no active Runs or allocations, pending Reviews or published ExecutionConfigs. Available empty states were checked for those sections. LLM Credentials coverage includes the empty list and creation form; a successful existing-credential detail page was unavailable because there were no records. Unavailable populated states were examined through routes and components, but their visual correctness is unverified. Starting a Review immediately creates a record, so the subsequent form was assessed from source. This review is neither user research nor a full WCAG assessment.

**What already works well**

| Element | Value and assessment |
| --- | --- |

| Findings | Model proposals, analyst decisions and evidence provenance are distinct. Preserve this semantics when making the screen more compact. |
| Runtime Agents | Online/offline status, availability, slots, heartbeat age and expandable diagnostics provide useful operator signals. |
| Dialogs | In the tested Add artifact → Git nested journey, focus stayed inside the active dialog for 16 successive Tab presses. Escape returned first to category selection, then to Add artifact. |
| Responsive behavior | 183 of 184 tested states had no document-wide horizontal overflow. Separate scrolling in tables and viewers is sometimes present and is not itself a problem. |

**Detailed observations and proposed changes**

**D01. Restore viewing of successful Runs.** [Screenshot](../../.local/ui-design-audit-20260919/screenshots/run-4-succeeded-1440.png). For `run_17fca0457f4ade4cbec9aed20bb4a7f6`, the API returns HTTP 200, but the page shows only `Runtime configuration response shape is invalid`. The response includes `attempts[0].runtimeConfiguration.allocations[*].origins.caido`; the client's allowed-field list in [runtime-configuration.ts](../../ui/src/api/runtime-configuration.ts) omits it. The deployed version's validator reproduces the error; a copy without `caido` passes — [probe result](../../.local/ui-design-audit-20260919/probes.json). Align client and Server contracts. Failure of an optional diagnostic section should leave independently validated core Run information and results accessible. Acceptance: this Run opens, results are available, and Caido provenance is displayed correctly.

**D02. Remove horizontal overflow from New Audit.** [Mobile screenshot](../../.local/ui-design-audit-20260919/screenshots/project-new-audit-390.png). At a 390 px viewport, document width becomes **916 px**; selected-profile panels and long values extend beyond the right edge. Check grid-item minimum widths, wrapping of long values and select width; form contents must fit the available column. Acceptance: the form and primary action are accessible at 390 and 320 CSS px without scrolling the whole page horizontally. The second width is a proposed regression criterion; this review used 390 px. See [W3C: Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html).

**D03. Fix hover in the ZIP tree.** [Hover screenshot](../../.local/ui-design-audit-20260919/screenshots/archive-hover-probe.png). Selected `App.java` has text color `rgb(233, 237, 243)` and hover background `rgb(227, 255, 154)`: contrast **1.07:1**, versus **11.20:1** without hover. The selected-file style conflicts with global button hover styles; default, selected, hover and focus states need coordination. Acceptance: normal-sized text has at least 4.5:1 contrast in all those states, with visible focus. [W3C: Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).

**D04. Handle SKILL.md metadata separately.** [Screenshot](../../.local/ui-design-audit-20260919/screenshots/skill-browse-1440.png). YAML between `---` enters the Markdown renderer and is interpreted as a large heading. As a result, `name: auth description: ... compatibility: ...` dominates the viewer. Extract bounded frontmatter into compact Name / Purpose / Compatibility fields and render the main content separately. Source must preserve the original file. Acceptance: opening `skills/auth` starts with a clear description and document; metadata YAML does not become a heading. Preserve existing safe-preview limits.

**D05. Use shared form components.** [Git import](../../.local/ui-design-audit-20260919/screenshots/project-git-import-1440.png), [Application target](../../.local/ui-design-audit-20260919/screenshots/project-target-edit-1440.png), [Upload Skills](../../.local/ui-design-audit-20260919/screenshots/skill-upload-1440.png), [Delete Project](../../.local/ui-design-audit-20260919/screenshots/project-delete-dialog-1440.png). Some input/select controls look like native gray elements; Application target labels and fields are almost fused into one line. Git URL is 30 px high with placeholder contrast **2.43:1**. Neighboring forms use different styling. Apply shared Field/Input/Select/ActionRow components in dialogs too, and check styles' dependency on parent containers. Keep focus clearly visible. Acceptance: consistent spacing, label placement, widths and focus/error/disabled states across all listed forms, including mobile.
**D06. Make completed-work lists more compact.** [Runs](../../.local/ui-design-audit-20260919/screenshots/runs-completed-1440.png), [allocations](../../.local/ui-design-audit-20260919/screenshots/operations-allocations-completed-1440.png). A page with 50 Runs is **15,449 px** tall on desktop and **23,283 px** on mobile. Identifiers and four audit labels inflate rows; Workflow wraps across many lines. The 50 completed allocations take **15,673 / 31,415 px** because of full metric cards and repeated explanations. Use a compact list: Workflow/task, project, status, result, duration, time; reveal IDs, labels, and resource details within a row or side panel. Project Runs already provides an example. Add contextual filters and pagination accessible at both the top and bottom. Acceptance check: the same dataset shows several comparable rows in a desktop viewport; technical details do not increase the height of a collapsed row.

**D07. Organize a Run around its result.** [Successful Run](../../.local/ui-design-audit-20260919/screenshots/run-1-succeeded-1440.png). A `Preview outputs` link is already visible in the first viewport, but a prominent `Configure another Run` button and a separate rerun panel precede Results. The Results heading itself starts at **y=925 px** on desktop and **y=1379 px** on mobile. The `Next valid action: Use the durable Run record` block suggests viewing diagnostics even after successful completion. After a brief status, show the primary output with a prominent “Open result” action; keep rerun as a secondary header action. For failed/cancelled Runs, prioritize the reason and a link to the controlling Audit/Eval. Put attempts, transitions, and raw diagnostics in separate tabs or expandable sections. Acceptance check: the first viewport of a successful Run focuses on reading the result; next-action text depends on the state.

**D08. Prioritize content in Artifact detail.** [Skill on mobile](../../.local/ui-design-audit-20260919/screenshots/skill-detail-390.png), [OpenAPI](../../.local/ui-design-audit-20260919/screenshots/project-artifact-openapi-1440.png). A binding heading, six metadata fields, another preview heading, and an explanation come first; the file starts much farther down. On mobile, Browse files is around y=864 px. Below the preview, Upload a new version remains expanded, followed by Versions and Lineage. Suggested structure: a compact file header with type/size and version selection, “Open / Download,” a main Files/Preview area, and adjacent History/Details tabs. Open version upload through a separate action. A full-screen preview is useful for diagrams and OpenAPI. Explicit loading remains appropriate for large materials; place the button near the top of the page. Acceptance check: users immediately see how to open the file, and its content occupies most of the workspace once opened.

**D09. Make incomplete audit coverage explicit.** [Overview](../../.local/ui-design-audit-20260919/screenshots/audit-overview-1440.png). The selected Audit is `COMPLETED`, but stopped at the time limit: **13 of 23** operations were fully checked, seven need continuation, and three were not checked. A banner explains this, but the primary badge reads as the outcome of the task. Show the coverage outcome alongside process completion: “Completed with gaps · 13/23 checked · time limit.” Connect a prominent “Continue” text button to that message. Distinguish confirmed issues from candidates: `0 confirmed` and `1 candidate` must not collapse into a general “no issues.” Acceptance check: the first viewport makes clear what was checked, what remains, and which action is available.

**D10. Bring decisions closer to Findings.** [Audit findings](../../.local/ui-design-audit-20260919/screenshots/audit-findings-1440-full.png), [Project findings](../../.local/ui-design-audit-20260919/screenshots/project-findings-1440-full.png). Full Markdown descriptions occupy long cards; Review/Correct analyst rating buttons follow the text. In the project list, a confirmed finding precedes one awaiting review. Show a compact title, severity, decision status, source, and short excerpt; open details and evidence in a panel. Make the “Needs decision” filter obvious and keep actions for the open finding beside its context. Preserve the distinction between a model proposal and a human decision. Acceptance check: users can see the decision queue and open an item without scrolling through other findings' full descriptions; the action remains available while reading the selected finding.

**D11. Separate check results from technical history.** [Checks](../../.local/ui-design-audit-20260919/screenshots/audit-checks-1440.png), [Runs](../../.local/ui-design-audit-20260919/screenshots/audit-runs-1440.png). The Coverage tab is titled `Checks & results` internally, while Checks shows technical records; the distinction is unclear. The 23 checks form a **16,641 px** desktop page. The operation hash repeats in the heading and fields; task/result links hinder scanning. In Audit Runs, the wide ID column takes space from meaningful fields. Use purpose-based names: “Coverage and results,” “Check execution”; use the API method and path or requirement name as headings. Put status, verdict, attempt count, and evidence in the row; reveal keys and provenance on expansion. Acceptance check: a row conveys the subject and outcome of a check without opening technical fields.

**D12. Improve profile selection in New Audit.** [Form](../../.local/ui-design-audit-20260919/screenshots/project-new-audit-1440.png). The initial value is `openapi-operation-trace@2`, although @3, @4, and @5 are available; other families also appear as flat version lists. This is an observed value, not proof that the older version is unsuitable. Select a profile by purpose first, then an explicit version; use a published recommendation to set the preferred option, or otherwise show the latest family version with access to earlier ones. Show the objective, coverage size, and required materials alongside it. Acceptance check: version selection is deliberate, the reasons for a recommendation are visible, and the pinned contract remains precise.

**D13. Make Home an accurate readiness summary.** [Home](../../.local/ui-design-audit-20260919/screenshots/home-1440.png). Runtime capacity is available and shown as `HEALTHY / Capacity is ready`, but the environment's queue is paused. Show admission state separately, with a link to Queue. `Recent failures` contains 26 failures from the last 50 Runs, mostly old work from one period; without a clear age, this summary looks like a current problem. Group by project/Audit, show the period and age, and distinguish history from issues requiring action. Move “Continue project / Select Workflow” higher; Quick start currently follows the main summary. Acceptance check: Home makes clear whether new work can start and which specific actions need attention.

**D14. Reduce repeated headings and internal terminology.** [Settings](../../.local/ui-design-audit-20260919/screenshots/operations-settings-1440.png), [Agent detail](../../.local/ui-design-audit-20260919/screenshots/agent-detail-1440.png). An eyebrow, large title, architectural description, tabs, another heading, and a panel heading often repeat the same idea. `USER SCOPE BINDING`, `EXACT CAS UPDATE`, `IMMUTABLE`, and `SAFE TYPED BODY` are more prominent than the user's action. Settings first shows two “configuration areas,” then their cards and repeated headings; the only Scheduler field starts around y=898 px. Keep one page title, a short purpose statement, and a toolbar; move contract explanations into Details/help. Retain runtime/operator terms where they help users choose. Acceptance check: the first working section is available immediately after brief context.

**D15. Organize Project overview around current work.** [Screenshot](../../.local/ui-design-audit-20260919/screenshots/project-overview-1440.png). Pending Audit Review and unreviewed Findings are different queues; the overview should explicitly account for both. Project context shows the first three of four materials by name: two API JSON files and source-metadata; the main source ZIP is absent from the summary. Use neutral styling when no tasks require attention and show actual actions. Group materials by role: source code, API, documents, results, supporting metadata. Acceptance check: source is visible in the Nextcloud overview, and the attention color reflects a real need for action.

**D16. Help users choose a Workflow for their task.** [Catalog](../../.local/ui-design-audit-20260919/screenshots/catalog-workflows-1440.png), [Project Workflows](../../.local/ui-design-audit-20260919/screenshots/project-workflows-1440.png). **D17. Group agent versions.** [List](../../.local/ui-design-audit-20260919/screenshots/catalog-agents-1440.png). **D18. Present Skills as instructions with a purpose.** [List](../../.local/ui-design-audit-20260919/screenshots/catalog-skills-1440.png), [opening from Catalog](../../.local/ui-design-audit-20260919/screenshots/skill-from-catalog-1440.png). **D19. Focus Evals on comparing results.** [List](../../.local/ui-design-audit-20260919/screenshots/evals-1440.png), [detail page](../../.local/ui-design-audit-20260919/screenshots/eval-detail-1440.png). Move the scenario, suite/version, associated Runs, evaluation result, and comparison with previous attempts to the top where such evaluations exist in the data. A Succeeded Run indicates execution completion and must not automatically become a passed Eval. If there is no evaluation model, explicitly present it as a workspace for Runs. Acceptance check: two Evals with the same name are distinguishable by meaningful data; the current result appears near the top of detail.

**D20. Make the active configuration visible.** [List](../../.local/ui-design-audit-20260919/screenshots/runs-configuration-1440.png), [bindings](../../.local/ui-design-audit-20260919/screenshots/runtime-bindings-1440.png). Display Built-in/— for sentinel timestamps. In the rebind dialog, show a brief before → after; if there is no change, explain the action explicitly or omit it. Acceptance check: users can identify the active default version directly in the list.

**D21. Connect execution settings through shared navigation.** RuntimeConfig and runtime credentials are under Runs, ModelPolicy/Gateway and LLM credentials under Operations, Git SSH under Settings, and the target under Project. Acceptance check: from Configure Run, users can find the configuration in use and where to change it, understanding which future work it will affect.

**D22. Standardize how forms open and are structured.** [Publish RuntimeConfig](../../.local/ui-design-audit-20260919/screenshots/runtime-config-publish-1440.png), [Add artifact](../../.local/ui-design-audit-20260919/screenshots/project-artifact-add-1440.png). In Publish RuntimeConfig, show a section's fields after enabling it, retaining a brief description of its effect; put technical parameters in Advanced. **D23. Improve Run parameter fields.** [Configure Run](../../.local/ui-design-audit-20260919/screenshots/workflow-run-drawer-1440.png). `authorization_scope`, `objective`, and `target` appear as identical single-line fields without domain-specific examples; the objective and analysis boundaries usually require several sentences. Use published labels/help/examples and textareas for long values, preserving exact keys in Details. Link the missing-field counter to the fields. Acceptance check: users can fill required parameters using form guidance without reading the technical contract; progress and draft saving remain available.

**D24. Emphasize resource state and trends in Performance.** [Screenshot](../../.local/ui-design-audit-20260919/screenshots/operations-performance-1440.png). Many numbers have equal visual emphasis, alongside technical footnotes and `Unavailable`; charts start far below the summary. Put CPU, RAM, GPU/VRAM, and database metrics at the top, with a clear measurement scope, freshness, and short trends with period selection. Expand detailed counters on demand. Format memory as readable GiB plus a percentage, with exact MiB in details where needed. Unavailable values should be visually neutral; status colors should use defined thresholds. Acceptance check: operators can see the current constraint and its trend without a long scroll.

**D25. Explain errors accurately and offer an available action.** [Nextcloud ZIP](../../.local/ui-design-audit-20260919/screenshots/project-artifact-zip-1440.png). Archive indexing returns 422; the UI mentions a 256 KiB text-file limit even though no file inside has been selected. Distinguish index/uncompressed-size/entry-count limits from individual preview limits, use the response reason, and offer Download. On a Run, provide a way to retry reading and return to context, with the technical reason expandable. In empty Reviews/allocations, explain the state briefly and provide a relevant link; do not spend space on inactive pagination for a single empty page. An unknown URL currently returns only `not found` on white — [screenshot](../../.local/ui-design-audit-20260919/screenshots/not-found-1440.png). Provide a clear 404 page linking to Home/Projects while preserving the HTTP status. Acceptance check: messages explain the specific failed operation and the next available step.

**D26. Align mobile tabs and tables.** Project tabs become a select; Audit and Operations use a horizontal strip with some items hidden. Add a visible scroll hint/More action or use a consistent section selector. In wide tables, keep the name and action visible while allowing extra columns to scroll; compact cards may work for short lists. Acceptance check: the selected section and access to the others are obvious, and primary actions are available without searching beyond the right edge. Preserve existing code and schema scrolling as specialized content behavior.

**D27. Standardize action emphasis.** Refresh often dominates a toolbar, while the useful action is hidden in an icon or farther down the page. Confirmations already identify the object and consequences usefully, but Cancel/Keep unchanged text and button order/spacing vary, with buttons touching in places. Acceptance check: each context has one clear primary action and consistent secondary and destructive actions; Refresh is accompanied by data freshness.

**D30. **D32. Align secondary labels and visual emphasis.** [Login](../../.local/ui-design-audit-20260919/screenshots/login-1440.png) shows a hardcoded `v.2.0`, while the application shows UI `0.2.0`. **Suggested order of design changes**

1. **Restore previewing and fix clear defects:** D01–D05. Check a successful Eval Run, New Audit on mobile, file hover, and SKILL.md; apply shared fields to dialogs.
2. **Orient primary flows toward results:** D06–D13. Compact history, a Run result in the first viewport, a viewer with a large content area, a clear Audit outcome and decision queue, and accurate Home readiness.
3. **Align recurring patterns:** consistent page header, toolbar, status summary, compact list, detail/disclosure, field/action row, and dialog/drawer. Then apply D14–D30 to catalogs, Evals, and Operations.
4. **Validate with real tasks:** open a completed Run's result; read a Skill and a file in a ZIP; find an unreviewed Finding and its evidence; understand incomplete Audit coverage; select a Workflow and exact inputs; identify the active default configuration. For each scenario, measure search time and selection errors, not just click counts.

Overall improvement criterion: the first viewport answers “where am I,” “what happened / what is available,” and “what action is needed now.” Technical precision remains available in details without requiring users to read it before every action.
