M · Reusable, verifiable artifacts — diff as lingua franca

Web-sourced prior art, tools, papers and articles relevant to this direction. Links are real web-search results; relevance notes are the researcher's synthesis.

M1 — Feeding the @trace-annotated diff to verify/exploit raises accuracy vs raw findings

Diff-XYZ: A Benchmark for Evaluating Diff Understanding
Isolates diff representation from retrieval/tool noise via apply / anti-apply / diff-generation tasks on 1,000 real edits. Establishes that models can reliably reason over a diff as an input artifact — the precondition for handing an annotated diff to a downstream verifier.
Nexxen — Building an Artifacts System for Our LLM Data Agents
Engineering account of passing intermediate work products between agents as first-class artifacts rather than re-prompting from raw source — the pattern of consuming an upstream artifact instead of re-deriving.
SWT-Bench: Testing and Validating Real-World Bug-Fixes with Code Agents
Agents reason over a diff/patch to generate tests that validate a change — analogous to a verifier consuming an annotated diff to confirm reachability rather than re-deriving entry→sink.

M2 — Persisted annotations make a re-run / update workflow cheaper than cold

Reusing Caches and Invariants for Efficient and Sound Incremental Static Analysis
Formal incremental-analysis result: reuse prior caches/invariants and re-analyze only changed parts + dependencies. The soundness argument behind warm-re-trace reuse of persisted annotations.
Reviser — Incremental Analysis
Concrete algorithm that extracts changed program parts and re-analyzes only those plus dependencies; reports up to ~80% time saved vs full recomputation — a direct quantitative analog of cold-vs-warm token savings.
Static Code Analysis Best Practices (SonarQube PR-scan caching)
Describes the production mechanism: analysis cache reuses data for unchanged files, PR-focused analysis examines only affected code. The exact incremental-reuse pattern M2 wants for an update workflow.

M3 — Artifact discipline: every artifact must have a consumer or be dropped

Exploring Advanced LLM Multi-Agent Systems Based on Blackboard Architecture
Blackboard model where every intermediate/final product is written to a shared store and write-events activate other agents' monitors — gives a producer→consumer activation graph, the natural place to detect an artifact with no consumer.
Architecting Efficient Context-Aware Multi-Agent Frameworks (Google)
Argues for a shared workspace where agents write/read/patch shared content "without inflating agent prompts" — motivates pruning artifacts no agent reads, since unconsumed artifacts are pure context/cost overhead.
Context Engineering 2.0: The Context of Context Engineering
Frames working context as a compiled view over sources/flows/processors — implies any artifact not flowing into a compiled downstream view is dead weight, the discipline M3 proposes.

M4 — A unified-diff artifact is reused more reliably by small models than a bespoke JSON/YAML artifact

Unified diffs make GPT-4 Turbo 3X less lazy (aider)
Headline prior art: switching the edit artifact from SEARCH/REPLACE to unified diff raised benchmark score 20%→61% and cut lazy/unhelpful output 3X. Strong evidence diff format itself, holding content constant, changes reuse reliability — and that line numbers hurt.
Diff-XYZ (PDF) — format × model-size interaction
Crucial nuance / partial counter-signal for M4: format choice interacts with model size — search-replace helps larger models on generation but is "not suited well for diff analysis and smaller models." Supports testing format × model-size rather than assuming diff always wins.
LLM Structured Output in 2026 — reliability by method
Quantifies that prompted JSON is schema-valid only ~80–95% of the time and fails silently on edge cases (without constrained decoding) — the failure mode a line-anchored diff sidesteps for small models.
Beyond JSON: Picking the Right Format for LLM Pipelines (JSON/YAML/XML/TOON)
Comparative discussion of format token-cost and parse-reliability tradeoffs across LLM pipeline stages — useful framing for the structured-vs-diff A/B and its cost dimension.

M5 — The artifact-contract generalizes: any reusable diff beats re-deriving from source

SWE-bench — unified diff as the canonical code-change representation
Establishes the unified diff (.patch) as the standardized, machine-applicable, GNU-diffutils-based interchange format every coding agent emits and consumes — the case for diff as a project-wide artifact contract, not a trace-specific one.
SWE-Bench-CL: Continual Learning for Coding Agents
Treats accumulated patches/diffs as reusable artifacts an agent composes over across tasks — generalizes "consume the diff vs re-derive" beyond a single stage, matching M5's multi-task-pair claim.
SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering
Aggregates an episode's edits into a single .patch as the canonical hand-off — concrete evidence that emitting one verifiable diff per task is a workable, re-appliable contract across heterogeneous tasks.
