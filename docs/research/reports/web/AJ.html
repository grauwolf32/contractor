AJ · Pragmatic RAG integration (plain, pinned, bounded)

Where plain RAG earns its place in a project that defaults to a deterministic artifact pool (Z) and in-prompt skills (AE/AA) — kept reproducible, plain over graph, and bounded by where cache-augmented in-context beats retrieval. Links are real web-search results; relevance notes are the researcher's synthesis.

AJ1 — plain RAG over a curated security KB lifts the small model where knowledge doesn't fit resident context

ToolRAG: A Novel Approach to the Detection of Code Vulnerabilities
A RAG agent retrieves CWE-database fields to give the analysis LLM better context and avoid false positives — direct evidence that retrieving a curated security KB (CWE/sinks) helps a detection agent, the AJ1 use case.
RESCUE: Retrieval Augmented Secure Code Generation
Training-free injection of external security knowledge; also warns conventional RAG struggles with raw-doc noise and misses implicit security semantics — argues for a curated KB, not a dump.
Retrieval-Augmented Generation for LLMs: A Survey
The canonical survey: RAG most helps knowledge-intensive, domain-specific, factual tasks and under-fitted (smaller) models — frames when RAG is worth the plumbing for a 27–80b model with knowledge gaps.

AJ2 — reproducibility-pinned RAG recovers run-to-run determinism (executes Z6)

On The Reproducibility Limitations of RAG Systems (ReproRAG)
Shows non-determinism originates in the vector-retrieval stage and ranks the sources of uncertainty: embedding > index > precision > hardware > distribution. The fix is to pin them (fixed encoder, deterministic index, stable aggregation) — the concrete recipe for the "pinned RAG" Z6 proposed, and the test (Jaccard / Kendall's Tau across repeats).
Local Hybrid Retrieval-Augmented Document QA
Local, hybrid (lexical + vector) retrieval that runs without external APIs — fits the sovereignty/on-prem constraint and reduces the embedding-model variance ReproRAG flags (lexical/BM25 is deterministic).

AJ3 — plain/hybrid RAG suffices; GraphRAG's cost isn't justified for small KBs

GraphRAG vs. Vector RAG: side-by-side comparison
GraphRAG wins multi-entity/relationship and cross-document reasoning; vector RAG is faster/cheaper for simple factual retrieval — for this project's small, mostly-lookup KBs, plain vector/hybrid is the right default.
Graph RAG vs Vector RAG benchmark
Quantifies the tradeoff (graph 3–4× better on aggregation/cross-doc; vector degrades past ~5 entities/query) and notes LazyGraphRAG cuts graph indexing cost to ~0.1% — i.e. adopt graph only if relationship queries actually dominate.
VectorRAG vs GraphRAG: technical challenges
Warns entity-extraction quality is the single biggest determinant of GraphRAG success and that teams waste months on it where hybrid search would have sufficed — the case for "don't over-engineer; plain first."

AJ4 — RAG as the retrieval layer for experience memory (O) and N-day variant matching (N)

RAG for LLMs: A Survey (retrieval mechanisms)
The retrieval machinery (similarity over a store) is exactly what O (recall prior confirmed findings / FP anti-patterns) and N (find code similar to a known-vulnerable pattern) need — RAG is the implementation layer, over the deterministic pool (Z) as the substrate.
Retro-li: Small-Scale RAG with Noisy Similarity and Domain Shift
RAG tuned for small-scale stores and noisy retrieval with domain shift — matches an experience/finding store that starts small and grows, and shows it can still help under imperfect matches.

AJ5 — for small static KBs, CAG (preload into context/KV-cache) beats RAG; find the crossover

Don't Do RAG: When Cache-Augmented Generation is All You Need for Knowledge Tasks
Preloading a small, stable KB into the context (cached KV) eliminates retrieval latency and retrieval errors and matches/beats RAG — the formal backing for the project's "in-prompt skills beat RAG plumbing" stance (AE/AA), with the explicit limit: it only works while the KB fits the window.
CAG: Cache-Augmented Generation (reference implementation)
Working implementation; useful to A/B CAG vs RAG as the security KB / skill set grows, to locate the size crossover where retrieval finally earns its keep.
Beyond RAG: how CAG reduces latency and complexity for smaller workloads
Practitioner framing: CAG suits well-defined, stable, smaller knowledge sets (prioritize speed/simplicity, no retrieval failure surface) — precisely this project's skill bundles today.

Caveat — KB hygiene (data, not prompt-injection)

Security Threats of Knowledge Base Poisoning in Retrieval-Augmented Code Generation
A retrieved KB can carry vulnerable/poisoned examples that degrade or subvert output — so any RAG here must retrieve from a curated, provenance-tracked store (the deterministic pool Z), not from untrusted scraped corpora. This is a data-hygiene concern, distinct from the agent prompt-injection topic that's out of scope.
