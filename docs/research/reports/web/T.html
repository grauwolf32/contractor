T1 — Coverage feedback raises exploit success where blind probing plateaus, at equal budget

OSS-Fuzz: Fuzz Target Generation using LLMs
Google's production system feeds coverage deltas (via Fuzz Introspector) back to the LLM to steer toward under-covered branches, then revises on compile failures — the exact coverage-in-the-loop mechanism T1 proposes, with measured coverage gains.
google/oss-fuzz-gen (open-source implementation)
Reference implementation: +29% max line coverage over human targets, 370k+ new lines covered across 272 projects, 26 new vulns found — strong evidence coverage feedback beats blind generation at scale.
Large Language Models Based Fuzzing Techniques: A Survey
Survey mapping how LLMs are wired into coverage-guided fuzzing (seed/mutation/driver synthesis) — situates T1's design space and reports where the model-steered approach lifts capture vs plateauing baselines.
Fuzzing BusyBox: Leveraging LLM and Crash Reuse for Embedded Bug Unearthing
Concrete case study combining LLM-proposed inputs with coverage/crash feedback under a fixed budget — directly analogous to T1's "same budget, coverage on/off" capture-rate test.

T2 — LLM-proposed property tests, falsified by a fuzzer, find logic bugs missed by static + HTTP probing

Agentic Property-Based Testing: Finding Bugs Across the Python Ecosystem
An agent infers properties/invariants from code+docs, synthesizes and runs PBTs, reflects to confirm true bugs — 56% of reports valid across 100 packages. The exact "model writes invariant, fuzzer falsifies it" loop of T2.
Property-Based Testing with Claude (Anthropic)
Vendor write-up on having an LLM author properties for a counterexample search to surface logic bugs — practical evidence that LLM-authored invariants are a viable bug-finding signal beyond pattern scans.
Can Large Language Models Write Good Property-Based Tests?
Studies the quality of LLM-generated PBTs (the failure modes: weak/trivial properties) — important calibration for whether T2's "new TP class" actually materializes or drowns in vacuous properties.
Why Property-Based Testing? (fast-check)
Reference on PBT mechanics — invariant/round-trip/metamorphic patterns and counterexample shrinking — the framework substrate T2's "user can never read another's order"-style invariants would run on.

T3 — Runtime taint (grey-box) confirms reachability the static path only conjectured, raising precision

Newsome & Song, Dynamic Taint Analysis for Automatic Detection of Exploits (NDSS'05)
Seminal DTA paper: observing tainted input actually reaching a sink at runtime detects/confirms exploits with low false positives — the foundational basis for T3's "verified-exploitable, not conjectured" verdict.
Dynamic Runtime Reachability Analysis: Real-Time Vulnerability Management
Explains how confirming a vulnerable path is actually loaded/executed at runtime upgrades priority and cuts false positives — directly the T3 effect of moving cases out of exploitable_unverified.
What Is Taint Analysis? Static vs Dynamic, and Why They Complement
Clear articulation that static taint gives breadth while dynamic taint confirms exploitability at runtime — the static-conjecture / grey-box-confirmation split T3's verdict eval measures.
HardTaint: Production-Run Dynamic Taint Analysis via Selective Hardware Tracing
Addresses DTA's main blocker — runtime overhead — making grey-box taint feasible inside a sandbox/fuzzer, relevant to whether T3 is practical to host in the existing Kali code-exec environment.
