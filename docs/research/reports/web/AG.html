AG1 — A per-line character cap (~2000 chars, before the byte budget) raises signal density

opencode #25337 — Make read tool MAX_LINE_LENGTH configurable (hardcoded 2000 chars)
A real CLI agent already enforces a per-line cap at exactly ~2000 chars and the discussion is about tuning it — direct prior art and validation that minified/data/markdown lines otherwise eat the read budget (AG1's exact mechanism).
Context management in agent harnesses: memory, files, and subagents (Arize AI)
Surveys how harnesses (Pi: 2000 lines/50KB cap) actively manage reads and "truncate in a way that hints at what else can be accessed" — frames the line-cap as one layer of disciplined read budgeting, content-blind and safe for code.
Maximum line length in your code (DEV)
Normal source code lines sit at 80–120 chars, so a ~2000-char cap only ever truncates minified/generated/base64 lines — evidence the cap is content-blind-safe for real code/comments that matter to vuln/trace.

AG2 — Large-output offload (spill to artifact + preview + resumable handle) turns truncation into pagination

NVIDIA NeMo-Agent-Toolkit #748 — Large Tool Context Management with Truncation and Storage
Exact proposal: truncate to a preview + reference, store the full output as a file keyed by tool/timestamp, retrieve via a paginated retriever tool — the spill-to-artifact + handle pattern AG2 describes, in a production toolkit.
MCP Output Too Large: Why Tool Results Exceed Token Limits and How to Fix It (Morph)
Documents single MCP outputs consuming 35–140% of the usable context and the pattern of writing full output to a scratch file, returning only a preview — turning a context-consumption problem into a (cheaper) retrieval problem.
AI Agent Loop Token Costs: How to Constrain Context (Augment Code)
"Output capping: write full content to a scratch file, return a short preview… strictly cheaper" — confirms offload recovers tail findings at modest cost, exactly AG2's pass condition.

AG3 — Throw-instead-of-truncate on a no-limit oversized read costs fewer tokens and teaches better tool use

Tool-Result Truncation: The Silent Bug That Makes Agents Lie (DEV)
Argues a half-truncated result silently corrupts reasoning, whereas a fail-loud structured error makes the model adapt (add a filter / request the first page) on the next turn — the behavioral case for throw-over-truncate.
Context management in agent harnesses (Arize AI)
Documents the Claude Code re-read stub (returns a tiny stub instead of duplicate content) and fail-loud wrappers that "stop a half-truncated response from ever reaching the model" — the measured comparative AG3 cites, that a tiny error bills far less than a truncated head.
openclaw #24920 — Tool output truncation to reduce context bloat
Open-source feature thread weighing truncate-with-stub vs error-on-oversize; corroborates that nudging the model to scope reads (offset/limit/grep) is the intended downstream behavior.

AG4 — Input compaction is where the leverage is (input ≈ 47× output)

AI Agent Loop Token Costs (Augment Code)
States prompt/input tokens dominate agent workflows when files and history are re-processed repeatedly, and that caching only helps the static prefix — directing optimization to the input side (re-feed dedup, scoping), exactly AG4's claim.
Prompt Caching 201 (OpenAI Cookbook)
Shows caching benefits accrue to the stable input prefix and that the dynamic, per-turn input (tool outputs, re-read source) is the uncacheable cost driver — supports targeting cross-turn source-refeed dedup over output-side tweaks.
OpenCode Token Usage: How It Works and How to Optimize It (TrueFoundry)
Breaks down where tokens go in a CLI agent loop and quantifies the dominance of accumulated input context — empirical backing for the XBOW ~47:1 input:output ratio motivating input-side compaction.
