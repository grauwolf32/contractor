AD · Task & pipeline composition

Web-sourced prior art, tools, papers and articles relevant to this direction. Links are real web-search results; relevance notes are the researcher's synthesis.

AD1 — Task ablation maps which tasks earn their place (leave-one-out ΔF1/Δcost)

PublicAgent: Multi-Agent Design Principles From an LLM-Based Open Data Analysis Framework (arXiv)
Runs systematic ablations across five models: removing the analysis agent loses 76–100% of pairwise comparisons, discovery agent 79.5–98% — a concrete template for the per-task value table AD1 proposes (drop each stage, read the delta).
What Is an Ablation Study and How Removing Components Reveals What Makes AI Models Work
Plain methodology reference: measure metric delta between ablated and full pipeline to quantify each component's value — exactly the leave-one-out design for pruning dead-weight tasks (ties D).
AblationBench: Evaluating Automated Planning of Ablations in Empirical AI (arXiv)
Benchmark for automated ablation planning; useful if the catalog audit is itself to be driven by the eval harness rather than hand-curated.

AD2 — A specialized agent beats the generalist only when the subtask is distinct enough

PublicAgent (arXiv)
Ablations confirm specialized discovery/analysis agents are required for consistent cross-model performance — but the wins are concentrated in distinct subtasks, supporting "specialize where it wins, not everywhere."
Single-Agent vs Multi-Agent AI Systems (2026) — The Thinking Company
Summarizes Princeton finding that a single agent with the same tools/context matches or beats multi-agent on 64% of tasks; specialization wins only on parallelism, distinct domains, or adversarial validation — the decision rule AD2 wants (measured lift, not intuition), and the proliferation cost.

AD3 — Declarative composition (topological order from declared artifact deps) reproduces hand-coded pipelines with less code

Prompt2DAG: A Modular Methodology for LLM-Based Data Enrichment Pipeline Generation (arXiv)
Turns a pipeline into a versioned JSON artifact (components + flow + deps) instead of bespoke code; the Hybrid/template approach hit 78.5% success vs 29% for direct LLM generation — evidence that data-as-pipeline (AD3's core bet) beats ad-hoc and that structure must be kept, not fully delegated.
A DAG-Based Approach to LLM Workflow Orchestration (DEV)
Shows dependency-defined execution order auto-handles parallelization/retries/cost and "reduces orchestration code" — directly the LOC-reduction claim AD3 must validate against hand-written workflow.py.
From Pipelines to Agents: How Orchestration is Being Rewritten (ZenML)
Notes traditional static DAGs handle runtime-determined paths poorly — the honest kill condition for AD3 ("kill if the graph can't express a needed control flow") and why dynamic/conditional edges are a known patch.

AD4 — Target-aware auto-composition (select tasks by target type) matches a fixed maximal pipeline at lower cost

How to Build Agentic Workflows with Conditional Logic and Branching (MindStudio)
Content-based routing inspects input properties and selects paths dynamically — the mechanism for API-vs-no-API / has-deps / has-URL task selection AD4 describes.
Microsoft Agent Framework Workflows — Edges (Microsoft Learn)
Documents selection-function edges that route to a subset of executors based on runtime conditions — concrete prior art for a selector that assembles only relevant tasks (and the misroute-rate risk AD4 flags).
Inside AWS Security Agent: A multi-agent architecture for automated penetration testing (AWS)
Production pentest pipeline that does broad recon first to map surface, then dynamically generates focused test tasks tailored to discovered endpoints/business logic — a target-aware composition pattern at security-tooling scale.

AD5 — Missing tasks add coverage (recon/auth-discovery, SCA, hypothesis-gen, triage)

Why DAST Tools Miss Real IDOR Vulnerabilities (And How AI Helps) — Apiiro
Explains IDOR needs correlated multi-user sessions that most scans lack state for — concrete justification for inserting an auth-discovery task before trace to enable two-user IDOR (AD5's named example).
Testing for IDORs (PortSwigger)
Canonical workflow: discover identifier-bearing endpoints, then test with a second low-priv account — the staged recon→auth→access-control sequence AD5 wants to insert into the pipeline.
Inside AWS Security Agent (AWS)
Each phase (recon, scanning, focused testing) is a distinct purpose-built agent — empirical layout of the catalog AD5 proposes growing (recon/auth-discovery as their own stages).

AD6 — Staging dominates: scan→triage→verify, cheap-broad then expensive-narrow, beats flat

Introducing Cascade: multi-agent penetration testing (Escape.tech)
A named multi-agent pentest product organized as cascading phases that spend expensive depth only on what cheap phases surface — direct industry evidence for AD6's cheap-broad-first staging.
Integrate Continuous Penetration Testing into CI/CD (Upscend)
Recommends lightweight checks on PRs, mid-weight on integration, full DAST+pentest on release candidates — a staged, increasing-cost handoff that AD6 mirrors at the task level (F1-per-token).
PublicAgent (arXiv)
Multi-agent design-principles study; its discovery→analysis staging and ablation deltas inform which handoff order maximizes quality per added cost.
