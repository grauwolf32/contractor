fs-tool limits across CLI coding agents

How read_file and grep cap content length in 8 popular agents — and how to tune Contractor's.

Compiled 2026-06-03 · 10 agents · Sources: local shallow clones in ~/src/cli-agent-research/ + leaked Claude Code tree in ~/claude-leaked/src/, cross-checked with vendor docs & issues. All figures cite file:line from the actual source.

Executive summary

Every mature agent applies at least two independent caps on a file read, and three distinct strategies dominate:

Strategy A · line + per-line
2000 / 2000

Default 2000 lines, and every line truncated at 2000 chars. Defuses minified/generated files. gemini-cli, opencode

Strategy B · byte cap
50 KB – 400 KB

Hard byte budget on the returned slice, with a continue-here footer. opencode 50KB · cline 400KB · goose 50KB

Strategy C · token-aware
25 000 tok

Cap on actual output tokens, plus a file-size pre-gate that errors instead of truncating. Claude Code, codex

Contractor today
80 KB · 100

fs_max_output=80_000 bytes + fs_max_items=100 grep matches. No per-line cap, no token cap. gap

Bottom line for Contractor. Two cheap, low-risk borrows give the most value: (1) a per-line character cap (kills minified/bundled/lockfile blowups that today eat the whole 80 KB budget on one line), and (2) a token-aware ceiling so the cap tracks context cost, not raw bytes. The popular "strip header comments" trick is explicitly not recommended here — see the warning below.

Techniques & "hacks" worth knowing

1 · Per-line truncation — the cheapest big win

gemini-cli and opencode cap every line at 2000 chars and append … [truncated]. This is the single most effective defence against the worst case for a byte/token budget: one giant line — minified JS, bundled CSS, base64 blobs, package-lock.json, SVG paths, generated protobufs. Without it, a single line can consume your whole budget and the model sees nothing useful.

// gemini-cli — packages/core/src/utils/fileUtils.ts:541
if (line.length > MAX_LINE_LENGTH_TEXT_FILE) {
  line = line.substring(0, MAX_LINE_LENGTH_TEXT_FILE) + '... [truncated]'
}

2 · Token-aware ceiling instead of raw bytes

Claude Code caps the actual output token count (default 25 000, env-overridable via CLAUDE_CODE_FILE_READ_MAX_OUTPUT_TOKENS) rather than bytes. Bytes are a poor proxy: CJK, JSON, and code tokenize very differently. The cap that matters for context cost is tokens.

3 · Pre-gate that throws rather than silently truncates

Claude Code's 256 KB check is on total file size and it errors before reading, nudging the model to use offset/limit/grep. Their own source documents the experiment:

// claude-leaked — tools/FileReadTool/limits.ts (verbatim comment)
// Tested truncating instead of throwing for explicit-limit reads that
// exceed the byte cap (#21841, Mar 2026). Reverted: tool error rate
// dropped but mean tokens ROSE — the throw path yields a ~100-byte error
// tool-result while truncation yields ~25K tokens of content at the cap.

Insight: a hard error is often cheaper than a truncated body, because the body still costs a full budget of tokens while teaching the model nothing.

4 · Continue-here footers (offset hints)

opencode / Claude Code / gemini-cli all tell the model exactly how to resume: Use offset=2001 to continue. deepseek-tui makes it a first-class response field — every truncated read returns next_start_line and a truncated="true" flag, so the model never has to compute the resume point. opencode / openclaw phrase it as prose ("continue with offset until complete"). Contractor's footer reported lines-left but not a ready-to-use offset — now fixed: the footer emits resume with read_file offset=N alongside the existing fields.

// opencode — read.ts:348
output += `\n\n(Output capped at 50 KB. Showing lines ${offset}-${last}. Use offset=${next} to continue.)`

// Contractor — format.py:126 (current)
footer = f"\n\n### truncated at line: {cut} ### lines left in the file: {remaining} ###"

5 · grep: output mode + stacked caps

Claude Code defaults grep to files_with_matches (cheapest), making full content opt-in. cline stacks two caps — 300 results and a 0.25 MB byte ceiling — so a few huge matching lines can't blow the budget even under the count limit. openclaw caps each match line at just 500 chars (GREP_MAX_LINE_LENGTH) — the most aggressive in the survey — and deepseek-tui caps total matches at only 20. Contractor only caps by count (100), so 100 fat match entries are unbounded in size.

6 · Whole-repo skeletonisation (aider)

aider's real "hack" isn't on a single read — it's the repomap: tree-sitter parses every file, discards function bodies, keeps signatures + class/def structure, ranks files by a PageRank over the symbol graph, and packs the top of that into a ~1024-token budget. It's the strip-the-noise idea taken to repo scale. Relevant if you ever want a cheap "structural overview" tool alongside read_file.

⚠ On "strip header comments / strip comments" — do NOT do this in Contractor.
It's a popular token-saver (RTK/TAMP proxies strip comments + boilerplate for ~50% savings), but Contractor's workers do OpenAPI tracing and vulnerability analysis. Comments routinely carry exactly the signal those workers need: auth/permission notes, TODO/FIXME/SECURITY markers, deprecation warnings, route docs, license/PII hints. Your own crAPI fixtures had vuln-hint comments scrubbed on purpose to avoid leaking answers — proof that comments are semantically load-bearing for this workload. Stripping them would silently degrade trace/vuln quality and risks overfitting behaviour. Cap by length/tokens (content-blind), never by semantic class (comments).

Recommendations for Contractor

Ordered by value/effort. All are content-blind (safe for trace/vuln). File pointers are to the current tree.

1

Add a per-line character cap to read_file and grep high value · low risk

Truncate any line over ~2000 chars (suggest a fs_max_line_length setting) with a … [truncated N chars] suffix, before the byte budget is applied. This is the gemini-cli/opencode default and the biggest gap today: one minified line currently consumes your entire 80 KB read. Touch format.format_output (format.py:105) and the grep match rendering (FsEntry.from_matches). New knob in settings.py next to fs_max_output.
2

Make the truncation footer emit a ready-to-use offset ✓ shipped

Implemented. format.format_output now appends resume with read_file offset=N next to the existing fields, where N is absolute and reflects the lines actually kept after footer-trimming (no gap/overlap). Opt-in via a base_offset kwarg so diff output is unaffected; suppressed when a single line exceeds the budget (would otherwise loop). Precedent: deepseek-tui ships this as a structured next_start_line field.
3

Add a token-aware ceiling alongside the byte cap high value · medium

Bytes under-count CJK/JSON and over-count ASCII code. Add an optional fs_max_output_tokens (Claude Code uses 25 000) using whatever tokenizer the run already loads, and cap on min(bytes, tokens). If a tokenizer isn't cheaply available in the tool layer, a bytes-per-token heuristic (~3.5–4) is a fine first cut. Keep the byte cap as the fast pre-filter.
4

Give grep a per-output byte/line budget, not just match count medium · low risk

cline stacks a 0.25 MB byte cap on top of its result count. Contractor caps at 100 items but each item's rendered match line is unbounded — 100 long matches can dwarf an 80 KB read. Apply the same per-line cap from #1 to each match, and add a total-bytes guard in the grep paginator (read_tools.py:444-460).
5

Consider a file-size pre-gate that errors on oversized whole-file reads nuance · optional

Claude Code's measured result: when a read with no explicit limit targets a >256 KB file, returning a short error ("use offset/limit/grep") cost fewer tokens than returning a truncated head, because the truncated head still bills a full budget. Worth A/B-ing in your eval harness given your existing pass@X envelope — but only for the no-limit path; explicit-range reads should still truncate.
Suggested defaults if you adopt #1–#3: fs_max_line_length = 2000, fs_max_output = 80_000 bytes (keep), fs_max_output_tokens = 25_000, fs_max_items = 100 (keep), + a grep per-match line cap reusing fs_max_line_length. Every value mirrors at least one mainstream agent, so they're well-trodden, not guesses.
