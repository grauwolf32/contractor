Contractor vs CLI agents — capability gap analysis

What 10 popular coding agents do that Contractor doesn't — filtered to what actually serves its mission: static analysis of a codebase → OpenAPI specs + security traces + vuln findings.

Compiled 2026-06-03 · method: parallel source-level tool-surface inventory of all 10 cloned agents + the leaked Claude Code tree, diffed against Contractor's real tool registry (contractor/tools/*). Every claim about Contractor was verified in-tree, not assumed.

Framing. Contractor is not a general coding assistant — it's a batch, sandboxed, security-analysis pipeline. So most "cool agent features" (cron, teams, worktrees, browser, notebooks, plan-mode-with-human-approval, web search) are deliberately out of scope and listed as such at the end. The gaps below are only the ones that move the needle on tracing, vuln-finding, or OAS fidelity.

First, where Contractor already leads

Several agent-inventory findings were simply wrong about Contractor (the inventories lacked full context). Verified in-tree, Contractor is ahead of every surveyed CLI on the things that matter for its mission:

Recommended additions

Ordered by value-to-mission ÷ effort. Each is content-/security-aware and fits Contractor's existing primitives (tree-sitter engine, artifact store, podman sandbox, overlay FS).

1

Ad-hoc AST-pattern search (ast-grep) — complements trailmark

LOW–MED valueeffort: med
Correction from an earlier draft: Contractor is not limited to regex here. Its trailmark engine is tree-sitter–based and already gives AST-derived structure — a typed symbol + call/import/inherit graph, framework-aware route/entrypoint detection (Flask/FastAPI/NestJS/Spring/actix/… via decorator+attribute patterns), and a taint model (TAINT_PROPAGATION, PRIVILEGE_BOUNDARY, trust levels). So "every caller of eval" and "every route handler" are already answerable.

What trailmark does not do is match an arbitrary syntactic shape outside its fixed node/edge schema: e.g. os.system($CMD) with a specific argument shape, request.args[$K] subscript access, attribute chains, or a sink whose name is built dynamically (so the call-graph can't resolve it). A thin ast-grep wrapper in the podman sandbox covers exactly those ad-hoc, expression-level patterns. It's a complement to trailmark for novel sink shapes — not a foundational gap, hence the downgraded priority.
trailmark already covers structure: analysis/entrypoints.py:11-31 (route decorators), models/annotations.py (taint kinds), query/api.py (callers_of/paths_between) · the delta is ad-hoc pattern matching only
2

Large tool-output offload to an artifact (spill + preview + handle)

HIGH valueeffort: med
Contractor already has honest truncation (result.py caps and flags) and an artifact store — but a capped grep/read/graph result is discarded past the cap, not parked. Borrow the now-standard pattern: when a tool result exceeds a token threshold, write the full result to an artifact and return a short preview + a handle (artifact_key + offset/grep continuation). This directly extends the read_file/grep limit work and turns truncation from data-loss into pagination. deepseek goes further — a synthesis sub-agent condenses the spilled output and returns only the summary, keeping the raw in a variable.
deepseek-tui-h large_output_router.rs:23 (DEFAULT_LARGE_OUTPUT_THRESHOLD_TOKENS=4096) · opencode registry.ts:174,182 (truncate.output → outputPath) · Claude Code utils/collapseReadSearch.ts
3

Git history / blame tool

HIGH valueeffort: low
For a vuln finding, when and in which commit a line was introduced is first-class provenance — and for OAS-update runs, "what changed since the last spec" scopes the work. Cheap to add as thin wrappers over the project's git (it's usually a repo, and the podman sandbox can run git): git_log(path), git_blame(path, line_range), git_show(rev). Pairs naturally with trace annotations (date the sink) and the post-diff vuln-agent idea already in your memory.
deepseek-tui-h git_history.rs:34 (git_log), :151 (git_show), :268 (git_blame) · Contractor gap verified: no git_* tool in contractor/tools
4

Ranked codebase skeleton (aider-style repomap)

MED valueeffort: med
A cheap "where do I start" overview for a fresh large target: tree-sitter tags → a symbol graph → PageRank (with personalization toward mentioned files/idents) → token-budget binary search → signature-only output. Far better orientation than ls/glob, and complementary to your call-graph (skeleton = breadth/ranking; graph = precise reachability). Your attack_surface/complexity_hotspots already cover the security-priority angle, so treat this as onboarding/efficiency, not core.
aider repomap.py:374-445 (PageRank + personalization), token-budget binary search ~676-703; boosts: chat-mention 50×, long identifier 10×, private 0.1×
5

Source linter / typecheck passthrough

MED valueeffort: low
Run the target's own checker (mypy/tsc/eslint/go vet) through the existing podman sandbox and surface structured errors with code context. Broken types and undefined names silently degrade OAS fidelity (wrong param/response shapes) and can flag dead or newly-added routes. Low effort since sandbox exec already exists — mostly a per-language command map + error parser (aider's linter is a good template, including its "show context around the error line" output).
aider linter.py:21-150 (pluggable per-lang, flake8 fatal codes, TreeContext error context)
6

LSP find-references / call-hierarchy — consider, with caveats

MED valueeffort: high
Every TS-based CLI leans on LSP for findReferences, goToDefinition, incomingCalls/outgoingCalls. It gives language-server-grade cross-file precision that tree-sitter can't match on overloads/dynamic dispatch. But Contractor's call-graph engine already answers the core trace questions, and LSP means running & managing a language server per language inside the sandbox — heavy, and at odds with the batch model. Recommendation: only pursue if multi-language reference precision becomes a measured bottleneck in eval; otherwise invest the same effort in #1 (structural search), which is cheaper and more security-specific.
opencode lsp.ts:12-19 (9 operations incl. prepareCallHierarchy/incomingCalls) · Claude Code tools/LSPTool/LSPTool.ts

Two small efficiency wins (low effort, low risk): read_many_files (batch-read a glob in one call — gemini-cli) and a fuzzy, scored file-find on top of glob (deepseek file_search). Worth doing only if they show up as friction.

Deliberately not recommended

These are real, popular agent features — and a poor fit for Contractor's batch, non-interactive, security-analysis mission. Listing them so the choice is explicit, not an oversight:

  • Cron scheduling / remote triggers / teams & swarms (Claude Code, gemini-cli) — orchestration belongs in your workflow layer, not as model-callable tools.
  • Git worktree isolation, checkpoints — Contractor already isolates writes via the overlay FS + artifact diff; worktrees would duplicate that.
  • Browser automation (cline) — not needed for static analysis; HTTP client + Caido cover the dynamic/exploit side.
  • Plan-mode-with-human-approval, AskUserQuestion (most CLIs) — there's no human in the batch loop; the planner subtask machine is the planning surface.
  • Web search / WebFetch-to-markdown — research isn't the mission; the HTTP client is for hitting the target, not the open web.
  • Notebook editing, REPL, config tool, multimodal image/PDF read — orthogonal to code→OAS→vuln.
  • MCP client — strategically interesting (pluggable vuln DBs / SAST), but a large architectural lift; revisit later, not part of this round.
  • Already present, don't rebuild: skills, structured outputs, memory, honest truncation, parallel fan-out, sandboxed exec.

Methodology

Four parallel inventory agents read the tool source of all 10 clones + the leaked Claude Code tree, each diffing against Contractor's registry; findings were then re-verified directly in contractor/tools/* (which corrected several false "Contractor lacks X" claims — it has skills, structured outputs, memory, and parallel fan-out). Repos: ~/src/cli-agent-research/{aider, gemini-cli, cline, opencode, goose, codex, qwen-code, openclaw, deepseek-tui-h, deepseek-tui-a} + ~/claude-leaked/src.

If you do two things: (1) large-output offload to artifacts — completes the read_file/grep truncation work and stops capped tool results from losing evidence; (2) git blame/log — near-free vuln provenance & OAS drift. Both fit existing primitives (artifact store, podman) and avoid interactive-agent features that don't suit a batch pipeline. Ad-hoc AST-pattern search (ast-grep) is a worthwhile complement to trailmark for novel sink shapes, but lower priority — trailmark already covers symbols, calls, routes, and taint.
