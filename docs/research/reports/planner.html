Internal design memo · visualizations

Planner & task-runner variants

Eleven A/B-able challengers to the streamline planner, mapped to the committed decision each one tests, the code seam each one needs, and the order to build them. The baseline is one point in this space — these are the moves that change how decomposition and worker-judging happen on small (27–80b) models.

▸ Design spec & diagrams: docs/architecture/planner.md  ·  Research index: research.html  ·  hypotheses (research.html)
Baseline = streamline planner · all variants route through the eval/v1 pass@N harness

2 · One decision, three prices

V3, V4 and V8 all challenge the same committed decision at three cost points. Test them as one axis — the comparison you want is across prices for the same win, not three unrelated experiments.

Committed decision: the planner trusts the worker's self-reported status — execute_current_subtask advances on done; nothing re-checks the deliverable.
cheapest · re-ask the same worker

V8 Re-execute-once

On incomplete, re-invoke once with the prior output as context. A transient failure (sampling noise, a flaky tool) costs one retry, not a decomposition.

mid · ask a judge

V3 Critic gate

A verifier checks a done result. Cheapest scope: verify only the subtask's one Acceptance: line — which today nothing machine-checks.

priciest · ask N workers

V4 Best-of-N

Run the worker N× and merge. The recall lever for hard fixtures where a single pass misses (BOLA / injection on large Django).

4 · Effort × expected signal

Build order falls out of the bottom-left first: cheap, high-signal. V2 is high-value but high-effort and attribution-risky (it dissolves three mechanisms at once).

⚠ V2 carries an attribution risk: it dissolves the schema-instrumented planner/worker boundary, the malformed-fallback machinery, and the records pool simultaneously — if it wins you won't cleanly know why. Dot colour = axis (blue control-flow, orange trust, green context, purple retry).

5 · Recommended sequence

Two things come before any variant; then cheapest-and-highest-signal first.

0a

Seam first

Nothing is A/B-able until the planner is swappable like the worker.

0b

Baseline telemetry

V2 stays the architectural wildcard (run it, read it with the caveat). V4 / V5 / V6 / V10 are second-wave — costlier to build and run.

6 · Before any variant runs

Do this firstWhy it changes what you can conclude
Instrument the baseline
decompose count · skip-reason histogram · malformed rate · "single-child-succeeds-immediately" proxy		Without counters you can score a variant but not diagnose it. Several hypotheses ("reactive decomposition is mostly churn") are checkable from baseline telemetry before V1 is built at all — free signal on what's even worth building.
Budget for variance
pre-register N and a promotion threshold		27–80b models are high-variance; pass@N with too few seeds promotes noise. A challenger must beat baseline f1 by a margin exceeding the baseline's own seed-to-seed spread. Matters doubly because V1 / V8 / V10 are cost-wins at f1 parity — and "parity" needs a defined tolerance.

7 · The variants

Each names the committed decision it tests (§9.1 of the design doc), the seam it needs, and the metric that confirms or kills it.

V0Direct (no planner)control-flow · driver · exists
Decision tested
Whether the planner's decomposition tax pays at all on small/medium tasks.
Mechanism
Drive a single instrumented worker via AgentRunner — no subtask machine. Already the trace-direct path; give it a strategy label so it emits the same envelope.
Pass / kill
The honest floor: if f1 holds at lower tokens/run, planning isn't earning its cost on that workload.
f1 · tokens/run vs. streamline baseline
V1Plan-oncecontrol-flow · planner_builder
Decision tested
Reactive decomposition (vs. a full upfront plan, no mid-run re-planning).
Mechanism
Remove decompose_subtask from the toolset and ship a paired plan_once prompt — prompt v5 references decomposition throughout, so tool and prompt must change together (else the planner calls a tool that no longer exists).
Pass / kill
Wins if malformed/retry churn drops at equal f1; killed if recall falls because some tasks genuinely need adaptive splits.
malformed/retry count · steps/task · f1
V2ReAct / interleavedcontrol-flow · planner_builder · ⚠ attribution
Decision tested
Committed pre-planning itself — does an emergent think→act→observe loop beat a flat list decided up front?
Mechanism
A different root agent with no StreamlineManager; honours only the fixed-key contract + end_invocation.
Caveat
Dissolves the schema-instrumented planner/worker boundary, the malformed-fallback machinery, and the records pool at once. Worth running (it tests the paradigm) but budget follow-up ablations — a win won't tell you which mechanism mattered.
f1 · recall · step-budget hit-rate
V3Critic gatetrust · execution_policy / finish closure
Decision tested
The planner trusts the worker's self-reported status — nobody re-checks the deliverable.
Mechanism
A verifier gates done, at one of three scopings (cheapest first): (a) acceptance-line — verify only that the evidence satisfies the subtask's one Acceptance: line; (b) finish-gate — one verifier call per task; (c) per-subtask — gate every done. Reuse trace_verifier_agent.
Pass / kill
Targets the documented failure modes (over-annotation precision loss, silent misses). The acceptance-line scope is far easier for a small model than open-ended verification.
precision · verdict accuracy · false-done rate · cost per scope
V4Best-of-N workertrust · execution_policy
Decision tested
One worker pass per subtask (trust axis — the priciest re-check).
Mechanism
Run the worker N× on the same subtask; the policy merges or picks before returning one result.
Pass / kill
The recall lever for hard fixtures (crApi-workshop BOLA / injection misses); watch the cost multiple.
recall@N · unique-findings union · cost
V5DAG / dependency-scheduledcontext · scheduler · deep
Decision tested
Flat, strictly-sequential execution.
Mechanism
A depends_on field on Subtask; the scheduler picks the first dep-ready subtask; the runner executes independent ready siblings concurrently (reuse the trace_graph_pathpar overlay fork/merge machinery).
Pass / kill
Wallclock win at f1 parity when subtasks are independent. Second-wave — the one seam spanning manager and runner.
wallclock · f1 parity
V6Rolling-summary contextcontext · records_policy
Decision tested
The last-20 records pool as the only history view.
Mechanism
Fold each record into a running compressed summary (an on_record hook); the planner sees that summary instead of the raw tail.
Pass / kill
Wins if f1 holds on large fixtures at lower tokens/run; killed if compression drops detail the planner needs.
f1 on large fixtures · tokens/run
V7Proactive complexity-gated decomposecontrol-flow · planner_builder
Decision tested
Reactive decomposition (split only after an incomplete).
Mechanism
The planner estimates subtask size before executing and splits big ones upfront.
Pass / kill
Catches "too big to finish in one pass" before the wasted attempt — but the planner estimates blind (it never touches domain tools), which V9 fixes. A high V8 re-execution-success rate weakens V7's case.
first-pass done rate · malformed count
V8Re-execute-once on incompletetrust · execution_policy · cheapest
Decision tested
The invariant that incomplete can never be re-executed (only decomposed/skipped).
Mechanism
Allow exactly one in-place re-execution of an incomplete subtask, with the prior record injected as context ("you tried this and got X"); a second incomplete falls back to decompose/skip. A tiny change (incomplete → new, once).
Pass / kill
Many incompletes on small models are stochastic (sampling noise, a flaky tool), not structural; forcing decomposition on a transient failure spends budget for nothing. A high re-execution success fraction also weakens V7.
fraction of re-executions reaching done · tokens saved vs. decomposing
V9Worker-proposed decompositioncontrol-flow · schema + prompts
Decision tested
That the planner decomposes — blind, since it never reads code.
Mechanism
Extend SubtaskExecutionResult with an optional suggested_subtasks; on incomplete the worker (which just read the code, and knows why the subtask was too big) proposes the split; the planner may adopt, edit, or ignore it.
Pass / kill
The information-flow fix V7 only approximates. Wins if worker-proposed children clear on first pass more often than planner-guessed ones.
child first-pass done rate vs. baseline decomposition
V10Plan carry-forward across attemptsretry/resume · runner flag
Decision tested
That every retry rebuilds an empty plan — discarding and re-doing every done subtask.
Mechanism
_build_task_initial_state keeps the prior attempt's subtask list — done preserved, the failing one reset or pre-decomposed — turning retry into resume.
Pass / kill
Potentially the single biggest tokens/run reduction on multi-attempt tasks. Risk: a poisoned plan — mitigate by carrying forward only when the prior attempt failed at finish stage, or behind its own flag.
tokens/run on multi-attempt tasks · f1 parity
