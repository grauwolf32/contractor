Two verification gates per win
  • unit (CPU, parallel) — a pre-flight correctness gate: proves the change does what it mechanically claims. Cheap, parallel, no model. Not the verification of the hypothesis.
  • eval (GPU, sequential) — the actual verification: on/off A/B on real fixtures via LM Studio, comparing the metric the hypothesis predicts. Run one at a time (model loaded once; never two concurrently → no OOM).

Deferred / rejected (per your guidance)

  • Per-line character cap (AG1) — rejected for now. Capping long lines means the agent can't fully read them; the better fix is to prettify/normalize a file before reading, not truncate mid-line. Dropped from this batch.
  • Git tools (N4) — deferred. The agent already has a code-exec/bash tool, so it can run git blame/log directly; a dedicated tool is redundant and every extra tool's schema eats the token budget every turn. Not worth it now.

Phases

Phase 1 — implement + unit-test (parallel, CPU). One agent per win in its worktree: change + focused unit test, run pytest tests/units/… green, commit. Concurrent; no GPU.

Phase 2 — eval, the verification (sequential, GPU, I run it). One branch at a time on LM Studio (lm-studio-qwen3.6, temp 0). Order: QW1 → QW3 (QW4 needs none). Each: run off-arm, then on-arm, read metrics.jsonl + the eval envelope, record the delta. Model loaded once per run, never two at once.
