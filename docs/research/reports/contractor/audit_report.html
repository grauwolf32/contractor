Memory-overlay filesystem fs-overlay

8 findings · 3 verified bugs

The overlay is a carefully-built fsspec COW layer with solid path normalization (delegated to RootedLocalFileSystem for symlink/sandbox safety, which is sound) and a pure, well-factored diff/patch split. The main risks cluster around (1) the parallel-fork merge logic, whose delete-merge baseline is semantically wrong and whose dir/delete union ignores conflicts and tombstone-vs-live races; (2) several state-mutation edge cases (mv into a subtree, ranged base reads, write-file flush concurrency) that can corrupt or mis-handle data; and (3) encoding inconsistencies where diff/patch assume UTF-8 while writes accept arbitrary encodings. No symlink-escape hole was found in the overlay itself because all real-path resolution happens in the sandboxed base_fs. Most findings are medium severity edge cases rather than common-path failures.

Fork merge propagates deletes using a meaningless baseline (pre-fork files vs tombstone paths)
✓ verified bugMEDIUMbugconfidence: medium
contractor/tools/fs/merge.py:105-108
merge_overlay_forks computes `new_deletes = fork._deleted - set(pre_fork_files)`. `fork._deleted` is a set of tombstone *paths* (deletions of base_fs entries), while `pre_fork_files` is the dict of pre-fork overlay *file contents*. Subtracting overlay file keys from tombstone paths is a category mismatch: the two sets rarely overlap (a deleted path is, by definition, usually not a live overlay file), so essentially ALL tombstones in every fork — including those that already existed pre-fork — are unioned into the target. The intended 'only changes after the fork point' semantics are not achieved. Re-adding pre-fork deletes is idempotent (harmless), but a fork that *restores* a previously-deleted path (clears a tombstone) will not have that restoration reflected — the target keeps the stale tombstone. Unlike file conflicts, delete/dir merges are blindly unioned with no conflict detection at all (lines 105-108), so a path deleted in one fork but rewritten in another resolves nondeterministically depending on iteration order.
for fork in forks:
    target._dirs.update(fork._dirs)
    new_deletes = fork._deleted - set(pre_fork_files)
    target._deleted.update(new_deletes)
Fix Baseline deletes against the pre-fork tombstone set (capture `pre_fork_deleted = set(overlay._deleted)` alongside pre_fork_files and use `fork._deleted - pre_fork_deleted`). Detect delete-vs-write conflicts (path deleted in one fork, written in another) and surface them in the returned conflicts list rather than relying on dict/set union order. Likewise dir unions should drop dirs that another fork turned into a file.
Verifier rationale (confirmed)
The cited code at merge.py:105-108 matches exactly, and the data-model claim holds up against overlayfs.py. In MemoryOverlayFileSystem, `_files: dict[str,bytes]` is keyed by file path with content values, and `_deleted: set[str]` holds tombstone paths (a base_fs path is added to `_deleted` on rm — see rm_file:921-922, rmdir:963, rm:1006). `pre_fork_files` is `dict(self.overlayfs._files)` (workflow.py:110), so `set(pre_fork_files)` is the set of pre-fork overlay file PATHS. CORE DEFECT CONFIRMED: `new_deletes = fork._deleted - set(pre_fork_files)` subtracts the wrong baseline. To restrict to "deletes after the fork point" you must subtract the pre-fork `_deleted` set — but that set is never passed into merge_overlay_forks (the function only receives pre_fork_files). A tombstoned path (removed from _files, present in base) and a live pre-fork _files key are essentially disjoint, so the subtraction filters out nothing: the filter is effectively dead code. The claim "the intended only-changes-after-fork semantics are not achieved" is literally true. WHERE THE CLAIM IS RIGHT: - The author correctly notes the additive direction is harmless: target IS self.overlayfs (workflow.py:109/139), which already holds the pre-fork tombstones, and fork_overlay replays the pre-fork patch (including delete_path ops) so fork._deleted legitimately re-contains them. `target._deleted.update(...)` re-adding them is idempotent. So the broken filter does not corrupt the additive result. - Restoration gap is a REAL correctness hole: merge only ever does `_deleted.update()`, never removes tombstones. If a fork restores a previously-deleted path (restore()/_unhide_path clears the tombstone), the target keeps the stale tombstone. Worse, if a fork rewrites a previously-tombstoned path, the write lands in target._files but the tombstone in target._deleted survives, and every read path (cat_file:853, open:668, exists:690, isfile:705) checks _is_deleted BEFORE _files, so the resurrected file stays hidden. Genuine bug. WHERE THE CLAIM OVERREACHES: it says delete/rewrite "resolves nondeterministically depending on iteration order." That is inaccurate — it is deterministic. Both the file loop (85-103) and the delete loop (105-108) always run, so a path written by one fork and deleted by another ends up in BOTH _files and _deleted, and _deleted's read precedence makes delete win every time, regardless of order. It is a silent, unflagged conflict (never added to the returned `conflicts` list), but not order-dependent. PRACTICAL IMPACT: the sole caller (trace_graph_pathpar) only adds @trace annotations — workers write/modify, they don't delete or restore — so the broken cases are latent. The test suite (test_overlay_merge.py) exercises only file writes; zero coverage of _deleted propagation. The defect is real and the code is genuinely wrong, but the most-cited consequence is harmless and the truly-broken cases aren't triggered in-repo, so this is a medium-severity latent bug rather than high.
mv/copy into a subdirectory of the source corrupts or loses data
✓ verified bugMEDIUMbugconfidence: medium
contractor/tools/fs/overlayfs.py:1024-1061
Recursive `copy` iterates `self.find(path1, withdirs=True)` and writes each entry under target_root while mutating the same overlay. If path2 is nested under path1 (e.g. copy /dir -> /dir/backup), the freshly-written destination files become new descendants of the source subtree; depending on find() snapshotting they may be re-copied or skipped, and `mv` then calls `self.rm(path1, recursive=True)` which deletes path1 *and the just-copied path2 beneath it*, losing all moved data. `find()` returns a materialized dict so it won't infinite-loop, but the rm-after-copy in mv (line 1060-1061) unconditionally removes the entire source subtree including any target nested inside it.
def mv(...):
    self.copy(path1, path2, recursive=recursive, **kwargs)
    self.rm(path1, recursive=recursive, maxdepth=maxdepth)
Fix Reject or special-case moves/copies where the normalized path2 is path1 or a descendant of path1 (e.g. raise ValueError('cannot move a directory into itself')). At minimum compute the source listing before any writes and refuse if target_root.startswith(source_root + '/').
Verifier rationale (confirmed)
Re-read contractor/tools/fs/overlayfs.py and the calling layer. The claim holds up on every load-bearing point. copy() (lines 1024-1050): for recursive dir copy it iterates `self.find(path1, withdirs=True, detail=False)` and writes each entry to `posixpath.join(target_root, rel_path)` via cp_file -> pipe_file. find() (lines 1196-1230) fully materializes its result through `self.walk(...)` and returns a `sorted(result)` list, so iteration is over a pre-write snapshot — confirming the claim's note that there is no infinite loop and the destination files DO get written correctly into the nested target first. mv() (lines 1052-1061) is exactly the cited two-liner: `self.copy(path1, path2, recursive=...)` then `self.rm(path1, recursive=recursive, maxdepth=maxdepth)`. rm(..., recursive=True) (lines 988-1015): computes `prefix = path.rstrip('/') + '/'` and deletes every key in self._files where `file_path == path or file_path.startswith(prefix)` (lines 992-994), same for self._dirs (996-1000). pipe_file stores destination content into `self._files[path]` keyed by the normalized destination path (line 823). So for `mv('/dir', '/dir/backup')`, the copied files at `/dir/backup/...` start with prefix `/dir/` and are unconditionally deleted by the prefix match. rm also tombstones path1 (`self._deleted.add(path)`, line 1006) whose _is_deleted ancestor-walk additionally hides any base-derived nested target. No guard exists: the agent-facing wrapper write_tools.py mv -> _dual_path_op (lines 182-209) validates src and dst independently (existence + sandbox) but never checks whether dst is nested under src, and neither copy() nor mv() reject the overlap. The tool is reachable from the worker tool surface (write_tools.py:294-306, registered at line 1387). I downgrade severity to medium: the defect is real and reachable, but it operates only on the in-memory MemoryOverlayFileSystem overlay (the host filesystem is not directly corrupted; blast radius is the worker's per-run artifact diff), and the triggering input (mv of a directory into its own subdirectory) is an uncommon pattern rather than a routine one. Still a genuine silent data-loss bug that should be guarded (reject dst nested under src, or copy-then-rm-then-restore ordering).

✓ verified bugLOWperformanceconfidence: high
contractor/tools/fs/overlayfs.py:843-867
cat_file accepts start/end but, when the path is not in the overlay, calls `self.base_fs.cat_file(path, **kwargs)` WITHOUT forwarding start/end, then slices the full result in Python (`data[start:end]`). For large base files a ranged read (the common case for paginated reads / read-caps that the project explicitly added) reads and materializes the whole file every time, defeating the purpose of byte ranges and risking OOM on large source files. return data
Fix Forward the range to the base when possible: `self.base_fs.cat_file(path, start=start, end=end, **kwargs)` (fsspec's LocalFileSystem.cat_file supports start/end), falling back to read-and-slice only if the backend rejects the kwargs.

Diff/patch hard-code UTF-8 while writes accept arbitrary encodings
LOWbugconfidence: medium
contractor/tools/fs/overlay_diff.py:16-31
_is_text and _lines in the diff renderer (and _is_text logic generally) decode strictly as UTF-8 and use errors='replace' for line splitting, but pipe_file/write_text/_OverlayWriteFile let callers write with any encoding (`kwargs.get('encoding')`, default utf-8). A file written as latin-1/utf-16 will be classified as binary by the diff (any null byte → binary) or rendered with replacement chars, producing a misleading or lossy diff. The patch path is byte-exact (base64) so this only affects the human-facing diff(), but it means non-UTF-8 source files are silently shown as 'Binary files differ' even when modified textually.
def _is_text(data: bytes) -> bool:
    if b"\x00" in data:
        return False
    try:
        data.decode("utf-8")
        return True
Fix This is acceptable for diff display but should be documented; if multi-encoding source trees matter, thread the file's encoding (or a small charset sniff) into render_overlay_diff instead of assuming UTF-8.
_OverlayWriteFile.flush writes full buffer on every flush; partial flush + concurrent reader sees inconsistent state
LOWbugconfidence: low
contractor/tools/fs/overlayfs.py:1502-1512
flush() takes the fs lock only around the dict assignment, copying the entire BytesIO buffer into self._files[path] each call. The write buffer itself (self._buf) is not lock-protected, so if the same fs/path is opened for write on two threads (the fork model runs paths concurrently, though on separate fork instances), interleaved write()/flush() on a shared instance would race on the un-synchronized BytesIO. Within a single fork this is fine, but the class advertises an RLock for thread-safety elsewhere; the write-file object is the one mutable surface left unguarded. Also, an explicit flush() mid-write publishes a truncated/partial file to readers (who go through the lock and will see it) — acceptable for fsspec semantics but worth noting.
def flush(self) -> None:
    with self.fs._lock:
        self.fs._files[self.path] = self._buf.getvalue()
        self.fs._invalidate_filetype(self.path)
Fix Document that a single _OverlayWriteFile is not safe to share across threads (fsspec norm), or guard the buffer if shared use is possible. The fork-per-path design already sidesteps this; no change needed if that invariant is enforced.

GitLab filesystem backend fs-gitlab

6 findings · 3 verified bugs · 2 false positives

The module is a reasonably structured read-only fsspec backend with background loading and API fallback, but it has several correctness hazards. The most serious are concurrency bugs: caller threads mutate the shared entry dicts without locking while the background loader swaps them, and reload() clears state out from under a still-running loader thread. There is also a response-lifecycle leak in the retry wrapper, fragile/incorrect line-number reporting in the GitLab-search grep fallback, broken offset pagination for large trees, and a retry path that can re-raise None. None block the happy path on small repos, but they produce wrong results or crashes under concurrency, large repos, or transient HTTP failures.

Background loader and caller threads mutate shared dicts without synchronization
✓ verified bugLOWbugconfidence: high
contractor/tools/fs/gitlabfs.py:1419-1431, 1028-1054
_get_file_entry (called from any worker thread via _open/cat_file) does `self._entries[norm] = entry` and mutates `entry.data`/`entry.size` with no lock, while the background loader thread concurrently rebuilds and reassigns `self._entries`, `self._children`, `self._tree_paths` in _build_tree_index/_build_index. A read started during loading can insert an entry into a dict that is then wholesale replaced by the loader's swap, silently dropping the fetched data, or iterate a dict (grep/glob/file_count/memory_usage) while it is being replaced (RuntimeError: dictionary changed size during iteration). The comment 'Atomic swap ... effectively atomic in CPython' only covers the reference rebind, not the read-modify-write on individual entries. The fs holds a `_lock` only inside _BackgroundLoader for state, not for the index structures.
self._entries[norm] = entry / entry.data = data ... (no lock) vs `self._entries = entries; self._children = children; self._tree_paths = ...` in _build_index running on the loader thread
Fix Guard all reads/writes of _entries/_children/_tree_paths with a single RLock (or make TreeEntry.data writes go through a lock), or treat the index as fully immutable after each swap and never insert from caller threads (cache API-fetched data separately).
Verifier rationale (confirmed)
I re-read the cited regions in /home/ruslan/src/contractor/contractor/tools/fs/gitlabfs.py. The core claim holds: the index structures are shared mutable state accessed from two threads with no lock protecting them. - The background loader runs on a daemon thread (start() at line 601-606, _run at 608), default constructor mode is blocking=False (lines 871-872, 911-914), so the loader thread ALWAYS exists during use. - Loader-side writes have no lock: _build_tree_index (lines 1028-1030: self._entries = entries; self._children = children; self._tree_paths = tree_paths) and _build_index (lines 1052-1054). The _BackgroundLoader._lock (line 533) is only ever taken around self._state (lines 544, 585, 623, 637), never around the index dicts. - Reader-side writes also have no lock: _get_file_entry (lines 1419-1431) does self._entries[norm] = entry (1427) and entry.data = data / entry.size = len(data) (1429-1430). This is reachable from worker threads via _open (1443) / cat_file (1459). - Reads during loading are by design, not a corner case: the fallback paths in _get_or_fetch_file_data (lines 1102-1129) and ls/info (1150-1172) are explicitly gated on `not self.is_ready` and proceed to touch self._entries while the loader is still running. So loader-vs-reader concurrency is the intended operating regime. So the dropped-write race is real: a reader inserting into the current _entries dict via _get_file_entry can have that insert discarded when the loader rebinds self._entries to a fresh dict in _build_index. However this is self-healing — the next read re-derives the data via the API fallback, so it wastes work rather than corrupting state. One part of the claim is technically wrong: it asserts iterating a dict (grep/glob/file_count/memory_usage) "while it is being replaced" by _build_index yields RuntimeError: dictionary changed size during iteration. The wholesale rebind `self._entries = entries` does NOT mutate the dict object an in-flight iterator already holds — it only rebinds the attribute, leaving the old object intact, so the loader's swap by itself cannot raise that RuntimeError. A genuine "changed size during iteration" RuntimeError requires a concurrent insert (_get_file_entry, line 1427) into the same dict object being iterated by _glob_in_memory (1292) / file_count (1068) / memory_usage (1077-1081). That is possible but requires concurrent reader activity, not the loader swap as the claim states. Also note grep is gated on is_ready (line 1330) so _grep_in_memory's iteration (1368) only runs post-final-swap and is the safest of the four; glob is the exposed one (runs at tree_available, line 1283). Verdict: a real unsynchronized-shared-state defect exists, but the severity is lower than implied — the dropped write self-heals via API re-fetch, and the cited RuntimeError mechanism (iteration crashing due to the loader's reassignment) is inaccurate; the actual crash window requires concurrent reader-insert plus reader-iterate. Hence confirmed but low.
reload() clears index while a prior background loader thread is still running
✓ verified bugMEDIUMbugconfidence: high
contractor/tools/fs/gitlabfs.py:947-977
reload() calls `self._entries.clear()`, `self._children.clear()`, `self._tree_paths.clear()` and then `self._start_background_load()`, which creates a brand-new _BackgroundLoader and overwrites self._bg_loader. The previous loader's daemon thread is neither stopped nor awaited; it keeps running and will call _build_tree_index/_build_index on `self`, racing with the new loader and repopulating cleared state with stale data from the old ref/settings. There is no cancellation token and start() only no-ops if the SAME _bg_loader thread is alive (a new instance is created each reload), so two loader threads can run simultaneously.
self._entries.clear() ... self._start_background_load()  ->  self._bg_loader = _BackgroundLoader(self); self._bg_loader.start()
Fix Before reloading, join/cancel the existing loader (or invalidate it via a generation counter so a stale thread's results are discarded). At minimum, don't create overlapping loader threads.
Verifier rationale (confirmed)
Read gitlabfs.py around the cited region and the _BackgroundLoader class. The race is real. reload() (lines 962-977) mutates self._settings/ref, clears _entries/_children/_tree_paths/_errors, then calls _start_background_load(). _start_background_load() (lines 936-939) unconditionally constructs a NEW _BackgroundLoader(self) and overwrites self._bg_loader, then calls start(). _BackgroundLoader.start() (lines 589-606) only no-ops when "self._thread is not None and self._thread.is_alive()" — but self._thread belongs to the freshly-created instance and is None, so the guard never inspects the PRIOR loader's thread. The previous daemon thread is never cancelled or joined: _BackgroundLoader has no cancellation token (only _ready_event/_tree_ready_event, __init__ lines 530-540). The stale thread continues in _run() (lines 608-641), calling self._fs._build_index()/_build_tree_index() on the shared fs and reassigning self._entries/_children/_tree_paths. Two loader threads can thus run concurrently and race to repopulate the index; whichever finishes last wins, so a stale loader can clobber the new ref's data. One correction to the report: the CITED EVIDENCE implies the loaders repopulate via the .clear()'d dicts, but _build_index/_build_tree_index actually build fresh local dicts and reassign by reference (lines 1028-1030, 1052-1054, commented "Atomic swap"). That atomic swap only prevents torn reads of one dict; it does NOT prevent two competing loaders, nor inconsistency across the three separately-reassigned containers (a reader can observe _entries from loader A and _children from loader B). So the described in-place-corruption mechanism is slightly off, but the underlying defect — an uncancelled prior loader racing the new one after reload(), with start()'s liveness guard structurally unable to see it — is confirmed by the code. Downgraded to medium: it only triggers on an explicit reload() overlapping an in-flight load, in a GitLab-backed read cache, yielding a stale/inconsistent in-memory index rather than disk corruption or a crash.
GitLab Search grep fallback produces wrong line numbers and inconsistent matches
✓ verified bugMEDIUMbugconfidence: high
contractor/tools/fs/gitlabfs.py:759-796, 393-437
grep_via_api builds results from the search API 'data' field, which is a small surrounding snippet (a few lines), not the whole file. It iterates `data.split('\n')` and reports `line_number = startline + i`, re-running the user's regex over each snippet line. Lines outside the snippet are never searched (false negatives), and because GitLab's blob search is its own tokenized index (not regex), the set of returned files differs from a true regex grep — so the in-memory path and the fallback path return materially different results for the same query depending on cache readiness. Additionally search_blobs swallows all exceptions with a bare `break`, silently returning partial/empty results on any HTTP error.
data = item.get("data", ""); startline = item.get("startline", 1); for i, line in enumerate(data.split("\n")): ... "line_number": startline + i
Fix Document that the fallback is best-effort/approximate, or for each matched blob fetch the full file via download_file_simple and grep that for accurate line numbers and coverage. Don't silently `break` on search errors — surface or distinctly log them.
