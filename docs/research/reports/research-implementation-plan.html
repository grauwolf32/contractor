IMPLEMENTATION BLUEPRINT · 2026-08-05 · applies to directions A–AY

Research and implementation plan

Turn the 228-hypothesis memo into a controlled, reproducible program that improves Contractor without turning production code into an experiment harness. The central move is to represent every hypothesis, arm, fixture slice, metric, decision, and implementation change as a versioned artifact.

1. Target outcome

Within one quarter: every promoted behavior change should be traceable from hypothesis → preregistered experiment → immutable run envelopes → statistical decision → guarded implementation → post-promotion regression check. A person unfamiliar with the experiment must be able to reproduce the decision from the repository plus model/runtime identifiers.

Research system

  • Machine-readable hypothesis registry.
  • Dependency-aware priority queue.
  • Paired A/B runner with fixed manifests.
  • Immutable raw results and generated decision records.
  • Dashboard views for evidence, not only latest scores.

Production system

  • Stable interfaces and typed events.
  • Experiment arms injected through factories/config.
  • No research-specific branching in core loops.
  • Default-off feature flags until promotion.
  • Fast rollback and compatibility tests.

2. Operating principles

  1. Measure foundations before features. AR/AO/AP/AT/AU/AW/AY can invalidate conclusions across dozens of directions.
  2. One mechanism per contrast. If an arm changes prompt, tools, and iteration policy together, it is a system comparison—not evidence for any one mechanism.
  3. Implementation tests prove mechanics; evals test hypotheses. Unit tests cannot verify “recall improves.” Model evals cannot prove a filesystem matcher is correct.
  4. Raw attempts are immutable. Scorers and aggregators are versioned and rerunnable; never overwrite evidence after changing tolerance.
  5. Compare against deterministic floors. Semgrep/CodeQL/OSV and simple structural heuristics are arms, not footnotes.
  6. Optimize adopter utility. Primary frontier: severity-weighted recall, precision/triage cost, GPU-seconds, wall-clock, and analyst review—not token count alone.
  7. Negative results are deliverables. A killed hypothesis removes complexity and prevents repeat spending.
  8. Production defaults change only after replication. Exploratory wins generate a confirmatory run on held-out fixtures.

Keep the machine-readable control plane under research/, published material under docs/research/, and CPU-only contract tests under tests/units/research_tests/. Reusable metric/event primitives belong in production only when production also needs them.

Experiment manifest

Must capture hypothesis_id, design type, control/treatment arm hashes, fixture slice hash, case IDs, paired seed schedule, model/runtime digest, scorer version/parameters, primary metric, MDE, α/FDR family, sample plan, sequential looks, stop rules, timeout policy, exclusion rules, cost ceiling, and owner. Freeze the manifest before the first model call; amendments create a new revision and invalidate confirmatory status.

Run envelope extension

Keep eval/v1 readable. Add optional fields or introduce eval/v2 only after a compatibility reader exists: experiment_id, arm_id/hash, fixture_digest, model_digest, runtime_digest, seed_requested, seed_effective, scorer, tool_outcome_summary, stage_metrics, gpu_seconds, wall_clock_ms, and artifact content hashes.

Decision record

Record actual sample size, exclusions, raw and adjusted effect, confidence/credible interval, FDR-adjusted value, guardrail outcomes, subgroup stability, cost delta, result status, reviewer, implementation action, rollback flag, and follow-up. The record must distinguish statistically supported from worth shipping.

7. Prioritization

Use a two-stage process: hard dependency gates, then a scored portfolio. Do not rank all 228 items as if independent.

7.1 Hard gates

  1. Is the metric trustworthy? If not, route to AR/AP/AO/AT/AW/AY first.
  2. Can the hypothesis change a decision? If both outcomes lead to the same implementation, do not run it.
  3. Does a cheaper deterministic test answer it? Run that first.
  4. Is the arm separable and reversible? Refactor the seam before the model eval.
  5. Is there enough fixture binding? Do not test truncation on fixtures that never reach the cap.

7.2 Score

Priority = (DecisionImpact × EvidenceLeverage × MissionFit × Reuse × Reversibility) / (GPUCost × EngCost × ValidityRisk × DependencyDepth)
Score each 1–5. Use geometric means within numerator/denominator so one extreme does not dominate. Add a +20% “information value” boost when the result would kill or unlock five or more dependent hypotheses.

9. Verification protocol

9.1 Four test layers

LayerQuestionExamples
L0 ContractDoes the mechanism behave exactly?Glob parity, schema validation, arm resolution, seed propagation
L1 Micro-evalCan the mechanism affect its intended local behavior?Malformed repair, typed empty retry, tool argument correction
L2 Capability evalDoes quality improve on representative tasks?Trace recall, exploit success, hypothesis hit-rate
L3 Deployment evalDoes utility hold end to end under realistic conditions?Clean targets, distractors, lifecycle handoff, triage cost

9.2 Standard experiment sequence

  1. Preflight: CPU contract tests; confirm the arm changes only intended bytes/config.
  2. Binding check: prove the intervention activates on ≥30% of selected cases (cap reached, tool failure injected, path branches, etc.).
  3. Pilot: small paired sample to estimate variance and execution health; never use it for promotion.
  4. Freeze: set MDE, N, stopping boundaries, exclusions, metric version, and cost ceiling.
  5. Run paired arms: same fixture order and requested seed, randomized arm order; record actual serving variance.
  6. Analyze primary metric: paired effect and interval; then guardrails and diagnostic subgroups.
  7. Correct multiplicity: within the preregistered experiment family.
  8. Adjudicate scorer-sensitive cases: blind review; preserve both original and corrected GT.
  9. Replicate: fresh fixtures or a second model/runtime—not merely more attempts on the same public cases.
  10. Promote or kill: update registry and decision record immediately.

10. Statistical decision system

  • Unit of analysis: fixture/case, not individual finding. Attempts are nested within cases.
  • Primary estimate: paired case-level delta. Use paired bootstrap CIs; use McNemar for paired binary completion as a diagnostic.
  • Repeated attempts: report pass@1 and pass@N, but do not treat attempts as independent cases.
  • Seeds: request common random numbers; AR1 measures how effective the serving stack makes them.
  • Multiplicity: Benjamini–Hochberg FDR within a declared batch; primary outcome remains one per hypothesis.
  • Sequential testing: group-sequential looks at 25/50/75/100%, with alpha spending or always-valid intervals. Stop for efficacy, futility, or cost.
  • Non-inferiority: efficiency hypotheses require quality above a preregistered margin and cost improvement—not “p > .05 means equal.”
  • Small-vs-large claims: use headroom-normalized uplift and an interaction term; void ceilinged large-model comparisons.
  • Scorer sensitivity: rerun AR2 tolerance grid. A result that flips becomes scorer-sensitive, not supported.
Promotion rule example: treatment improves severity-weighted recall by ≥5 percentage points; 95% paired interval excludes 0; FDR q≤0.10; precision drops no more than 2 points; GPU-seconds rise ≤15%; effect direction holds on fresh fixtures. All five clauses must pass.

12. Implementation roadmap

Phase 0 — inventory and freeze (week 1)

  • Export all 228 hypotheses into YAML with status/evidence links.
  • Assign aliases from old planner V* to PV*.
  • Hash and archive existing run envelopes; record scorer versions.
  • Define current production defaults as arm baseline-2026-08.

Phase 1 — research control plane (weeks 2–3)

  • Implement registry/manifests/JSON schemas and validation CLI.
  • Implement arm resolver over existing env/version seams.
  • Add model/runtime/fixture/scorer digests to envelopes.
  • Create research list, plan, run, rescore, decide, report.

Phase 2 — validity floor (weeks 3–5)

  • AR1 serving-noise repeats; AR2 scorer tolerance; AR3 FDR families.
  • AO1 deterministic baseline; AP1 blind GT adjudication sample.
  • AW1 typed tool outcomes; AT1 miss-cause join.
  • AU1 GPU-seconds; AY2 secure twins/clean targets.

Phase 3 — cheap, high-confidence wins (weeks 5–7)

  • A1 prefix caching, A2 retention, AW2 ambiguous-empty recovery.
  • AC2/AC5 extensions using the newly trustworthy miss taxonomy.
  • D simplifications as non-inferiority experiments.

Phase 4 — capability/search substrate (weeks 7–10)

  • H1 minimal def-use primitive and H4 dominating-control check.
  • AX1 failure router; AX2 offline calibrated difficulty model.
  • Only then prototype AX3 external tree and compare with U/AL baselines.

Phase 5 — realistic end-to-end confirmation (weeks 10–12)

  • AY1 distractor sweep and AV2 size curve.
  • C proof-chain verification plus AY3 lifecycle subset.
  • Decide whether residual misses justify L/V ensemble or AI escalation.

15. Operating cadence

Weekly

  • Monday: triage new hypotheses, dependency changes, and runtime capacity.
  • Tuesday: freeze manifests; run CPU preflight and binding checks.
  • Wednesday–Thursday: sequential GPU queue, one heavy experiment at a time; cheap rescores in parallel.
  • Friday: blind adjudication, decision records, registry/status update, publish negative results.

Monthly

  • Re-run production canary suite and deterministic floors.
  • Audit stale supported hypotheses not replicated within 30 days.
  • Review portfolio balance and cost per decision, not number of runs.
  • Search recent primary literature and attach only mechanisms that change a test or decision.

Dashboard views

  • Hypothesis funnel by state and age.
  • Dependency graph and blocked high-leverage items.
  • Effect-size forest plot with raw/adjusted intervals.
  • Quality × GPU-seconds Pareto frontier.
  • Miss-cause distribution by fixture/model/backend.
  • Scorer-sensitivity and GT-adjudication deltas.
  • Promotion health and rollback status.

17. Definition of done

A hypothesis is not done because code exists or one run improved.

  • ✓ Claim, mechanism, MDE, primary metric, guardrails, and dependency chain are recorded.
  • ✓ Contract tests prove the intervention actually activates.
  • ✓ Manifest was frozen before model calls.
  • ✓ Raw attempts, configuration hashes, scorer identity, and artifacts are preserved.
  • ✓ Decision rule and multiplicity correction were applied.
  • ✓ Result is marked supported, refuted, or inconclusive—never “promising” indefinitely.
  • ✓ Supported result replicated on held-out evidence before default promotion.
  • ✓ Promoted code has rollback, documentation, and post-promotion monitoring.
  • ✓ Refuted code/flags are removed or explicitly retained for a documented reason.
North-star program metric: severity-weighted, above-deterministic-floor, evidence-confirmed findings per GPU-hour at a bounded clean-target false-positive rate—reported separately for the small self-hosted model and the larger comparison model.
