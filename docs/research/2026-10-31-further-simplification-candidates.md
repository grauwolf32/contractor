# Дополнительные направления упрощения Contractor

Дата: 2026-10-31. Просмотренная ревизия:
`711320fc1de58155aa549967f4813475ad581f3d`.
Область: конфигурация исполнения, Studio, Managed Evals, Planners и предметные
правила стандартов внутри Audit.

Основные кандидаты после редизайна Audit — каскад настроек исполнения,
дублирующая семантическая валидация Studio и самостоятельная оркестрация Evals.
Модельные Planner и Worker сохраняются по решению пользователя.
Сокращение требует выбора
поддерживаемых возможностей и гарантий; перенос прежнего кода между пакетами
сам по себе не уменьшает сложность.

Связанное [исследование сложности](2026-10-31-architecture-simplification-research.md)
содержит исходные наблюдения и уже выполненные упрощения.

## Статус на 31 октября 2026

Пользователь попросил сохранить обсуждённые направления пересмотра.
Перечисленные варианты остаются предложениями агента. Решения об удалении
возможностей не приняты; задачи на реализацию этой заметкой не создаются.
Текущее поведение определяет спецификация соответствующего компонента.

Решение пользователя от 2026-10-31: сохранить модельные Planner и Worker как
отдельные уровни. Их удаление исключено из кандидатов и порядка пересмотра.

## Размеры областей

| Область | Примерный размер рукописных исходников |
| --- | ---: |
| Go configuration | 10,9 тыс. строк во всём `internal/config`, включая полезную общую логику |
| Studio | 6,6 тыс. строк UI, включая CSS |
| Managed Evals | 12,7 тыс. строк Go и 8,6 тыс. строк UI |

Это физические строки с комментариями и пустыми строками, без явных тестовых
и generated-файлов. Размер области не является оценкой чистого сокращения;
границы пересекаются через общие контракты, поэтому числа нельзя складывать
как независимую экономию.

## Каскад конфигурации исполнения

Выбор моделей, Gateway, credentials, summarizer и compactor складывается из
настроек AgentTemplate, Workflow, Run, Stage, Worker и escalation. Его правила
поддерживают Go, Runtime, wire-контракты и Studio.
Источник: [слои ExecutionConfig](../spec/configuration/agent-templates.md#executionconfig-layers)
и [resolver](../../internal/config/execution_config.go).

Предложение: сохранить существующий resolved snapshot на Run, сократив
authoring до базовой конфигурации и одного явно выбранного уровня override.
Существенно другое поведение можно оформлять отдельной версией Workflow.

Цена — меньше точечных переопределений и динамических комбинаций escalation,
возможно больше версий Workflow. До изменения контракта нужно перечислить
реальные комбинации shipped-конфигураций и поддерживаемые сценарии. Правила
секретов и фиксация точной эффективной конфигурации сохраняются.

## Семантическая валидация Studio

Две большие функции локальной валидации содержат около тысячи строк и
повторяют часть серверных правил, но не обеспечивают полное разрешение
зависимостей. Источники: [validation.ts](../../ui/src/routes/studio/validation.ts)
и [advanced-validation.ts](../../ui/src/routes/studio/advanced-validation.ts).

Предложение: оставить YAML-редактор, просмотр графа, базовые проверки контролов
и отображение ошибок авторитетного validator. Полная проверка сейчас доступна
через CLI. Полная проверка черновика из UI потребует узкой серверной операции;
её наличие нельзя считать уже реализованным.

Более сильный вариант — визуально редактировать только типовые настройки,
остальное оставлять в YAML. Цена — меньше мгновенных подсказок и визуальной
настройки редких полей. Черновик должен сохраняться при ошибке, а UI должен
точно сообщать, какую проверку он прошёл.

## Самостоятельная оркестрация Managed Evals

Evals имеют собственные experiment/member/submission lifecycle, восстановление
операций, selections и поколения представлений. Исполняемым элементом может
быть Run или целый Audit. Источники: [Managed Evals](../spec/evals/managed-evals.md),
[driver](../../internal/evalservice/driver.go) и
[collection](../../internal/evalservice/collection.go).

В модели исследовательской платформы стоит проверить возможность использовать
общий механизм выполнения исследований. Данные тестовых случаев, скрытая
ground truth, scoring, повторные выборки и сравнение остаются предметной
логикой Evals. Отдельно можно пересмотреть необходимость двойного управления
`server/external`, live comparison и выбора разных ревизий результатов.

Этот пересмотр следует за работающим новым Audit. Первый опыт должен показать
одно A/B-исследование с точными входами и конфигурациями, учётом всех попыток,
изоляцией ground truth, scoring и корректным восстановлением. Цена сокращения
зависит от выбранных режимов управления и сравнения. Новый универсальный
coordinator до такой демонстрации не нужен.

## Сохранение модельных Planner и Worker

Модельный Planner строит подзадачи и вызывает Worker, внутри которого работает
другая модель. Оба уровня требуют контекста, истории, бюджетов, завершения и
восстановления. Источник: [Planners](../spec/execution/planners.md).

Пользователь 2026-10-31 решил сохранить эту архитектуру. Предложение заменить
её детерминированным Workflow и одним Worker снято. Адаптивная декомпозиция
Planner и выбор Workers остаются поддерживаемыми возможностями.

Пользователь указал два основания решения:

- На длинных Runs с моделями ограниченного контекста иерархия позволяет
  разделять контекст общего плана и локальной работы над подзадачами.
- Planner отделён от Worker через A2A. Эта граница позволяет развивать
  исполнителя независимо от планирования, включая другой runtime или
  general purpose агента вместо ADK-исполнителя.

Такой путь уже описан для OpenCode в
[proposal 0048](../proposals/0048-opencode-audit-environments.md): существующий
A2A WorkerInvoker обращается к Runtime endpoint, за которым работает адаптер
другого исполнителя, а Runtime формирует WorkerCompletion. Это проектное
направление, а не готовая смена настройки: текущий
[контракт Runtime Agent](../spec/execution/runtime-agent.md) допускает другие
in-process adapters, а предложенный OpenCode-вариант требует явного расширения
контрактов исполнения и lifecycle. Само наличие A2A не означает полной
эквивалентности инструментов, наблюдений и бюджетов разных исполнителей.

## Предметные правила стандартов внутри Audit

Встроенные modes, mappings и evidence policies стоит пересмотреть при переходе
к общей модели гипотез. Checklist и выбранные требования стандарта могут
поставлять исходные гипотезы с критериями достаточности; общий coordinator
исполняет их одним способом. Источник:
[standard-backed inventories](../spec/audits/audits.md#standard-backed-inventories).

Предметные правила остаются у владельца соответствующего домена. Сохраняются
точная версия источника, исходный состав покрытия, непроверенные пункты и
условия достаточности доказательств. Перенос семантических правил в
модельный текст не заменяет эту гарантию.

Это часть уже обсуждённого сокращения Audit, а не дополнительная независимая
экономия.

## Рекомендуемый порядок пересмотра

1. Упростить authoring конфигурации исполнения и число уровней override.
2. Удалить дублирующую семантику Studio с учётом выбранного языка конфигурации.
3. После работающего нового Audit проверить Evals на общем механизме выполнения.

Для каждого изменения фиксировать сохраняемый сценарий, потерю возможностей,
реальных callers, границы размера и доказательство восстановления. Результат
измерять по production LOC, авторитетным представлениям, durable states,
controller loops и receipt/lease-механизмам. Сокращение проверок не должно
скрывать повторные действия, потерю evidence или неверные выводы о покрытии.
